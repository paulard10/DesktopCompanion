# M3.0 implementation roadmap and product behavior specification

Date: **2026-10-27 (Europe/Madrid)**. **Planning only. User approval is required before M3.1.** Companion source and the installed v0.1.1 are unchanged. Evidence and pinned references are in [56](56_M3.0_ARCHITECTURE_AND_REFERENCES.md).

## 1. Product contract and proposed order

Deliver a recognizable small robot that accompanies the pointer at a comfortable distance, rests, and can return to a clickable home. Screen explanation is a separate explicit interaction; it grants no computer-control authority. Start with Windows remains off unless independently chosen; Start Awake remains independent; existing Wandering starts off. No new autonomous mode turns on during migration or upgrade.

Order: **M3.1 shared compact layout → M3.2 voluntary following → M3.3 optional home → M3.4 local selection/crop → M3.5 explicit vision request → M3.6 restrained guidance and autonomy polish.** Validate each before the next. M3.4 depends on the pause/intent boundary from M3.2, but does not require home to be enabled or even shipped. Retain v0.1.1 installer/checkpoint as the last validated release until a separately authorized release passes installed tests.

All numeric motion/size/budget values below are **initial proposed criteria**, not observed performance or already approved UX. User-visible behavior takes priority over matching a reference project's constants.

## 2. Ownership and interfaces

Keep **three orthogonal sources of state**, not a new giant enum that duplicates all existing reducers:

1. **Visual lifecycle:** existing renderer BehaviorState owns sleep/wake blends, alertness and inactivity; characterDirector owns facial/secondary presentation. SLEEPING_AT_HOME is derived from confirmed home docking plus visual SLEEPING. WAKING remains the existing visual phase. Do not send sleep-phase decisions from an LLM.
2. **Desktop intent:** one main-process autonomy controller owns the requested mode, temporary goal and exclusive movement owner. Pure planners produce intentions; only overlayWindow applies OS bounds. IDLE, OBSERVING_CURSOR, FOLLOWING_CURSOR, RESTING and RETURNING_HOME are locomotion intentions, not replacements for renderer TRACKING.
3. **Interaction session:** existing chat/speech/session state and a future screen-context session supply blocking reasons. CHATTING, SCREEN_SELECTING and PAUSED are derived blockers. A pause stores no stale follow destination or animation clock that later catches up.

Proposed small contracts (independently implemented, no framework):

- **AvatarLayout:** version/profile id, fixed window size, body center/radius, projection body diameter, conservative visual envelope, chat-button geometry and trail attachment. Main selects known profiles; renderer cannot upload arbitrary hit geometry. Legacy and compact profiles must share a definition.
- **CursorObservation:** latest global DIP point, monotonic sample time and display id; main reuses its existing 16 ms sampler. Keep only latest/previous points needed for bounded velocity estimation, not a history log.
- **MotionIntent:** owner none/manual/follow/wander/home, optional target in global DIP, expiry, session epoch and pause reason. One arbiter chooses the owner. A main adapter starts existing fixed-goal travel or steps pure follow kinematics; no second setBounds loop.
- **AutonomySnapshot:** visibility, lifecycle phase, chat/voice/generation blocks, own selection state, reduced motion, latest cursor freshness, display workAreas, current bounds and optional home anchor.
- **HomeAnchor:** advisory display id, named corner, bounded DIP inset and optional normalized offset. No cursor trail or unrelated app metadata.
- **ScreenContextSession:** opaque id, phase, display/topology revision, selected rectangle, bounded crop handle, consent state and expiry. Renderer never supplies an image path, executable, source id or arbitrary network URL.
- **VisionProvider:** bounded crop bytes/media type plus explicit question and AbortSignal → existing-style text/status/usage events. Separate from current string-only AIProvider. Main is the only caller; no tool execution API.

Main and renderer clocks are different. Send durations and epochs across IPC; do not compare Date.now timestamps with performance.now. Use a monotonic clock for new motion integration and inject clock/RNG in pure tests.

## 3. State priority and transitions

Priority from highest to lowest:

1. Quit, destroyed renderer/window, unavailable display/topology, system suspension or invalid input sample: cancel motion, invalidate late callbacks, release capture/session resources.
2. User Hide/Pause or our active selection: zero autonomous velocity immediately; no automatic show/focus. Selection restores only surfaces that were visible before it.
3. Explicit user Sleep: cancel autonomous travel and return-session intent; run the existing sleep blend immediately. Preserve current tray Sleep-in-place. Do not silently turn Sleep into Go Home.
4. Chat open, recording/transcribing, TTS or generation: pause motion, discard follow target. Resume only after blockers clear plus a short rest. Keep current manual travel pause/resume semantics.
5. Explicit manual move/Stop: yield autonomous ownership; discard pending follow/wander commands. Proposed follow cooldown **8 seconds** after manual movement finishes. Stop may pause autonomy for the session until the user resumes, as a clear escape.
6. User-requested return home: own the motion until arrival, cancellation, interruption or timeout. Cursor changes do not divert it.
7. Enabled following or enabled wandering: **mutually exclusive** autonomous modes; never allow two planners to issue motion in the same tick.
8. Observe/rest: stationary window with existing ambient animation/gaze.

A sleeping robot is never awakened by cursor samples. The next explicit body/home/tray Wake can start a fresh bounded exploration session if the user enabled that mode. Keep the present six-minute exploration ceiling for the first follow prototype; following must not continuously renew it or override the independent 60-second inactivity policy without a product decision. When its hold expires, cancel automatic motion and allow the existing sleep reducer to settle.

Transitions:

- Off + explicit Enable Follow while awake → observing/rest → follow if thresholds hold.
- Observing + sustained far moving cursor → following; follow + arrival/idle/cooldown → rest.
- Any auto state + blocker → paused; unblock → discard old goal, rest **500 ms minimum**, sample a fresh goal.
- Awake + Home click → returning home → settle → existing USER_SLEEP.
- Docked asleep + Home click → existing WAKE → wake blend → observing if follow remains enabled, otherwise ordinary idle.
- Returning + second Home click → cancel return, rest/idle; if wake is requested explicitly, wake. No queued duplicate return.
- Returning + user Sleep, Pause, Hide or manual override → cancel docking intent. Never deliver a late arrival sleep after cancellation.
- Any own screen selection → SCREEN_SELECTING blocks motion and prevents body capture; screen completion/cancel → restore prior user visibility and bounded resting state.

External app text selection, typing and mouse-button holds are **not known** from cursor positions alone. Do not claim they can be reliably detected without additional access. This version reduces interference with distance/dwell rules, motion click-through and an obvious Pause command. If that proves inadequate, stop and review a separate minimal input-observation proposal; do not quietly add global hooks.

## 4. Compact avatar specification

Candidate: **130 DIP visible height**, adjustable design range **110–140**. Begin with a fixed **176 × 200 DIP BrowserWindow**, body proxy/projection **104 DIP**, centered at (88,100), no invisible slack, and an 18-DIP-radius chat badge centered provisionally at (150,174). The full antenna, arms, hover, wake overshoot and gestures require empirical fit; these values may need more padding.

Migration steps:

1. M3.1a introduces a shared layout module whose **legacy profile exactly reproduces 300 × 400, body 160, badge (262,332), trail radius 80**. No visual or startup change.
2. A development-only compact profile changes projected body size and synchronized hit geometry. Test it in the old window briefly to isolate camera/input errors.
3. Apply the fixed compact bounds once at profile change/creation. Recenter by visual anchor so a profile toggle does not jump across the desktop. Clamp full bounds to workArea. Keep a legacy rollback option; do not resize continuously while traveling.
4. Test all body poses and the existing avatar identity. If the visual envelope clips, enlarge the **window/padding** first, not the click region and not the robot's anatomy. Keep the nominal body proxy conservative; antenna/arm interaction remains a later gate.
5. Once approved, add an explicit size choice. No upgrade should silently resize the installed user's character until that rollout is approved.

Keep PerspectiveCamera, materials, lighting, eye geometry and rig semantic hierarchy. Use CSS/DIP dimensions for camera sizing; cap rendering DPR at 2 independently. Re-evaluate DPR on monitor scale transitions even when DIP size stays unchanged. Update renderer size, aspect/projection and layout id together; stale/mismatched layout means passthrough until synchronized. Main never accepts renderer-supplied arbitrary capture regions.

Chat placement uses the compact rect; preserve its current readable size rather than shrinking chat. Trail derives the tail point from the selected layout; particle lifetime/count remain bounded. Existing full-rig tests must be extended beyond simplified robotFrame bounds to projected vertices or sampled conservative transforms across eye/body/arm/antenna animation extremes. Do not mistake the 160-DIP nominal body circle for exact painted-pixel coverage.

## 5. Cursor-follow behavior specification

Reuse the trusted cursor sampler; do not add another global cursor poll. Retain its 16 ms cadence during the first prototype to protect validated body-click behavior. Run **goal planning at most every 200 ms (5 Hz)** while follow is enabled and awake; run movement integration on the existing **32 ms travel tick** only when moving. Immediate blockers/avoidance are checked with the newest sample every tick. When resting, no movement interval runs; the existing sampler and one bounded wake/deadline scheduler suffice.

Proposed initial tuning:

- Treat cursor changes below **3 DIP** as noise. Estimate direction from latest deltas with **150 ms exponential smoothing**, clamp unreasonable gaps/velocities, and hold the last stable direction through a turn.
- Preferred robot-center offset: **170 DIP behind** the smoothed cursor direction, with an optional seeded lateral offset up to **35 DIP**. No target is the cursor itself. If direction is uncertain, retain a safe side/corner candidate.
- Enter following only if center distance is **over 220 DIP for 250 ms**; stay still in a broad **140–220 DIP** band unless the goal genuinely changes. Target retarget dead zone **24 DIP**; settle when within **8 DIP** and speed under **5 DIP/s**.
- Maximum actual velocity **160 DIP/s**, normal desired speed **90–140 DIP/s**, acceleration/braking bound **320 DIP/s²**. Smooth direction changes through velocity; never teleport. dt is clamped to **64 ms**; a long pause discards velocity/goal instead of catching up.
- A concrete pure integrator can choose desired velocity toward target, limited by speed and braking distance, then cap the velocity change to acceleration × dt, integrate fractional DIP, and round only at setBounds. Test actual per-step speed/acceleration. **Do not call requestTravel repeatedly for a changing follow target**: its smoothstep restarts at zero slope and would stall or jitter. Preserve it for manual/fixed-home travel.
- Enforce an exclusion circle of at least **110 DIP around the newest cursor**, enlarged if a selected layout's visual radius requires it. Check the whole proposed movement segment, not just its end. Stop/replan if it would cross that circle, the cursor is stale (>250 ms), or clamping a goal would put the robot too close. Safety stops may zero velocity immediately.
- If cursor motion stops for **1.2 seconds**, settle and observe; after **6 seconds** of stillness, choose subtle look-around poses and an optional seeded rest, not a compulsory chase. During longer inactivity retain the existing sleep deadline/lease limits.
- To avoid constant motion, after **4–8 seconds** of a movement bout, rest **3–7 seconds**, using injected seeded RNG. No background LLM decides these actions.
- During autonomous motion, body capture is **passthrough** and the badge is hidden; when safely stopped, restore trusted body/badge hit policy after **300 ms stable dwell**. Never accept untrusted renderer hover as input authority. This new policy needs real Windows fast-click tests. An intentionally clickable settled robot still intercepts clicks on its body; do not promise every desktop pixel is always accessible.

Same-monitor MVP: pin an awake session to the avatar's current display. If cursor changes display, stop at the current display and look toward it; no teleport, no crossing a layout gap, no chasing the pointer through a taskbar. A later explicit cross-monitor option needs adjacency paths inside actual display rectangles, seam/DPI tests and topology cancellation. Never use the bounding union of displays as walkable space.

Reduced-motion mode disables automatic desktop translation initially, while retaining manual commands and the existing reduced visual motion. The user can pause/hide from tray; these recovery controls must remain accessible even if the robot cannot be clicked.

## 6. Home and sleep lifecycle

Use **one optional static 2D home BrowserWindow**, not another Three renderer. Default proposed location: bottom-right of the home display's workArea, **16 DIP inset**; user can choose another named corner. Candidate home bounds **80 × 56 DIP**, subject to design approval. The home surface must have an obvious clickable base outside the docked avatar's body proxy. A moving avatar alone cannot keep a fixed home visible, and a permanent desktop-sized canvas is unjustified.

HomeWindow follows current transparent/no-Mica/nonfocusable/showInactive chrome, top-level trusted preload and a **main-owned fixed hit shape**. Reuse the existing cursor sample for its hit decision; no second 16 ms interval. Coordinate overlap tests must ensure the top avatar window passes clicks to the home base. Keep normal floating level, no constant z-order raising, and no keyboard focus.

Render home only on creation/resize/status change. Use local SVG/CSS/Canvas 2D, with no independent rAF, blink interval, WebGL context or sleeping particle loop. Disabled home destroys the window. App Hide also hides home and clears travel/trail. If its renderer fails, release its capture, destroy/hide it, and retain tray recovery.

Dock workflow:

1. Explicit Home click creates an epoch-bound return session, cancels follow/wander goal, resolves a current valid home anchor, and requests fixed-goal travel.
2. Preserve one movement actuator; arrival is reported only when current epoch owns travel and actual bounds are within **3 DIP** of the dock anchor.
3. A new narrow renderer command for **user-requested home transit** may reuse the existing bounded hold mechanism with a hard **15-second maximum**, even near the normal inactivity deadline. This is a deliberate user event, not a cursor-driven lease renewal. Keep the renderer as the authority for sleep blending. Main's session watchdog bounds travel/resources, not facial state.
4. On arrival, settle **400 ms**, clear the transit hold and send existing Sleep. On timeout/blocking interruption, stop safely and fall back to Sleep in place or idle according to the user's latest command; never extend the return indefinitely.
5. A second Home click while docked/asleep sends explicit Wake, finishes the normal wake animation, and re-arms only the previously enabled session mode. A wake must not create a second avatar.
6. Home missing/disabled: existing tray Return Home still works. For an explicit home-and-sleep request, use a safe workArea anchor and Sleep in place if return cannot complete; explain unavailability once in chat/tray without trapping input.

Persist only corner/inset/display association and home-enabled preference after user approval. Do not persist transient dock/velocity/return phase. At startup, preserve current Start Awake behavior; enabling home does not automatically dock, move or wake the robot. Display id is advisory and may change; reconcile against current displays and primary fallback, clamp inset, and cancel in-flight return on any topology revision. No smooth teleport when a monitor disappears is promised: recovery placement is a necessary exception, followed by rest.

## 7. Screen-understanding workflow

### Local capture phase (M3.4)

User chooses **Ask About Screen** from tray/chat → chooses target display if ambiguous → one short-lived focusable selector on that display → draws rectangle → explicit **Capture / Cancel** confirmation → hide our surfaces → one-shot acquisition → trusted crop → restore prior surfaces → crop preview and question in existing chat. **There is no network request in M3.4.**

Tray activation must not blindly use the pointer now sitting on the taskbar to infer the intended monitor. Offer the avatar display plus a display choice in existing UI. A later optional accelerator can use the cursor's display at invocation. Shortcut is off by default, user-chosen, registered only after ready and unregistered on disable/quit; registration failure keeps tray activation working. No keyboard hook.

One session only, one monitor per rectangle, **30-second selection timeout**, Escape/right-click/Cancel, display-change cancellation and stale-epoch rejection. Clamp finite coordinates and rectangle size in main; reject empty/cross-monitor/unexpected sender payloads. Selection intentionally focuses only after user activation, and restores no arbitrary external window.

Capture must occur **after** the selection window and all our visible avatar/home/trail/chat surfaces are hidden. Record which were visible beforehand. Wait for a tested desktop-composition settle before taking the single image; a hide call returning is not proof its pixels have left composition. Verify no self-overlay appears in preview; fail/ask retry rather than silently upload a contaminated frame. No automatic screenshot warmup at boot.

Coordinate procedure:

1. Snapshot display id, global DIP bounds/workArea, scale and rotation for the session. Use display bounds for screen selection; workArea for robot/home.
2. Selector sends only a local DIP rectangle plus session id. Main authenticates the exact WebContents/top-level page and session.
3. The initial adapter requires a **single 1x NativeImage representation** (inspect getScaleFactors), uses getSize(1), and maps local rectangle edges to that actual image by widthRatio = image width / display DIP width and heightRatio = image height / display DIP height. Floor leading edges, ceil trailing edges, clamp to image. This handles reduced-resolution thumbnails without assuming one scalar or globally multiplying origins. Reject unexpected representation scales until normalization and crop-unit tests exist; do not feed 2x bitmap coordinates directly to a logical-image crop operation.
4. Match source display_id exactly. No source-index/name fallback. If dimensions/rotation/mapping are ambiguous, cancel. With a later native physical-pixel source, use the Windows display conversion APIs per display and validate against its physical dimensions.
5. Discard unselected thumbnails/full image references immediately after the crop; never send full-display bytes to the selector/chat/provider.

Electron getSources can return thumbnails for **all displays** and has no rectangle-only/source-id argument. The consent text must disclose temporary display-image acquisition; only the chosen crop is retained/sent. Proposed preflight limits: at most **8 million aggregate requested thumbnail pixels**, at most **2 million crop pixels**, no more than **2 MiB encoded crop** (reject or show reduced-resolution preview), one pending image, **2-minute pending-image TTL**. Inspect actual dimensions as well; native capture allocations are not fully bounded by JS and must be measured. Conservative initial working estimate is up to three raw-image copies plus 256 MiB reserve; refuse if available physical memory is insufficient or unknown. This separate provisional screenshot budget does not change the **1,024 MiB Whisper guard**.

Do not keep PNGs on disk or clipboard by default. Serve one bounded crop preview through a new **in-memory, random-token app:// route**, still same-origin img-src self, TTL and session checked; never turn the packaged-file resolver into general file access. Revoke the route and references on cancel, discard, timeout, close, failure, after completed send or quit. Clear renderer image src and release decoded preview too. Avoid Base64 copies in the selector. Cancellation cannot necessarily interrupt an already-running getSources call; ignore/dispose a late result by epoch and never upload it.

Protected/blank/secure-desktop content is an unavailable result; do not bypass protection or elevate. Avoid logging image contents, source window names, paths, thumbnails or recognized text. The OS's ability to capture is not consent to upload.

### Vision phase (M3.5)

Preview → explicit question → visible provider/model/region and possible charges → separate **Send image and question** action → one cancellable request → plain text explanation in companion chat → dispose crop. Regular text Send and Demo continue unchanged. Demo vision uses a clearly labelled synthetic fixture in tests, not a screenshot sent to Qwen.

Current Qwen is text-only at the application boundary. Official docs list image support for qwen3.7-plus and a Singapore compatible endpoint; document 56 records sources. Prefer validating a separate VisionProvider using that same model/allowed endpoint before adding another provider. Keep capabilities disabled until request-format/entitlement/cost checks pass. Do not automatically switch models, regions or providers after an error.

Main owns encoded crop and builds the content array with text and image_url inline Base64; renderer sends session id and bounded question only. No arbitrary URLs, paths, HTML or source identifiers. Keep HTTPS endpoint allowlist, redirect rejection, bounded output, timeout, single-request concurrency and AbortController; cancellation discards late responses and does not resend. Exact provider caps and parameters require verified documentation at implementation time. Display actual usage where supplied; do not promise zero cost or exact token estimates.

Reuse chat layout and status/Stop controls, but keep vision-session image state outside text conversation history. An answer may be shown as a labelled screen explanation; the image is not attached to subsequent turns automatically. Screen text and model output are untrusted, may be wrong, and cannot invoke tools. “What should I click?” produces a textual suggestion only.

### Guidance/control boundary

Later visual arrows should be generated only after user requests guidance, mapped back from crop coordinates with its topology revision. New screenshot/changed UI invalidates them. Guidance is wholly click-through and short-lived. **No automatic clicking, typing, UIA invocation, scripts or shell execution** is in M3.1–M3.6. A future computer-control milestone needs a separate threat model, explicit permissions and per-action confirmation; screen understanding approval is not approval for control.

## 9. Measurement and acceptance strategy

Keep the 220-test checkpoint as historical baseline, then run typecheck, tests, production build and fresh-process smoke **during each future implementation**, using no real microphone/network in automated tests. Source-string assertions alone cannot establish rendered clipping, click delivery or capture correctness; add pure numerical/fixture tests for the new logic and Windows validation for native behavior.

Use an installed comparison build only after separately authorized packaging. Repeat baseline and feature conditions on the Surface with user-confirmed state; do not close applications or change pagefiles. Take two or three ~10–15 second samples, not long stress loops: sleep, awake idle, follow movement, follow rest, home sleep, selection, cleanup; trail off/on separately. Record CPU-time deltas / wall interval / 12 processors, private commit, working set, GPU frame/engine metrics where supported, available physical/commit headroom, IPC/setBounds counts and subjective typing/selection response. Working-set sums are not exclusive RAM.

Proposed investigation gates: compact legacy-equivalent idle private memory within **+15 MiB**; sleep CPU no more than **+0.3 percentage points whole-machine** over paired baseline; follow travel no more than **+1 percentage point whole-machine** above comparable manual travel with trail off; static home negligible draw activity; no sustained private-memory growth across **10** selection/cancel cycles after settling (investigate >10 MiB retained). Short noisy samples require repeats before conclusions. These values are release-screening proposals, not proven safe budgets.

Keep the existing animation cadence until a separately validated performance change. Use traces only when a regression is observed, with bounded timings/counts and no screenshot/text/cursor-path logging. Add worker/utility-process image transforms only if profiling shows main-thread stalls; extra processes and copies are not free on 8 GB. API capture completion, JS release and resident-memory reclamation can occur at different times.

## 10. Decisions before implementation

1. **Visible size:** options 110/130/140 DIP or legacy. Recommend 130 target with fixed padded window and legacy fallback, because current body/camera/input constants are coupled. Risk: too small to read expressions or clipped gestures. **User visual approval required** before compact default.
2. **Follow personality:** direct chase, continuous spring, or trailing bursts/rest. Recommend trailing bursts with exclusion distance and bounded velocity; current travel is fixed-goal easing and cannot be retargeted blindly. Trade-off: less immediate following, more workability. **User tuning trial required**.
3. **Follow startup/persistence:** always on, remembered on, or session opt-in. Recommend **session opt-in and off every launch** initially; remember only size/home/preset. This matches current Wandering safety. Start Awake/login settings stay independent. Risk: excessive setup versus surprise motion. **Product approval required** to ever remember enabled mode.
4. **Home placement:** any draggable coordinates or named workArea corner. Recommend bottom-right +16 DIP with corner choice and advisory display id. Risk: overlap with user work/taskbar variants. **User corner choice required**, not a new free-drag system.
5. **Home surface:** full-display scene, reused trail, or one static home window. Recommend optional static 2D window; fixed home cannot live in a moving local canvas. Trade-off: one renderer's memory. **Architecture approval required**; disable if measured cost is unacceptable.
6. **Movement priority:** concurrent controllers or exclusive intent. Recommend the priority in section 3 with user Stop/selection/chat above auto behavior; reuse one actuator. Risk: race conditions or late sleep. **No further preference question needed** after plan approval.
7. **Display crossing:** follow immediately anywhere or stay on one display. Recommend same-display MVP; no bounding-union paths. Trade-off: less companionship across monitors, much lower gap/DPI risk. **User approval needed** for later cross-monitor mode.
8. **Selection activation:** tray/chat, always-registered hotkey, or native hook. Recommend tray/chat first and optional user-chosen globalShortcut later. Risk: shortcut conflict or wrong target monitor. **User chooses shortcut if wanted**; hooks excluded.
9. **Capture acquisition privacy:** temporary display thumbnails then crop versus strict region-only native acquisition. Recommend transparent disclosure plus Electron crop MVP. It may acquire surrounding/unselected-display thumbnails briefly. **User acceptance of this scope is required**; otherwise defer to native research.
10. **Vision provider:** assume current text API works, add vendor, or separately validate image mode of current Qwen. Recommend separate provider contract, first check qwen3.7-plus Singapore (official capability documented); preserve text provider and safeStorage. Trade-off: explicit setup and possible cost. **User approval of provider/charges required** before a real request.
11. **Screen consent and retention:** capture/auto-upload, or preview then Send. Recommend two explicit approvals, one crop, no image history/disk/clipboard, TTL and cancel. Risk if wrong: private screen data leaves device. **Approve this contract before capture implementation**.
12. **Full-screen suppression:** claim current flags solve it, native detection, or manual Pause first. Recommend manual Pause/Hide; optional notification-state adapter later with clear limits. Trade-off: user action during presentations. **User preference required** before adding native detection.

## 11. Risk register and response

- **Compact proxy mismatch:** central layout/profile id, fail-closed stale state, real edge tests; rollback legacy.
- **Pointer obstruction during follow:** moving passthrough, exclusion segment and rests; stop rollout if selections/clicks are disrupted.
- **Retarget jitter/motion races:** velocity integrator plus one actuator/owner; deterministic clock-gap/priority tests.
- **Sleep/return disagreement:** derived dock state, explicit user transit TTL, epoch-bound arrival, renderer-owned blends.
- **Mixed-DPI/gaps/hotplug:** same-display movement/selection first, actual-image ratios, topology revision cancels.
- **Home/renderers raise idle RAM:** static draw, optional default off, destroy on disable and measured budget.
- **Capture recursion/timing:** hide all own surfaces and validate composition; no upload of contaminated preview.
- **Image privacy or prompt injection:** main-owned crop, explicit upload consent, no history or action tools, expiry.
- **Wrong source/thumbnail scaling:** exact display_id, no index fallback, numerical fixture tests plus actual Windows chart.
- **Unexpected provider cost/retry:** capability gate, named model/region disclosure, one explicit request, no fallback/retry.
- **Reference licensing/security drift:** pinned source links; independent implementation, no code/assets copied; unresolved licences block reuse.
- **False performance confidence:** historical v0.1.0 samples labelled; paired installed measurements before release, no assumed percentage savings in process RAM.
