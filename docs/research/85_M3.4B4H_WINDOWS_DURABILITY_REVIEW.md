## 3. Requirements A–E are separate

- **A — Same-process automatic replay:** prevent it by synchronously consuming
  the original consent/prepared identity/capability before asynchronous dispatch.
- **B — Automatic replay after restart:** prevent it by not persisting usable
  authorization, pending request payloads or recovery jobs, and never reconstructing
  consent/capabilities from a ledger, settings, startup arguments or old approvals.
- **C — Diagnostic evidence:** minimal attempt metadata is useful for explaining
  a possible submission, UNKNOWN outcomes and independent process contention.
- **D — Evidence surviving OS/power failure:** desirable but physically unproven.
  Losing evidence must never become permission or proof of zero transmission.
- **E — A user deliberately reviews and authorizes another operation:** permitted;
  it is a new authorization even if the image/question happen to be identical.

Required security property: **at most one application transport invocation per
specific authorization**, not exactly-once provider delivery, account-wide
deduplication, permanent prohibition of similar questions or guaranteed billing.

## 6. Restart and the missing-record counterexample

Suppose a POST was possibly invoked and the process dies before receiving or
recording a response. On a fresh launch there is no old preview/crop/token/job,
registered prepared identity, lease or privileged capability. No startup reader
rehydrates them, and no automatic request reconstruction or resumption exists.

Even if `attempt.jsonl` is missing after storage loss, its reader returns an
observation, not authority. No caller uses NOT_STARTED to reconstruct an old
permission. Calling the existing fake bridge with a fabricated old wire/capability
fails runtime recognition regardless of disk state. A new valid operation needs
a new session, exact review, confirmation and separately issued capability.

Important test interpretation: the existing worker's `restart` mode deliberately
constructs a NEW synthetic session, review and fake capability to challenge the
old exclusive file. Its rejection demonstrates persistent namespace contention;
it is not a test that serializes/restores old consent. If the old file were deleted
and that worker were run again, its new synthetic approvals must not be mislabeled
an automatic replay of the old authorization. No such deletion/test was performed.

## 7. What persistence adds, and what it does not

The optional ledger supplies metadata evidence, independent-handle/process
exclusive admission to one operation directory and conservative UNKNOWN recovery.
It can prevent a second trusted test composition from claiming that same namespace,
even when that composition creates new in-memory objects. It does not create,
restore or cryptographically attest human consent or identify identical images.

For A/B under the traced no-resume architecture, power-loss-perfect metadata is
not an additional prerequisite. It would become necessary to reassess if future
code persisted pending work, reconstructed permissions, reused a privileged launch
scope on startup, retried UNKNOWN, or exposed a restartable automatic issuer.
Such changes are prohibited assumptions of this readiness decision.

## 9. Windows file API guarantees and limits

Node's `wx+` rejects an existing path; exclusive mode has network-filesystem
caveats. Completion of a write is separate from `FileHandle.sync()`, whose storage
effect depends on OS/device. `datasync()` is not the portable metadata-flush
substitute. These API contracts do not certify sudden-power-loss survival.
[Node v24.22.0 fs contracts](https://raw.githubusercontent.com/nodejs/node/v24.22.0/doc/api/fs.md).

Upstream **libuv 1.52.1** Windows source maps exclusive creation to CREATE_NEW,
mkdir/mkdtemp to CreateDirectoryW, and both fsync/fdatasync to FlushFileBuffers.
Its rename calls MoveFileExW with REPLACE_EXISTING, without WRITE_THROUGH. This is
the matching-version upstream implementation evidence, not a disassembly or
certification of this Electron binary/storage device.
[libuv Windows filesystem source](https://raw.githubusercontent.com/libuv/libuv/v1.52.1/src/win/fs.c).

Microsoft documents FlushFileBuffers as flushing buffered file information to the
device. It also discusses unbuffered/write-through I/O; flushing an entire volume
requires administrator privileges. No volume flush or such privilege is needed
or proposed for this pilot. [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

CREATE_NEW fails for an existing file. NTFS write-through has metadata implications,
but hardware support is qualified; those flags are not automatically established
by the ledger's `wx+` string or its location in TEMP. A TEMP directory is not itself
proof of FILE_ATTRIBUTE_TEMPORARY. [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

## 10. Directory entries, rename, caching and NTFS

Windows normally caches data and metadata. A readback may be served from cache;
it verifies current bytes, not future physical survival.
[Microsoft File Caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching).

MoveFileEx describes WRITE_THROUGH, including copy/delete flushing. That flag does
not prove this ledger performs an atomic durable replacement: it performs no
rename at all. Do not substitute rename atomicity for persistence.
[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

NTFS uses logging/checkpoints for filesystem consistency after failure. Filesystem
recovery is not an application-level transaction coupling consent and remote POST.
[Microsoft NTFS overview](https://learn.microsoft.com/en-us/windows-server/storage/file-server/ntfs-overview).

The ledger flushes its open file, not a separately opened parent-directory or
volume handle. No end-to-end proof covers newly created parent entries, kernel
crash, drive cache/firmware, rollback, hostile reparse races or remote filesystems.
This review does not assert directory entries necessarily disappear, or that
Windows file flush excludes all relevant metadata. Their complete physical
survival on this device simply has not been established.

## 12. Process termination versus OS failure versus power loss

- **Process termination:** earlier owned subprocess exits after commit and inside
  fake transport retained the record, blocked old-directory reuse and published
  no late result. These are actual process-lifetime tests, not a hardware failure.
- **Crash before commit:** no call is reachable before admission ACK; termination
  also destroys the volatile authorization. A new process does not resume it.
- **OS crash/restart:** no experiment performed. Metadata may be complete, torn,
  unavailable or absent; old volatile grants are not restored by this application.
- **Power loss:** no experiment or absolute device guarantee. Evidence could be
  lost while the provider might already have received a POST. Delivery/billing is
  then UNKNOWN, never zero and never a reason for automatic resend.

This assumes a normal fresh process lifetime, not hostile main-code replacement,
VM/process-memory snapshot rollback or external replay of a privileged launcher.
Those are not protections supplied by a private WeakMap or this TEMP ledger.

## 14. Minimum fail-closed policy — all requested cases

1. **Missing ledger:** no evidence of an old transmission; no restored authority.
   A new operation directory is usable only with genuinely new independent grants.
   Missing evidence for a known old attempt remains UNKNOWN; do not mark it unused.
2. **Incomplete record:** UNKNOWN/consumed; existing file blocks overwrite.
3. **Corrupt record:** same; no repair/reset to make an old approval usable.
4. **Unreadable record:** UNKNOWN, no old resume. Metadata availability is not a grant.
5. **Write failure:** if admission requires a record, deny before lookup/dispatch.
6. **Flush failure:** deny admission; keep the used bit/tombstone, no retry.
7. **Directory creation/validation failure:** fail that attempted admission;
   do not fall back to TEMP, installed data or a different unreviewed root.
8. **Disk full:** same before dispatch; after possible dispatch retain UNKNOWN
   if terminal persistence is unconfirmed. Do not report success without evidence.
9. **Access denied:** same, with no elevation or ACL modification.
10. **Read-only storage:** same, no alternate storage or automatic second attempt.
11. **Crash before commit:** no admitted call; old grants die, no replay.
12. **Crash after commit/before send:** may consume an attempt that never sent;
    availability loss is acceptable. Missing response is not permission to retry.
13. **Crash during fake send:** earlier process test yields UNKNOWN, no resumption.
14. **Windows restart:** start empty; never deserialize consent or pending work.
15. **UNKNOWN:** display uncertainty if available; never retry/fallback automatically.
16. **New legitimate session:** fresh exact review/confirmation AND independent
    privileged approval, new operation identity; no image-hash deduplication or
    permanent ban merely because an older independent operation was uncertain.

The optional ledger and its guards are not removed. If a future operation chooses
metadata admission as a precondition, storage failures must still fail closed.
Diagnostically reading an absent record never upgrades an old authorization.
