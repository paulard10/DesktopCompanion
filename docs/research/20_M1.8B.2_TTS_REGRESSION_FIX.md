# M1.8B.2 — TTS regression fix report

Status: **fixed in code. Stop before manual testing.** Quit the running app and restart before validating.

## 1. Verified root causes

These were two separate defects. Pablo was not missing.

**Voice lookup gave up too early.** Chromium often fires `voiceschanged` once with an empty list, then delivers Microsoft Pablo on a later event. The M1.8B.0 pilot keeps listening. Production resolved that first empty event (or the 2.5s timer) to “not found” and cached the failure. The exact message the user saw came from that cached miss:

`Microsoft Pablo (es-ES) is not installed. Speech stays disabled until that voice is available.`

**Chat send never became ready, and Stop speech was painted even when idle.**

- `refreshSend()` called `refreshTtsUi()`, and `refreshTtsUi()` called `refreshSend()`. The first `refreshSend()` during startup threw a stack overflow **before** `bridge.notifyReady()`. Main therefore left `pageReady` false and refused to publish history, so a sent message never appeared.
- `.tts-bar { display: flex }` overrides the `hidden` attribute, so **Stop speech** stayed on screen whenever the bar existed, including after a failed or idle playback.

Send itself was not supposed to depend on Pablo. The stuck startup and the always-visible Stop control made it look like one TTS lock.

## 2. Exact changes

| File | Change |

| Tests | `chromiumTts.test.mts`, `textToSpeech.test.mts`, `chatGate.test.mts` |

## 3. How Pablo is detected

Still Chromium `speechSynthesis` in the chat renderer (the pilot path). A voice matches only if:

- `localService` is not `false` (no cloud voice), and
- the name or `voiceURI` contains Pablo, or the URI/name contains the OneCore token `esES_Pablo` / `PabloM`, and
- `lang` is `es-ES`, or `lang` is empty and the name/URI still says Spanish (Spain) or that token.

Helena, Laura, and any other locale are not substitutes. The live `SpeechSynthesisVoice` is taken by `voiceURI`, then by the same Pablo test. Enumeration does not stop on the first empty list.

## 4. Why text chat was blocked

Startup called `refreshSend()` → `refreshTtsUi()` → `refreshSend()` until the renderer crashed, so `chat:ready` was never sent. Main will not publish the transcript until that signal (`publishHistory` requires `pageReady`). The composer could accept a send, but the reply never showed up.

The visible Stop speech button was the CSS `hidden` override, not an active playback. Failed lookup now forces `idle`, and the bar stays hidden unless `tts.state() === 'speaking'`.

## 6. Manual validation

1. Quit every Desktop Companion window (the current `npm run start` holds the single-instance lock).
2. `npm run build` then `npm run start`.
3. In the terminal, confirm a line like `desktop-companion: tts-voices count=… pablo=true` and `send-disabled=ready` after typing.
4. Open chat. The Pablo-missing banner must not appear if that log says `pablo=true`.
5. **Stop speech** must be hidden until you press Speak.
6. Type a Demo message and press Send. The message and reply must appear. Repeat in Qwen only if you choose to; this fix does not call the network by itself.
7. Press Speak on the reply. You should hear Microsoft Pablo. Stop speech hides again when audio ends or you press Stop.
8. If Pablo is truly absent, the error must say you can still send text, and Send must still work.
