# M1.9A — Safe desktop movement foundation

Status: **implemented. Stop for manual validation.** Smoke did not pass in this run because Desktop Companion is already running (`npm run start`).

The neon trail and optional wandering now exist. Wandering is off until the development tray enables it. See [M1.9C](26_M1.9C_AUTONOMOUS_WANDERING.md).

## 1. Architecture changes

Review findings, before the movement code:

- The avatar is a frameless transparent always-on-top `BrowserWindow`, 300×400 DIP. `currentPlacement()` pins it to the lower-right of the **primary** work area, 16 DIP in from the edges (`placeOverlay`).
- Display add, remove, and metrics-changed used to call `setBounds(currentPlacement())`. Any topology change teleported the robot back to that primary corner.
- Click-through stays in the main process. The window starts with `setIgnoreMouseEvents(true)`. A 16 ms cursor poll tests a 160 DIP body circle. The renderer cannot call `setIgnoreMouseEvents`.
- Chat is placed once from the robot anchor, and again only when a display event asks. It is not moved every frame.
- Sleep, wake, speaking, error, and reduced motion already own the pose. Travel must not replace those.
- Tray recovery capture is a checkbox, off by default, and is not written to disk.
- Nothing in the previous build moved the window after show, except that display snap back to the lower-right.

What changed:

- A pure controller in `src/shared/desktopMovement.ts` decides the next DIP rectangle. It does not import Electron.
- The overlay main process is the only caller of `setBounds` for travel. The renderer receives a boolean, `overlay:travel`, when motion starts or stops. It cannot set a window position.
- Startup still uses the lower-right home and then stays there. No timer runs until a development tray command.
- A display change now clamps the current rectangle into the matching work area, or the primary work area if the match is gone. It cancels travel. It does not snap home unless the window is already outside that area.
- Home for **Return home** is the lower-right of the work area that contains the window at the moment of the command.

## 3. Window movement algorithm

The controller tracks phase `idle`, `moving`, or `paused`, plus current point, target, home, and duration.

A tray nudge asks for 120 DIP in one direction. The target is clamped into the current display work area before motion starts. Return home uses the same path toward the remembered lower-right point.

Motion is smoothstep over time, `t² (3 - 2t)`.

- Speed is at most **160 DIP per second**.
- A hop lasts at least **280 ms**, so a short nudge does not pop.
- A long return may last longer than 4 seconds. The duration ceiling is not allowed to push speed above 160 DIP/s.
- A remaining distance under 1 DIP ends the move. There is no teleport on a normal command.
- The main process applies `setBounds` about every 32 ms, and only while a move or a pause is active. Identical rounded coordinates do not call `setBounds`.
- Width and height stay on the live window, so a resize during travel is kept.
- Stop, hide, destroy, a destroyed window, or a thrown tick clears the timer and the target.
- Pause keeps the target. The next unblocked tick starts a new smoothstep from the current point. Stop forgets the target, so it does not resume.

## 4. Display coordinate handling

All travel math uses Electron DIP rectangles. `scaleFactor` is checked and never multiplied, because `workArea` is already DIP. Physical pixels are not mixed in.

- Negative monitor origins are valid. Clamping uses `workArea.x` and `workArea.y` as the minimum, not zero.
- The taskbar is avoided by using `workArea`, not the full display `bounds`.
- The allowed area is the display that `screen.getDisplayMatching` returns for the window. A nudge cannot cross onto another monitor.
- A scale factor that is missing, non-finite, or not positive is an invalid area. Travel stops.
- If the target falls outside a shrinking work area, the next tick retargets inside it.
- If the matching display disappears, the window is clamped into the primary work area and travel stops.
- The position is not written to disk. The next launch uses the lower-right home again, so an off-screen point cannot stick.
- Tray Show, Hide, Wake, Sleep, Recovery, and Quit still work after a clamp.

## 5. Click-through safety

Travel does not change the hit-test policy.

- The window is still created with `setIgnoreMouseEvents(true)`.
- The same 16 ms poll and 160 DIP circle decide interactive versus passthrough.
- `setBounds` does not call `focus`, `show`, or a full-window mouse capture.
- Show remains `showInactive()`.
- A stationary cursor is retested against the new window origin. The body becomes clickable only when the circle covers that cursor. Transparent regions stay passthrough, including the frame after the circle has moved off the cursor.
- Recovery capture is unchanged and still off by default.

## 6. Chat interaction policy

Travel is deferred. The chat window is not dragged every frame, and travel does not focus it.

Block priority:

1. Microphone armed or Whisper in progress, or Pablo speaking → `voice`
2. Otherwise a generating chat turn → `busy`
3. Otherwise a visible chat window → `chat`

`captureBusy` covers push-to-talk even when Conversation Mode is off, and it stays set until transcription finishes or the capture is cancelled. Closing the chat, Stop movement, hide, and quit clear it.

A blocked move pauses in place and resumes from the current point when the block clears, unless Stop already cleared the target. An open chat therefore holds the robot until the chat is closed, and an active voice turn is not interrupted.

## 7. Robot animation behavior

While `overlay:travel` is true and the robot is awake, the existing pose gains a small forward tilt (`tiltX + 0.08`), a soft antenna wave, a slight extra hover, and a small arm relax. Arrival clears the flag and the pose eases back through the normal ambient motion.

The offset is skipped when:

- alertness is below 0.9 (sleep, and the return to sleep)
- `prefers-reduced-motion: reduce` matches
- presence is `SPEAKING`, `ERROR`, or `HAPPY`

No new geometry and no model request.

## 9. Manual Windows testing procedure

Quit the running Desktop Companion first, including the instance started with `npm run start`. Smoke and a second `start` cannot share the single-instance lock.

1. `npm run build`, then `npm run dev` (or `npm run start` with `DESKTOP_COMPANION_MOVE=1`). A normal `npm run start` does **not** show movement commands.
2. Confirm the robot appears at the lower-right and does not move by itself.
3. Open the tray. Use Move left, Move right, Move up, and Move down. Motion should ease about 120 DIP and stay above the taskbar.
4. Use Return home. The robot should ease back to the lower-right of the same work area.
5. Start a move and choose Stop movement. It should halt immediately and stay there.
6. While the robot is moving, click a desktop icon through the transparent corners, and click the body itself. The body stays interactive. Corners stay click-through. The move must not focus another app's typing away, and it must not focus the overlay.
7. Open chat and try a move. The robot should wait. Type in the composer. Closing the chat lets a paused move continue. Stop movement before close if you do not want that resume.
8. Start the microphone, or let Pablo speak, and try a move. Travel waits until that voice work finishes.
9. Wake and sleep during a move. The sleep pose should win over the travel lean. Reduced motion, if enabled in Windows, should also skip the lean.
10. Toggle Recovery: capture whole window, then turn it off. A corner click should pass through again.
11. If a second monitor is connected, confirm a nudge does not jump onto it.

## 10. Known limitations

- Movement commands exist only in development, or when `DESKTOP_COMPANION_MOVE=1`. There is no autonomous wander.
- Travel stays on the one display that currently contains the window.
- An open chat defers the whole move, including after the microphone and Pablo are idle, until the chat closes or Stop is used.
- A display change cancels an in-progress move and clamps. It does not continue the old target.
- Home is recomputed from the current display's work area when a command starts. It is the same lower-right rule as startup, not a user-saved point.
- Long trips keep the 160 DIP/s cap, so they can last longer than 4 seconds.
- The 32 ms timer also runs while a move is paused, so it can resume as soon as chat or voice clears. It stops when the phase returns to idle.
- The neon trail is not drawn.

## 11. Design proposal for M1.9B — Neon trail

Do not build this in M1.9A.

A trail that stays on the desktop cannot live only inside the 300×400 avatar. Particles parented to that window move with the robot. Stretching the avatar window across the path would create a large hit rectangle and fight the validated click-through.

Proposed later shape:

- A second frameless transparent window, owned by the main process, with `setIgnoreMouseEvents(true)` for its whole life. No focus, no keyboard, no tray entry that captures it.
- Its bounds are the DIP bounding box of the recent path, plus a small margin, clamped to the same work area. It never covers another monitor in the first version.
- The avatar window stays the only interactive surface. The trail window is always passthrough.
- The renderer for that window draws a capped set of small neon-green points in local DIP. The main process sends a short list of screen points only when a segment ends or on a coarse sample, not every animation frame.
- Points fade by age. Reduced motion, sleep, and Stop emit nothing and clear the layer.
- No screen capture, no global hooks, and no extra 3D engine. Reuse the existing transparent overlay approach.
- Autonomous wandering stays a later milestone. M1.9B only draws the trail behind movement that M1.9A already started.
