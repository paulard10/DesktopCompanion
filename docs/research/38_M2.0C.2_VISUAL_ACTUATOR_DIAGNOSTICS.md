## 2. Why each actuator was invisible

The nodes on screen are the nodes the gesture code writes. Nothing later in the frame clears them. The writes themselves do not read as motion at desktop size.

**Arms.** `leftArmLift` and `rightArmLift` are stored in `rotation.x`. The arm mesh hangs in local -Y. Three.js applies X before Z. A rotation about X moves that arm toward or away from the camera. The largest lift is 0.12 rad. On a hanging arm that changes screen height by a fraction of a percent and moves the hand about 7 DIP in depth. The visible raise is `rotation.z`, which the emotional channel never writes. Rest `rotation.z` stays +0.42 or -0.42.

**Antenna.** A distinct cue sets `ambientMix` to 0, which removes the idle antenna wave of ±0.12 rad. The replacement sway is at most ±0.06 rad on a stem of about 0.41. That is about 2 DIP at the tip. The antenna looks stiller during Curious, Listening, and Thinking than it does while idle.

**Head.** There is no head bone. `headTilt` sets `Face display` `rotation.x` and leaves Y and Z at 0. The largest nod is 0.1 rad. The eyes sit 0.46 in front of that pivot, so the pitch shifts them by about 4 DIP. Curious is -0.08 rad, smaller still.

**Happy.** The change that reads on screen is `wakeScale` × 1.05 on the whole pivot, from the presence pose. The bounce is 0.028 world, about 2 DIP, and the arm lift is the invisible X rotation above. Happy looking slightly bigger matches that scale. The diagnostic does not use scale.

Curious, Listening, Thinking, Responding, and Error still use those channels. This pass does not retune them and does not say they are now visible.

## 3. Evidence the diagnostics reach the real meshes

Development chat, after the existing preview, has a **Rig diagnostics** row:

- Test left arm
- Test right arm
- Test antenna
- Test head tilt
- Reset rig

These are not expressions. They reuse the existing dev eye-preview channel with `PROBE_LEFT`, `PROBE_RIGHT`, `PROBE_ANTENNA`, `PROBE_HEAD`, and `PROBE_RESET`. The director stores one probe clock. It does not call `wake()`. Sleep and the return to sleep clear it and log `probe cancel=sleep`. At 2000 ms it logs `probe done` and clears it. Reset clears it immediately. The same age always returns the same offset. The next frame writes rest plus that offset, not rest plus the previous frame.

`apply` writes the normal pose first, then replaces only the tested axis:

| Test | Visible node | Write | Hold |
| --- | --- | --- | --- |
| Left arm | `Left arm` | `rotation.z = 0.42 + 0.7` | 2 s, then rest |
| Right arm | `Right arm` | `rotation.z = -0.42 - 0.7` | 2 s, then rest |
| Antenna | `Antenna base` | `rotation.z = 0.12 + 0.55` | 2 s, then rest |
| Head tilt | `Face display` | `rotation` (0.35, 0, 0.4) | 2 s, then rest |

The world sample is the hand, the antenna tip, or the left eye, not the shoulder origin. In development the overlay forwards a `desktop-companion: probe` line to the `npm run dev` terminal once when a test starts and once when it returns. It includes the actuator, the node name, the rest value, the applied value, and the world position of that moving point, rounded to 2 decimals. It does not include chat text, credentials, or pointer coordinates. Body scale is not part of the probe.

The buttons are inside `import.meta.env.DEV`. Production `onEyePreview` returns before it can send a probe. The probe does not call `setBounds`.

## 4. Manual movement

The tray command still goes tray → `onMove` → `moveBy` or `moveHome` → `requestTravel` / `requestHome` → `stepTravel` → `BrowserWindow.setBounds`. There is no second controller. Sleep does not block travel. Chat, voice, and a running reply do.

The captured session in the dev terminal (pid 18768, later exited 0) showed `chat-open`, `hold=chat`, and then `quitting`. It never printed `travel request` or `travel bounds`. That log does not prove `setBounds` failed. It proves that session recorded no travel command before the process quit. The later Windows report says Move Up, Down, Left, and Right still do not move the window. This pass does not treat the unit tests as a substitute for that report.

Development now prints one line per tray command:

`desktop-companion: move received direction=up block=none`

`block` is `chat`, `voice`, `busy`, or `none`. The existing travel line then prints phase, the pause, and `from` / `to`. The first real `setBounds` in that command prints `travel bounds`.

**Test window move** is one extra tray item, and one button in the dev chat. It calls the same `moveBy('up', 48)`. It does not call `setBounds` itself. 48 DIP is the existing minimum hop, so the travel clamp leaves it at 48. Chat, voice, and a running reply still pause it. If chat is open, the button caption is exactly:

`Movement cannot run until the chat closes. block=chat`

The paused hop stays in the existing controller and continues when the block clears. The terminal prints `move-test received` and `move-test result` with the source (`tray` or `chat`) and the block.

## 8. Remaining uncertainties

The rig tests were not watched on the desktop. A log line with a changed `applied` value is evidence the mesh write ran. It is not evidence the motion is easy to see. If the arm, antenna, or face still looks still, that result stands.

The movement controller was not watched either. The last captured session never logged a travel command, and it ended while chat was open. Whether the next closed-chat test is blocked, clamped to the same point, or actually changes bounds is what the new lines are for. Do not read a passing unit test as that result.
