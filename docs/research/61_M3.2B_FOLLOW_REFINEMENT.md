## 2. Verified observation-to-actuator path

The existing main-process `sampleAndApply` reads desktop DIP cursor position every
**16 ms while visible**. When Follow is enabled, it observes the latest cursor,
checks immediate gates and calls the pure planner. The planner paces goal
decisions at **200 ms maximum frequency**. This is roughly 208 ms in the idealized
16-ms sampling grid; it is not a promise of exact Windows scheduling.

`finishFollowStep` starts the **existing 32-ms travel interval** only for moving
follow. `tickTravel` selects follow OR fixed-endpoint travel; `tickFollow` checks
fresh gates, runs the same planner and integrates fractional coordinates. Only
then are coordinates rounded for `applyWindowPosition`; `setBounds` is called
only when the rounded native position changes. The interval stops at rest/hold.

There is **one movement owner and one actuator**, no repeated `requestTravel`
call for changing follow goals, and no restart of manual smoothstep easing.
`lastTickAt` is retained while retargeting an active follow. Thus repeated manual
easing restarts are **not a verified cause** of this prototype's slowness.
Manual/Home/Wandering retain their existing fixed-goal controller and timing.

Relevant original controls, all traced in source:

- Meaningful cursor movement: **3 DIP**; direction smoothing **150 ms**.
- Initial/resume rest: **500 ms**; far entry **>220 DIP for 250 ms**, checked at
  goal-decision cadence. A nominal 250-ms dwell can take about 416 ms on that grid.
- Preferred trailing distance remains `max(170, exclusion + 24)`; compact full
  footprint gives **about 191.59 DIP**, with exclusion **about 167.59 DIP** and a
  **2-DIP rounding guard**. This avoids the cursor; it is not an enlarged hit proxy.
- Old retarget dead zone **24 DIP**, goal blending **55%**, arrival **8 DIP** and
  speed **<5 DIP/s**. WorkArea clamps the entire 216 × 224-DIP window.
- Old desired velocity: `min(160, 130, sqrt(2 × 320 × remainingDistance))`.
  Consequently **130**, not the named 160 cap, was the attainable cruise speed.
- Vector acceleration/braking **320 DIP/s²**; integration dt capped **64 ms**;
  cursor age/clock gaps **250 ms** fail closed. Fractional state survives rounding.
- Old idle deadline **1,200 ms since meaningful motion** discarded the target,
  regardless of whether catch-up was complete.
- Old six-second bout deadline discarded the target, followed by **five seconds
  rest**, then normal re-entry gates if motion continued.
- Immediate holds: invalid/stale/other-display/too-close cursor, display failures,
  hidden/asleep, chat/listening/speaking/generation, manual ownership, reduced
  motion, recovery capture, unsafe movement segment and finite session lease.
- Moving capture is passthrough. **300 ms after stopping** restores the original
  trusted body/arm/badge policy; it never controls movement speed.
- Follow does not wake the robot or extend the independent **60-second** sleep
  deadline. The separate **six-minute session lease** is not renewed by pursuit.

## 3. Separate diagnoses

### A. Excessive slowness

**Verified in source and synthetic replay:** the fixed 130-DIP/s desired cruise
limits long-distance catch-up. More decisively, the 1.2-second idle cutoff aborts
catch-up after an ordinary large cursor jump followed by a pause.

For 200, 500 and 1,000-DIP jumps at nominal t=1 s, M3.2a first issues a rounded
movement command at t=1.616 s, peaks at 130 DIP/s, clears the goal at t=2.384 s and
finishes braking at t=2.768 s. It moves only **about 104 DIP**. Remaining trailing
errors are **96, 396 and 896 DIP** respectively; none approaches its goal in the
16-second test. Increasing speed alone would not repair this lifecycle defect.

### B. Intermittent pursuit

Three independently reproduced mechanisms:

1. **Abandoned catch-up:** stationary-after-jump input ceases to renew the motion
   timestamp, so the old idle gate drops an unfinished destination.
2. **Intermediate arrival/re-entry:** at continuous 60 DIP/s, a frozen 24-DIP
   retarget dead zone plus discrete 5-Hz updates produces five temporary arrivals
   and six entry dwells in 12 seconds. The active follow repeatedly stops to
   re-enter even though the cursor is moving steadily.
3. **Compulsory mid-pursuit rest:** in the 90-DIP/s travel-then-idle replay, the
   six-second bout expires at t=6.960 s. Braking finishes at t=7.168 s while the
   pointer is still moving. The five-second rest then outlasts the input movement;
   the robot remains about **134 DIP** beyond its intended trailing offset.

These explain reproducible gaps in the controller. **There is no retained real
cursor trace proving which mechanism caused each earlier user-observed pause.**
Sleep, safety/exclusion, topology and chat holds also intentionally interrupt
following; they must not be removed to make a demo appear continuous.

## 5. Chosen refinement and old/new controls

The following changes are confined to `src/shared/cursorFollow.ts`:

1. **Finish an accepted safe destination after pointer idle.** Idle prevents
   starting another chase; it no longer discards an existing safe catch-up.
   Ordinary fresh-sample and safety gates still run on every observation/step.
2. **Retarget before an intermediate arrival.** Keep 24-DIP target hysteresis
   while far from the current goal. Within 24 DIP of that goal, admit changes
   above the existing 3-DIP meaningful-motion threshold. Preserve 55% blending,
   150-ms direction smoothing and bounded vector acceleration.
3. **Retain active-entry state through a transient intermediate arrival** if
   meaningful cursor motion occurred within the last 200 ms. It may wait for the
   next paced goal update without incurring another 250-ms entry dwell. A genuinely
   stopped cursor leads to actual arrival, zero velocity and normal input dwell.
4. **Move the bout rest to natural arrival.** Six seconds is now rest eligibility,
   not a deadline that drops a safe in-flight target. At natural idle arrival after
   a qualifying bout, schedule the same five-second quiet rest. Renewed deliberate
   far motion may interrupt that rest only after its first 500 ms, and must still
   pass ordinary entry dwell. Tiny motion/near-cursor jitter cannot cancel it.
5. **Use a distance-dependent desired speed**, with unchanged braking and
   acceleration: `130 + 170 × clamp((targetDistance - 80) / 400, 0, 1)` DIP/s,
   bounded by **300 DIP/s** and the existing stopping-distance rule. At <=80 DIP
   remaining the desired cruise is 130; at >=480 DIP it can reach 300. Near arrival
   the stopping-distance cap reduces it smoothly to zero.

| Control | M3.2a | M3.2b |
| --- | --- | --- |
| Near-target cruise | 130 DIP/s | 130 DIP/s |
| Effective maximum desired speed | 130 (named cap 160) | Adaptive, hard cap 300 DIP/s |
| Acceleration/braking | 320 DIP/s² | Unchanged |
| Adaptive distance range | None | 80–480 DIP remaining to target |
| Cursor/travel/decision cadence | 16 / 32 / 200 ms | Unchanged |
| Entry distance/dwell/resume | 220 DIP / 250 / 500 ms | Unchanged |
| Comfortable center spacing | About 191.59 DIP | Unchanged |
| Retarget dead zone | 24 DIP | 24; 3 when within 24 of existing goal |
| Goal blend/direction smoothing | 55% / 150 ms | Unchanged |
| Idle 1,200-ms rule | Drop accepted target | No new chase; finish accepted target |
| Bout/rest | Force stop after 6 s; rest 5 s | Rest eligible after 6 s, taken at natural arrival; renewed far motion may interrupt after 500 ms + entry dwell |
| Arrival/input dwell | 8 DIP, <5 DIP/s / 300 ms | Unchanged; transient intermediate arrival retains entry state |
| Safety dt/stale/lease | 64 / 250 / 360,000 ms | Unchanged |

**Deliberate behavioral tradeoff:** active follow can now continue beyond a
six-second bout instead of stopping mid-pursuit. The unchanged main/renderer
ownership, explicit Sleep/Hide/Stop, independent inactivity deadline and finite
session lease still bound it. No additional controller, movement scheduler,
renderer or setting was introduced. This changes the rest policy, not the
application architecture, and needs user approval of distraction and resource cost.

### Why 300 rather than an arbitrary larger cap

After reproducing baseline defects, compared candidate caps with the lifecycle
fixes and **the same 320-DIP/s² acceleration**. Times below are seconds from the
nominal jump until within 8 DIP of both planned goal and preferred trailing range:

| Candidate cap | 200-DIP jump | 500-DIP jump | 1,000-DIP jump |
| --- | ---: | ---: | ---: |
| 160 | 2.312 | 4.360 | 7.464 |
| 240 | 2.280 | 3.880 | 5.960 |
| **300 selected** | **2.248** | **3.688** | **5.384** |
| 360 | 2.248 | 3.528 | 4.968 |

300 materially improves long catch-up over the corrected 160 candidate, while
360 gains only another 0.416 s for a 20% higher cap. Acceleration is not increased.
Continuous 60-DIP/s following remains below/equal to 130-DIP/s desired cruise.
These are **simulated comparisons**, not measured Windows travel speed or UX.

## 9. Performance cost and unresolved limits

At implementation time, actual active-follow Windows CPU/RAM had not been
measured for M3.2b. **Prompt 81 below now records actual A/B/C measurements and
user-observed responsiveness.** The earlier 4.51% OFF / 6.60% ON and 216.64 /
218.70-MiB ending private commit belong only to M3.2a's session. No causal
reduction in CPU, memory, battery use or thermal load is claimed.

The algorithm retains constant-size state and the same bounded candidate search,
adds a few scalar/hypot operations and a distance speed ramp, and creates no
timer/service/renderer. This is bounded algorithmic work, not a measured CPU
budget. Less interruption means **more movement duty cycle**: G issues 345 versus
255 bounds changes and I 325 versus 104 in the same finite simulations. For an
isolated long catch-up, fewer commands than the corrected slow candidate do not
establish CPU savings. Native movement, compositor, IPC and trail costs need a
paired Windows measurement. Existing animation quality and sleep policy are intact.

Limitations requiring honest validation:

- A nominal initial entry delay still exists; the jump replay's first native
  movement is 616 ms after the nominal jump. The sampler/decision phase and OS
  scheduling add quantization. It was intentionally not reduced in this patch.
- Safe pursuit may still stop/hold when the cursor jumps onto the character,
  crosses its exclusion path, leaves the pinned workArea, or activates a priority
  blocker. These are not removed as "intermittency fixes".
- Input capture still uses trusted static body/arm/badge proxies, not painted
  pixels, and only returns after the stopped dwell. Polling has a sampling delay.
- Single-display only; cross-monitor travel, mixed DPI, elevated underlying
  applications and real first-click delivery are not certified by mocks.
- Newly faster motion may feel excessive or increase CPU/thermal/battery cost.
  The chosen cap is a candidate for user judgment, not a universal optimum.
- Actual dragging/typing/selection state in other applications is not known from
  cursor position alone. No hooks, window inspection or new permissions were added.
