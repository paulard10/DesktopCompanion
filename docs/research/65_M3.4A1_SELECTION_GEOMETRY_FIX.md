## 2. Confirmed root cause and exact measurements

The geometry-only native experiment uses the installed **Electron 44.9.3** binary
and the same initial window options. It never imports a capture controller,
calls desktopCapturer/capturePage, reads screen pixels, records input or opens
personal content. It queries only display geometry, its own renderer viewport
and its own HWND/client rectangle. Its profile is disposable, with permissions
and remote requests denied; terminal logs are aggregate geometry only.

**MEASURED on the user's current Windows setup:**

- One display; Electron selected display and primary IDs both **3940565744**.
- Display bounds in DIP: **x=0, y=0, width=1536, height=1024**.
- Display workArea in DIP: **x=0, y=0, width=1536, height=976**.
- scaleFactor **1**, renderer DPR **1**, native window DPI **96**, zoom **1**.
- dipToScreenRect reports physical full display **(0,0,1536,1024)**.

**Original configuration:** the constructor was given full-display bounds, but
actual outer bounds, content bounds, getSize()/getContentSize() and CSS viewport
were **1536 × 976 at (0,0)**. This equals workArea, not display.bounds.
The deltas against the requested rectangle are **x=0, y=0, width=0, height=−48
DIP**. getDisplayMatching still identifies the intended display.

The same deficit exists immediately after construction, at ready-to-show and
after showing/two renderer frames. A separate Windows query verifies both
**GetWindowRect** and **GetClientRect + ClientToScreen** as
**(0,0,1536,976) physical pixels**, DPI 96. No discrepancy is hidden between
Electron and the native HWND for this case.

**Confirmed cause:** initial placement of this non-fullscreen window is
constrained to the workArea on this runtime, while the invariant correctly
requires the full display. The 48-DIP height deficit is exactly the bottom
reserved desktop/taskbar area. The original implementation assumed constructor
bounds established that full selectable surface and did not explicitly place
the client area afterward. The security check catches that incorrect assumption.
This is a reproduced API/native placement effect; no claim is made that its
internal Windows/Chromium implementation has been traced to a specific upstream
source-code defect.

This failure is **not explained by fractional DPI** on this machine (scale 1),
an outer/content inset (both match), wrong display (matching ID), or a position
that merely needed more time (unchanged after show/frames). These conclusions
apply to this reproduction, not every Windows version/DPI configuration.

## 4. Official references and upstream issue relevance

Verified against local 44.9.3 declarations:

- [screen](https://www.electronjs.org/docs/latest/api/screen) and
  [Display](https://www.electronjs.org/docs/latest/api/structures/display): bounds
  and workArea are distinct DIP rectangles; scaleFactor is not a second DIP
  multiplier. The existing nearest-point choice and one-display gate remain.
- [BrowserWindow](https://www.electronjs.org/docs/latest/api/browser-window):
  setContentBounds positions/sizes the client area; getContentBounds reads it.
  ready-to-show denotes initial rendering, not proof requested geometry was used.
- [constructor options](https://www.electronjs.org/docs/latest/api/structures/base-window-options)
  and installed types provide the flags audited above.
- [Electron #51572](https://github.com/electron/electron/issues/51572) describes
  small frameless bounds differences above 100% DPI, reported on 42.0.1.
  It motivates strict native/viewport measurement, but does not explain this
  **48-DIP deficit at 100%**.
- [Electron #51679](https://github.com/electron/electron/issues/51679) concerns
  frameless + thickFrame + resizable windows and differing native/logical bounds,
  reported on 42.1.0. Our selector is nonresizable, changing thickFrame does not
  cure it, and native/client/logical rectangles agree here. It is not established
  as this failure's cause. No version upgrade or copied workaround is applied.

## 5. Minimal corrective strategy and retained invariant

**Explicit scope: OPTION A — entire selected display.bounds**, including its
reserved taskbar region. workArea remains relevant only for the later preview.
No fallback silently changes selection to workArea.

After creating/hardening the hidden window, call
**win.setContentBounds(s.display.bounds)** before loading the page. This is the
placement operation supported by the experiment, using trusted display data;
no resolution, DPI, taskbar thickness or user-supplied destination is hardcoded.

Retain exact native content/display comparison at first paint, rectangle
submission and before acquisition. If Windows refuses the explicit size,
capture remains blocked with the original error. **Tolerance remains zero DIP**;
no 20/50-pixel allowance, nearest-size substitution or unconditional true.

In addition, readiness now reports viewport width/height and DPR from the
**isolated preload's own global DOM view**; the public bridge still exposes the
same zero-argument ready() method. Main requires the exact numeric schema and
equality with frozen display width/height/scale before accepting selections.
It cannot use a renderer's dimensions to expand or reposition the trusted area.
No new channel, capture capability, arbitrary command or coordinate region is
granted. Mismatches dispose the session before capture.

Geometry-failure diagnostics are development-only through the existing enabled
feature gate. They record stage/reason, count, display/workArea/outer/content
sizes, finite viewport width/height/DPR and rectangle **deltas**. They do not
record selected regions, screenshot bytes, user input/history, titles or secrets.
There is no polling or persistent diagnostic file.

All prior privacy boundaries remain: no startup/open/drag capture, explicit
confirmation, one session/display, owned frame/session validation, size budgets,
actual image density/dimension checks, stale-result rejection, UI exclusion,
no disk/clipboard/export/network/AI/OCR, no microphone and no security/CSP changes.
The one-shot screenshot still happens only through the existing confirmed path.

## 6. Complete selection-to-crop mapping

For the full-display selector at zoom 1:

1. Renderer-local clientX/clientY are CSS coordinates inside the viewport. The
   preload confirms the viewport dimensions equal the DIP selection surface.
2. Normalize a reverse drag into a local DIP rectangle. Main validates it inside
   full display width/height; no part may exceed the surface.
3. Global desktop DIP = local DIP + display.bounds origin. This origin may be
   negative/nonzero. Converting back subtracts the **same display origin**.
4. Captured display-relative coordinates are therefore the original local DIP;
   do not add/subtract workArea origin, even with a top/side taskbar.
5. Actual validated full-image width/height divided by display DIP width/height
   give independent x/y pixel scales. Apply each once; floor left/top and ceil
   right/bottom inside image bounds. Then check crop dimensions and PNG budget.

Example covered by regression: display origin **(−1920,80)**, scale 1.25;
local selection **(20,40,100,60)** corresponds to desktop **(−1900,120,100,60)**
and physical crop **(25,50,125,75)**. Existing fractional-edge coverage remains.

The geometry fix changes no crop math. Actual captured source metadata is
**unmeasured in this task**, because no real capture was authorized/executed.
Native window correspondence and synthetic crop pixels are necessary checks,
not proof of real captured text or overlay exclusion.
