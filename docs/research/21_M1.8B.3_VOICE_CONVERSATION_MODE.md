# M1.8B.3 — Voice conversation mode

Status: **implemented. Stop for manual validation.** Smoke did not pass in this run because Desktop Companion is already running.

## 1. Architecture

Conversation Mode is a coordinator in front of the existing microphone capture, Whisper transcription, chat send, and Pablo playback. It does not record audio, call Whisper, or call Qwen itself.

```text
Mic button → SpeechCapture → editable draft → Send (explicit)
                                              → one provider turn
                                              → completed demo/assistant line
                                              → Pablo, once
                                              → idle
```

The robot sleep/wake reducer is unchanged. Recording and transcription only publish `ATTENTIVE` or `THINKING` while the robot is already awake. Playback still uses the existing `SPEAKING` pose. A sleeping robot is not woken by these poses.

## 3. State machine

`IDLE → RECORDING → TRANSCRIBING → DRAFT_READY → WAITING_FOR_AI → AI_RESPONDING → SPEAKING → IDLE`

Also `CANCELLING` and `ERROR`.

Illegal and ignored:

- A second microphone start while recording or transcribing
- Send while recording or while a turn is already active
- Microphone while Pablo is speaking
- A second speak claim for the same Send

Cancel, reset, close, hide, and quit release the token so a late callback cannot speak. Leaving Conversation Mode stops the microphone and any playback.

## 4. UI and settings

Default **off**. The control is the small **Conversation** checkbox in the chat footer.

When off, capture, drafts, Send, manual Speak/Stop, and the optional Auto-read checkbox behave as before.

When on, a single status line shows: Recording, Transcribing, Ready to send, Thinking, Speaking, Conversation ready, Memory insufficient, or Microphone denied.

The transcript is still editable. Nothing is sent until Send. After Pablo finishes, the microphone stays off.

## 5. Cost and privacy

- One explicit Send still starts at most one provider request.
- Demo stays offline.
- The 1,024 MiB Whisper guard is unchanged.
- Qwen remains `qwen3.7-plus`, `enable_thinking: false`, Singapore endpoint, existing key storage.
- No wake word, no background capture, no cloud transcription, no new TTS model.
- The coordinator does not log chat text, audio, or keys. The terminal only logs the overlay pose name.

Partial streaming chunks, hidden reasoning, and provider errors are not spoken. If Pablo is missing or playback fails, the reply text stays and the existing speech message is shown. Text chat continues.

## 7. Manual Windows validation

1. Quit every Desktop Companion window, then `npm run build` and `npm run start`.
2. With Conversation **off**, send a Demo message, use Speak/Stop, and record once. Confirm nothing is sent until Send, and Pablo does not start by itself.
3. Turn Conversation **on**. Press the microphone, speak, stop, edit the draft, then press Send. Confirm one Demo reply, Pablo reads that reply once, and the mic does not restart.
4. Press Stop speech during playback. Confirm the text remains and the status returns to Conversation ready.
5. Turn Conversation off during a recording. Confirm the mic stops.
6. Clear conversation and close the chat during recording and during playback.
7. If memory is low, confirm the memory message and that typed Send still works.
8. Confirm a sleeping robot stays asleep until the usual wake action, and that a corner click still passes through the overlay.

## 8. Known limitations

- Conversation Mode speaks the reply for every explicit Send, including typed messages, not only microphone drafts.
- The separate Auto-read checkbox is ignored while Conversation Mode is on, so a reply is not read twice.
- Listening and transcribing reuse Attentive and Thinking. They do not add a new robot model.
- Windows microphone permission and the 1,024 MiB guard are unchanged, so a short laptop can still refuse Whisper until memory is free.
