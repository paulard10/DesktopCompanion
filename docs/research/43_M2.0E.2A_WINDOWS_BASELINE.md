# M2.0E.2A — Guided Windows performance baseline

Status: **measurement only.** No feature code was changed. Avatar rendering, sleep, cursor polling, eyes, body motion, chat, Whisper, Pablo, Qwen, movement, wandering, and Neon Trail stay as validated.

Machine: Microsoft Windows 11 Home 10.0.26200, 12th Gen Intel Core i5-1235U, 12 logical processors, 7.83 GiB RAM, Intel Iris Xe Graphics. The companion was the already-running `npm run dev` instance. It was not restarted, and no second instance was launched.

## 1. Process identification

No `whisper-cli.exe` was running. No second-instance process was in the tree.

## 2. Metric definitions

CPU time is `Win32_Process.UserModeTime + KernelModeTime`, in 100-nanosecond ticks. CPU seconds are the delta divided by 10,000,000. **Percent of one logical processor** is CPU seconds divided by the measured wall seconds, times 100. **Percent of the machine** is that figure divided by 12. A process can exceed 100% of one logical processor if it uses more than one. The samples below do not.

| Metric | Source | What it is |
| --- | --- | --- |
| Working set | `Get-Process.WorkingSet64` | Physical pages for that process, including shareable pages. |
| Private bytes | `Get-Process.PrivateMemorySize64` | Private commit. This is not physical RAM and can exceed the working set. |
| Private working set | `\Proceso(*)\Espacio de trabajo - Privado` | Physical pages private to the process. The instance is parsed from the counter path, because `InstanceName` drops the `#n` suffix and would otherwise collapse every `electron.exe` into one slot. |
| Shareable resident | Counter working set minus private working set | Shareable pages resident in that process. Other processes may have the same pages too. |

A sum of working sets counts shared pages once per process. It is not exclusive application RAM. The private-working-set sum is the closer exclusive physical figure, and it was available for scenarios B, C, and D.

GPU utilization is `\GPU Engine(*)\Utilization Percentage`. The instance name contains `pid_<pid>_..._engtype_<type>`, so a reading can be tied to a process. The only companion process with GPU engines was the GPU process, pid 27976. These readings are engine time, not frames per second, and not a whole-chip percentage.

## 4. Sleeping versus awake

| Process | Sleep, % of one logical processor | Awake idle, % of one logical processor | Difference |
| --- | ---: | ---: | ---: |
| Main | 2.59 | 2.52 | −0.07 |
| Avatar renderer | 8.77 | 14.08 | +5.31 |
| Chat renderer | 0.00 | 0.00 | 0.00 |
| GPU process | 9.17 | 22.23 | +13.06 |
| Network utility | 0.00 | 0.03 | +0.03 |
| **Electron tree** | **20.53 (1.71% of the machine)** | **38.85 (3.24% of the machine)** | **+18.32** |

Sleeping CPU is real: the avatar renderer and the GPU process keep working while the hidden chat renderer stays at 0.00. On this 12-thread CPU the whole tree is 1.71% of the machine while asleep and 3.24% while awake and idle.

The avatar renderer is the renderer-side cost. It is the only renderer with CPU in both labeled states, and it rises from 8.77% to 14.08% of one logical processor when the robot wakes. The GPU process moves more than the renderer, from 9.17% to 22.23% of one logical processor. This baseline does not split that work into pose math, draw submission, and compositing. The pose loop is one candidate inside the avatar renderer, and these numbers do not show it to be the larger share.

The main process stays near 2.5% of one logical processor asleep and awake. That process hosts the 16 ms cursor poll, so the poll’s cost is inside that 2.5%, along with every other main-process duty. The poll does not explain the sleep-versus-awake gap. Isolating the poll alone would require a code change, which this pass did not make.

## 5. Chat

Opening an idle chat added the chat renderer’s 0.29% of one logical processor (0.024% of the machine) and no process. Its private bytes stayed near 32 MiB. The avatar renderer and GPU process were lower during the chat-open minute than during awake idle (11.09% and 12.24% of one logical processor, against 14.08% and 22.23%). That is a difference between two one-minute windows, not a sign that chat reduced avatar work.

Five open/close cycles left process count and private bytes unchanged for practical purposes (−0.46 MiB of commit on the tree, +0.05 MiB on the chat renderer). There is no growth here that calls for a longer leak investigation.

`desktop-companion: webgl ready` is not in the retained dev-terminal buffer. The dev server was left running, so the line was not regenerated. Calls, triangles, device pixel ratio, and the reported GPU string are **unavailable**. No stand-in figures are used.

## 7. Recommendation

**A. No optimization needed.**

Resource use on this Surface is low and stable:

- Asleep: 1.71% of the machine. Awake and idle: 3.24%. Chat open and idle: 2.16%.
- Private commit stays near 243–247 MiB across sleep, awake idle, chat idle, and five chat cycles.
- The exclusive-side physical figure, summed private working set, was about 62–63 MiB when the working set had not just been trimmed.
- The one clean GPU sample, during chat-open idle, is 1.6% on a single 3D engine of the GPU process, peaking at 5.5%.
- Chat does not add a process or a meaningful idle cost, and five hide/show cycles do not grow commit.

A sleep change would be aimed at the avatar renderer and the GPU process. Removing all of their sleeping CPU would be a ceiling of about 18% of one logical processor, which is 1.5% of this machine, and only while the character is asleep. Some drawing remains at the existing sleep cadence, so the real saving would be smaller. The regression risk reaches the validated sleep pose, eyes, body motion, and the cursor poll that click-through depends on. That trade is not justified by this baseline.

Sleep GPU utilization was not captured, and scenario B’s GPU average mixed fourteen 3D engines. Those gaps stay gaps. The measured CPU, the one attributed GPU sample, and the flat commit are enough to leave the implementation in place.

Expected benefit of changing it now: a small slice of one core while asleep. Regression risk: high, against behavior that is already validated.

No optimization is implemented. No profiling daemon, telemetry, microphone, Whisper job, Qwen request, credential, Windows setting, or process termination was used.
