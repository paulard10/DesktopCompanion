## 3. Why a separate read-only operation was necessary

The existing ordinary vault load can request re-encryption after a successful
decode. The normal provider-settings reader can rewrite legacy configuration
when stripping embedded secrets. These remain ordinary application behavior;
they were unsuitable for this explicitly non-mutating diagnostic.

The added diagnostic operation uses the **same trusted safeStorage cipher** but:

- Returns an availability enum, never a secret.
- Checks bounded regular non-symlink records; distinguishes observed ENOENT,
  read error, failed native decode and unavailable encryption.
- Performs at most one encrypted-file read and one native decode if an entry
  exists. There is no second read/decode, fallback or alternate profile.
- Applies the existing structural validator, without assuming a key prefix.
- Ignores a shouldReEncrypt request: no save, rewrite, migration or deletion.
- Releases its decoded reference and clears its own encrypted buffer afterward.
  JavaScript physical plaintext erasure is not guaranteed or claimed.

A bounded read-only provider check validates the existing Qwen/endpoint schema
without updating settings or returning the private endpoint. Legacy plaintext
credential fields cause a safe stop, not a sanitizing rewrite or second store.

Windows supervision adds an independent write barrier: read-only FileStream
handles with **FileShare.Read** hold the existing selected Local State, settings
and vault files throughout child lifetime. They deny writing, replacement and
deletion, including native attempts. The supervisor never reads credential bytes.
The child confirms that existing protected files cannot be opened for writing
before entering the secure operation. File presence, size and modification-time
checks after child exit confirmed preservation; no credential hash was computed.
The missing credential entry remained absent. Only owned TEMP data was removed.
