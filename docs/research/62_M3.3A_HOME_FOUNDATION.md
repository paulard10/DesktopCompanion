## 2. Visual design and exact geometry

Original HTML/CSS/SVG now depicts a floating circular platform in perspective:
an off-white rounded chassis with visible thickness, glossy black upper deck,
mint-green inset ring and a green strip on its front edge. It echoes the robot's
white body, black display and green details. SVG gradients/reflections give
projected depth; this is **not a WebGL/Three.js 3D object**. It uses no
external artwork, fonts, raster assets, shadows, filters, canvas or WebGL.
No large text appears. A main-acknowledged click produces a **360-ms** mint
highlight; reduced-motion uses 1 ms. There is no ambient/continuous animation.

- Native Home window: **112 × 88 DIP**, independent of the robot's 216 × 224 DIP.
- Nominal bottom/right inset: **16 DIP** inside the primary display's workArea.
- Painted silhouette: an ellipse centered at `(56, 48)`, radii `(51, 18)`,
  extruded downward **12 DIP**. Its visible bounds are x=5–107, y=30–78:
  **102 × 48 DIP**, inside the unchanged native window.
- The upper deck uses the same ellipse center/radii. Chassis path, deck and SVG
  viewBox are generated from shared `HOME` constants; no old shelter hit region
  survives above the platform.

`placeHome` computes `workArea.right - 112 - inset` and
`workArea.bottom - 88 - inset`, rounds/clamps to integer DIP inside workArea,
and reduces the inset only for very small valid areas. It rejects invalid,
nonfinite or too-small areas without resizing the station or blocking input.
No multiplication by `scaleFactor` is applied to Electron's DIP coordinates.

Examples, expressed as `(x, y, width, height)` in DIP:

- workArea `(0, 0, 1920, 1040)` → Home `(1792, 936, 112, 88)`.
- workArea `(-1920, 40, 1920, 1040)` → Home `(-128, 976, 112, 88)`.

Display added/removed/metrics-changed events re-read the primary workArea and
reposition only this station through its controller. Taskbar exclusion follows
workArea rather than display bounds; actual taskbar/DPI behavior needs user checks.

## 3. Window ownership, tray and lifecycle

`HomeController` owns at most one lazy BrowserWindow. It reuses the existing
overlay chrome/security helpers: transparent, frameless, nonfocusable,
nonresizable, no shadow/taskbar entry and always-on-top at `floating` level.
It starts hidden and ignores mouse events. Both renderer readiness and native
`ready-to-show` are required before `showInactive()`; Home never calls `focus()`.

The development tray adds **Show Home (Experimental)**. It is unchecked at
startup and has no preference-store access. No automatic call enables it.
Production rejects enable requests, and normal smoke explicitly disables Home.

- Checkbox ON + avatar visible: create one station and attach its listeners.
- Checkbox OFF: release input, destroy the station, remove IPC/display listeners
  and clear the bounded load watchdog.
- Global Hide: destroy Home while retaining its enabled intent only in memory.
  Global Show recreates it if that session intent is still enabled.
- Quit: destroy Home before awaiting chat shutdown and disposing the overlay.
- Preload/load/render/native-window failure: disable Home, destroy its window and
  refresh the tray. A later explicit checkbox enable can retry.
- A **10-second** load watchdog prevents a permanently hidden/loading station.
  It is cleared on successful presentation, off/hide, fault or disposal.

No Home interval, animation frame loop, background service or idle timer is added.
Repeated enable/disable cannot accumulate live windows/listeners. Existing avatar,
chat/trail lifecycle and user-selected movement settings retain their ownership.

## 4. Trusted hit-testing and click-through

The existing avatar cursor sampler remains the sole desktop-cursor reader.
After computing its effective mouse mode, it publishes a main-only observation:
global cursor DIP, monotonic timestamp and whether the avatar owns that pointer.
Home receives this only while enabled. It does not read the cursor independently
or accept renderer-provided geometry. Null samples release Home capture.

Home subtracts native window origin from the desktop cursor and tests the
extruded ellipse: clamp local y to `[48, 60]`, then test normalized elliptical
distance from `(56, clampedY)` with radii `(51, 18)`. Outside that silhouette it uses
`setIgnoreMouseEvents(true)`; inside it enables capture. Exit/re-entry is evaluated
on the next existing sample (nominal 16 ms); there is no invisible entry margin
or exit hold. Invalid, future or older-than-250-ms observations fail closed.

**Avatar capture has priority in overlap.** Home ignores the pointer when the
avatar's trusted controller currently captures it, including recovery capture.
At the initial parking positions part of the rear rim can overlap the approved
arm proxy; the exposed deck center/front remain the intended station test surface.
An overlapping robot may receive a click on the rear rim. This is a documented input
priority, not a promise that both surfaces can receive one click.

SVG antialiasing at the silhouette edge is an approximation, not per-pixel alpha
hit-testing. Native Windows delivery, fast first clicks, nonfocusable-window
behavior, elevated underlying apps and mixed-DPI transitions remain manual gates.
Main-thread stalls can delay native mouse-mode updates; no global hook or extra
watchdog polling attempts to hide that limitation. Tray OFF/Hide/Quit is recovery.

## 5. IPC and security

Home's isolated sandbox preload exposes only `notifyReady()`, `notifyClick()`
and `onFeedback(callback)` with unsubscribe. Channels are fixed:
`home:ready`, `home:click`, `home:feedback`. Readiness accepts only its fixed
marker; click accepts **no arguments**, coordinates, commands or capture regions.

Main validates the exact owned WebContents, its main frame with no parent, and
the exact page URL. Click also requires enabled/visible/painted/ready state,
fresh trusted geometry, unchanged sampled/native bounds and avatar priority.
Acknowledgments are separated by at least **180 ms**. The only result is `'pulse'`
to Home. No movement/sleep/provider callback exists in this controller.

The window retains `sandbox: true`, `contextIsolation: true`,
`nodeIntegration: false`, `webSecurity: true`, no subframe/worker Node integration
and no Home DevTools. Popups, webviews, keyboard input and navigation/redirects
to anything except its exact page are denied. No filesystem/OS bridge is exposed.

It uses the existing local development server or packaged `app://` protocol.
The Home page adds a restrictive meta CSP, including `connect-src 'none'`, on
top of the unchanged shared security policy. All resources are first-party/local.
This intentionally blocks Vite HMR WebSocket connectivity for Home; restart the
development app after editing Home. Existing avatar/chat development behavior
is unchanged. Existing session permission gates remain in place; Home is not a
trusted chat microphone URL and gains no microphone/capture/network capability.

## 9. Future M3.3b docking contract — design only

The current click sends only feedback. No `HOME_REQUESTED` movement action,
arrival detector, docking reducer or sleep-after-arrival logic is implemented.

Proposed trusted read-only station snapshot for a separately approved milestone:
`{ boundsDip, primaryDisplayId, workAreaDip, topologyRevision, visible, ready }`.
Main computes it from native geometry. Renderers must not choose desktop targets.
The current internal `getBounds()` is not itself a validated docking contract.

Candidate platform arrival anchor: body center
`(home.x + 56, home.y + 48 - 54 - 8)` = `(home.x + 56, home.y - 14)`:
54 DIP nominal body radius plus a proposed 8-DIP hover gap above the deck center.
With current compact viewport center `(108, 112)`, candidate avatar origin is
`(home.x - 52, home.y - 126)`. **This is provisional and not safe to use blindly.**
For the 1920 × 1040 example the raw origin is `(1740, 810)`, but a 216-DIP-wide
avatar must be at x ≤ 1704: clamping causes **36 DIP of horizontal mismatch**.
M3.3b must explicitly revise the station inset/anchor or select a verified safe
fallback before claiming visual docking; do not silently change today's placement.

**User-required layering:** when resting, the robot must be suspended above the
platform surface and appear **in front of the platform**, never behind it or
occluded by it. Vertical DIP placement alone does not guarantee this across two
native windows. Future docking must coordinate native stacking in main without
focus theft or competing window-order loops; do not rely on window creation
order. Arrival visual validation must include unobscured body/arms and the hover
gap, including overlapping poses and Hide/Show. This is a documented requirement,
not an implemented stacking or docking change.

Proposed policy, subject to future tests/user approval:

- An explicit trusted click becomes one epoch-tagged home request. A single
  established movement owner performs travel; no second setBounds loop.
- Accepting a request cancels Follow and Wandering for that request. Never
  silently restore either after arrival/cancel if the user disabled it.
- Manual Move/Stop, global Hide, explicit Sleep and topology changes cancel the
  docking request. Chat/voice activity uses existing movement holds; discard stale
  targets rather than moving from an old snapshot. Suggested request TTL: 15 s.
- Arrival needs measured native origin within a proposed 3-DIP tolerance for
  400 ms **and** a validated visual alignment/containment gate. Only then request
  the existing character Sleep transition; never sleep merely because time elapsed.
- A later explicit character interaction can request the existing Wake transition;
  cursor proximity must not auto-wake. No new persisted movement mode.
- Unavailable/hidden/invalid station: an explicit user request may use the current
  Return Home fallback or sleep in place under a separately specified policy;
  never invent a target. Display changes cancel and require a fresh snapshot.

Conceptual sequence only: FOLLOWING → HOME_REQUESTED → RETURNING_TO_HOME →
ARRIVED → DOCKED_ASLEEP → WAKING → NORMAL_COMPANION. Reuse the established
behavior/movement owners instead of adding a parallel full state machine.
Today's Return Home remains the existing parked-position command.
