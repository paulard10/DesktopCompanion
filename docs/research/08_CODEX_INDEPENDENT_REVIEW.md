# 08 — Codex independent architecture review

**Date:** 2026-10-22  
**Verdict: APPROVE WITH CHANGES**

The proposed **Electron + TypeScript + Vite + Three.js** shell is a reasonable first Windows implementation, subject to an overlay prototype and measured resource use. The proposed **VRM/VRoid humanoid pipeline is rejected for this character**. The supplied design is a small hovering spherical robot with a white shell, black display face, neon-green eyes and cheeks, a flexible antenna, and articulated arms. Its primary asset path should be **Blender → glTF 2.0/GLB → Three.js**, with a small custom rig and procedural animation. M1 should use a code-generated robot so the Windows overlay can be tested immediately. No AI, voice stack, local server, VRM loader, or third-party character asset belongs in M1.

This is an architecture review, not a claim that the overlay, installer, performance targets, or art fidelity have been demonstrated. The local repository contains the seven `docs/research/` files and no app source, package manifest, model, or image files. I examined public repository source through read-only GitHub access and cross-checked platform, format, licensing, and distribution claims against linked primary documentation. I did not run third-party code, install packages, or inspect the two reference images as pixels; the art observations below use the description supplied with this request. Exact proportions therefore require a later visual measurement pass against the original images.

## 1. Verified claims, corrections, and open evidence

**Verified platform facts**

- Electron supports frameless transparent windows, but [its transparent-window guide explicitly says transparent areas are not automatically click-through](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles). [`setIgnoreMouseEvents`](https://www.electronjs.org/docs/latest/api/browser-window#winsetignoremouseeventsignore-options) makes the *whole window* ignore mouse input; the `forward` option is limited on Windows when an elevated app is active. Claude correctly identified both facts.
- Electron [`screen.getCursorScreenPoint()` returns desktop coordinates in DIP](https://www.electronjs.org/docs/latest/api/screen), with display and scale-change events. This is a sound basis for desktop-wide **gaze** tracking independent of renderer mouse events. It is not proof that every elevated-window interaction works.
- The [VRM 1.0 humanoid specification requires hips, spine, head, two leg chains, and two arm chains](https://github.com/vrm-c/vrm-specification/blob/master/specification/VRMC_vrm-1.0/humanoid.md). A floating sphere with no legs would need fake anatomy to conform. In contrast, [glTF 2.0 supports node transforms, skins, morph targets, and animation clips](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html), and [Blender exports those features](https://docs.blender.org/manual/en/4.2/addons/import_export/scene_gltf2.html). Claude's VRM decision was contingent on a humanoid and is now invalid.
- The [Violet window source](https://github.com/Hamza-Bilal-2002/Violet---Persona/blob/main/client/electron/window.js) does use a full primary-work-area transparent Electron window, `setIgnoreMouseEvents(true, { forward: true })`, and proactive microphone grants. Its GitHub repository reports no detected licence while its README says MIT; absent a clear licence grant, do not copy its code or assets.
- [AVATAR has an MIT code licence](https://github.com/ARPAHLS/avatar/blob/main/LICENSE), but [its own asset inventory distinguishes shipped VRMs, VRMA files, and other media from code](https://github.com/ARPAHLS/avatar/blob/main/docs/assets-manifest.yml). The [pixiv VRMA pack terms](https://booth.pm/ja/items/5512385) permit certain commercial use with credit while prohibiting redistribution in an extractable/re-riggable form. “Commercial use forbidden” would be inaccurate; shipping its raw `.vrma` files in an extractable app package is the problem. Do not bundle them.
- [AILIS's `approvalRequired()` accepts `args.approved === true`](https://github.com/haowenGuo/AILIS/blob/main/electron/ailis-computer-tool.cjs#L1500-L1515) in addition to `context.approved`. Since the action arguments are model supplied, that is a real trust-boundary defect in this path, not merely a theoretical policy concern. Its [MIT licence](https://github.com/haowenGuo/AILIS/blob/main/LICENSE) does not clear its separate assets or dependencies. Its build explicitly [packages Stockfish](https://github.com/haowenGuo/AILIS/blob/main/electron-builder.runtime.cjs), whose GPL obligations require separate review if redistributed.
- [Warashi's `NOTICE`](https://github.com/inni918/warashi/blob/main/NOTICE) confirms the MIT server/fork additions, restricted compiled frontend, proprietary Live2D core, and separately licensed sample models. Reusing Warashi wholesale is a poor fit for a 3D Windows overlay.

**Corrections and unsupported claims in the seven files**

- `01` and `07` say AILIS publishes no Windows installer. The [v1.4.9 release assets](https://github.com/haowenGuo/AILIS/releases/tag/v1.4.9) include `AILIS-Setup-1.4.9-win-x64.exe` and a portable exe. This corrects the release-inventory claim, but it does **not** establish that the installer works reliably on a clean Windows machine.
- `02`'s 47/55 stack score is a subjective weighting, not evidence of Windows overlay reliability or resource use. “Identical rendering everywhere” is too strong: bundled Chromium reduces browser-engine variation, while GPU drivers, compositor behavior, DPI, and OS window rules still differ. Neither Violet nor AILIS proves selective hit testing is robust across the test matrix.
- `03`/`06` require a humanoid VRM, VRoid model, head/neck bones, VRMA clips, and visemes. Those requirements would distort this robot. Remove them from the product pipeline and M1.
- `03` estimates image-to-3D repair at 50–80% of manual work and `06` gives 3–5 days for M1. Neither figure has a reproducible basis. A single illustration cannot establish unseen rear geometry, rig pivots, or reflective material response. Treat image-to-3D as concept exploration only unless the output passes a side-by-side art and animation review.
- `04`'s prediction that a second ASR pass “roughly halves” wake false accepts and adds about 300 ms is unmeasured. Voice accuracy, latency, CPU cost, and model redistribution rights remain future benchmark and licence questions. The [openWakeWord project explicitly separates Apache-2.0 code from CC BY-NC-SA pre-trained models](https://github.com/dscripka/openWakeWord#license).
- `05` correctly calls for signing but overstates that signing removes SmartScreen friction. [Microsoft says even newly signed binaries may warn until reputation develops](https://learn.microsoft.com/windows/apps/package-and-deploy/smartscreen-reputation), and that EV certificates no longer provide an instant bypass. The precise [Artifact Signing eligibility and alternatives are documented by Microsoft](https://learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options); the publisher's legal identity and distribution channel are not known here, so do not turn one possible regional restriction into a product assumption.
- `05` recommends Electron `safeStorage` generally. The [current Electron documentation](https://www.electronjs.org/docs/latest/api/safe-storage) says its synchronous methods are deprecated and will be removed in Electron 46; use the asynchronous API when credentials are added. Windows DPAPI protects secrets against other Windows users, **not** other processes running as the same user.
- `06`'s rule to wait two weeks before installing a patch is unsuitable for security fixes. Choose a maintained major, pin exact versions, review release notes, and apply relevant security patches promptly. An M1 compile and packaged smoke test must still validate the chosen set.
- The [Adobe Mixamo FAQ](https://helpx.adobe.com/creative-cloud/faq/mixamo-faq.html) explicitly limits auto-rigging to bipedal humanoids and permits commercial use of characters/animations in projects. It does **not** by itself settle redistribution of raw FBX files. The raw-file prohibition in `01`/`03` relies on secondary discussion; avoid third-party motions and obtain primary terms before any later use.
- The [Hunyuan3D-2 licence](https://github.com/Tencent-Hunyuan/Hunyuan3D-2/blob/main/LICENSE) does explicitly exclude EU/UK/South Korea from its grant. That is a fact about that optional model, not a reason to assume this project's publisher or users are in any particular region. Hunyuan is unnecessary for the chosen manual art pipeline.

## 2. Architecture choice

**Recommended:** a new, small Electron app with TypeScript, Vite for the renderer, Three.js WebGL, and a plain functional state reducer. Keep an `AvatarAdapter` boundary between behavior and geometry: the same named channels (`bodyPose`, `gaze`, `eyes`, `cheeks`, `antenna`, `leftArm`, `rightArm`, `hover`, `screenPosition`) drive a procedural M1 robot and a later GLB. An `AnimationMixer` may play authored glTF clips later, but deterministic layers own state, facial display, and cursor gaze.

**Electron vs Tauri v2.** Electron offers a direct, documented whole-window input passthrough API, display/cursor APIs, and a predictable bundled Chromium. It costs a larger binary and process baseline and still needs Windows-specific overlay tests. Tauri uses Windows WebView2, supports transparent windows and per-user installers, and can make a smaller shell. [Tauri documents WebView2 as preinstalled on Windows 11](https://v2.tauri.app/reference/webview-versions/), but its renderer still bears the Three.js scene and GPU cost; a small installer is not proof of low runtime RAM or power. Rust/JS boundary work and a future Node speech/MCP sidecar would add complexity. Keep Three scene and state logic shell-neutral enough for a same-scene Tauri comparison if measurements warrant it. No Tauri toolchain is needed for M1.

**VRM vs GLB.** VRM is valuable if a later user-selectable *humanoid* avatar needs standardized expressions, look-at, retargeted body motions, and VRM permissions. It is a poor primary format for this legless robot. Generic GLB is an open delivery format with exactly the nodes, authored clips, skins, and morphs the robot needs. A lightweight custom hierarchy is likely sufficient: root/hover pivot; body yaw/tilt pivot; left/right arm pivots (optional elbow/wrist joints); antenna base, one or two bend joints, and glowing tip. Rigid parts can be parented to nodes rather than skinned. Use a short skinned antenna only if bending segmented nodes looks mechanical. No humanoid skeleton or VRMA dependency is required. [Khronos glTF](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html) and [Three.js `GLTFLoader`](https://threejs.org/docs/pages/GLTFLoader.html) support this arrangement.

**Why not fork:** Violet's unclear code licence and full-screen/Docker design, AVATAR's humanoid/asset assumptions, AILIS's breadth and approval defect, and Warashi's Live2D/Python/frontend restrictions all impose more removal and audit work than a focused overlay shell. Their architectural ideas may be reimplemented without taking assets or source. Their existence is useful feasibility evidence, not product validation.

## 3. Windows overlay design and risk gate

1. Create **one compact, frameless, transparent, shadowless** window on a selected monitor's `workArea`, initially hidden and input-ignored. Use `showInactive()` after the first transparent frame is ready so startup does not take focus or flash; explicitly test whether `focusable:false` still permits the intended click on Windows before adopting it. Keep the window close to the rendered silhouette; a work-area-sized transparent window creates an unnecessarily large input and composition surface. Use an ordinary always-on-top level first. Electron's `screen-saver` level can sit above the taskbar and may be intrusive, so escalate only if user tests require it. Do not promise visibility over UAC's secure desktop or exclusive-fullscreen games. [Electron window APIs](https://www.electronjs.org/docs/latest/api/browser-window).
2. Main polls `screen.getCursorScreenPoint()` while visible (candidate 30–60 Hz, then measure). Coordinates and window bounds are DIP. Renderer converts the cursor to canvas coordinates and runs a Three.js [raycast against a dedicated interaction mesh/layer](https://threejs.org/docs/pages/Raycaster.html), not against the transparent canvas rectangle. For the M1 placeholder, simple body/antenna/arm hit geometry is sufficient. The visual silhouette and the interactive silhouette must be tested at animation extremes.
3. The main process alone calls `setIgnoreMouseEvents`. It should change mode only when the cursor is in the window, a recent hit result corresponds to that cursor sample/window generation, and the proposed hit is inside a conservative area around the robot. Add entry/exit hysteresis, but avoid a large invisible clickable halo. When the cursor is outside or hit data is stale, default to passthrough. The preload exposes only `reportHit({sampleId, hit})`; no arbitrary IPC or window-method access. Renderer results are hints, not authority to create a full-window click target.
4. **Do not depend on `forward:true` for recovery.** Main polling continues even when Windows stops forwarded movement over an elevated app. Test pointer gaze separately from click capture while such an app is focused. Do not request elevation or UIAccess. [Microsoft explains UIPI's cross-integrity restrictions](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/settings-and-configuration). If interaction over an elevated app cannot be made reliable, leave the overlay passthrough and make the tray command the fallback; do not bypass the integrity boundary.
5. Input switching is inherently sampled and can miss a very fast first click, or intercept a click if the hit region lags behind a moving limb. Measure those cases. [Electron's `setShape(rects)` is experimental](https://www.electronjs.org/docs/latest/api/browser-window#winsetshaperects); its region also controls drawing, so it is a prototype fallback for coarse static regions, not an assumed pixel-perfect solution. A tiny always-clickable control would improve reliability at the cost of a visible input target and must be a deliberate UX choice.
6. Keep eye/display gaze independent of window position. Update bounds and projections on `display-added`, `display-removed`, and `display-metrics-changed`; clamp the window within the chosen work area. Test 100%, 125%, 150%, mixed-DPI dual displays, negative secondary-display coordinates, monitor disconnect/reconnect, and GPU context loss. Cap render DPR only after measuring sharpness on the neon eye details. [Electron's screen API](https://www.electronjs.org/docs/latest/api/screen) supplies the conversion and events.

Use the GPU path by default and test integrated GPUs, renderer context loss, sleep/resume, and remote desktop. A fallback should show a recoverable static robot or tray control if WebGL is unavailable; silently disabling hardware acceleration would defeat the performance assessment.

The overlay's acceptance gate is **actual user input behavior on Windows**, including a click through each empty corner into another app, reliable wake over the robot, no persistent focus theft, and predictable behavior when an elevated window is active. Source examples do not satisfy this gate.

## 4. Recreating and animating the robot

**Art pipeline.** Use the close-up to measure shell silhouette, black display coverage/curvature, eye shape and spacing, cheek placement, antenna thickness/tip size, and material highlights. Use the full-body image for body-to-arm ratio, arm pivots, hover gap, and how the antenna and arms read at the intended desktop size. Produce a front/side/back turnaround and a small orthographic proportion sheet; the unseen side/back is an art decision, not something image-to-3D can recover. Model clean, separable parts in Blender: rounded white shell, inset black face lens, emissive eye/display layer, cheek lights, antenna segments and glowing sphere, and articulated arms. Export a GLB with stable semantic node names and authored pivot origins. Check the exported model in the actual Three.js lighting/camera rather than relying on Blender's preview.

**Materials.** Start the white shell as a warm off-white PBR material with controlled roughness and subtle clearcoat; the black screen as a near-black glossy surface with a deliberate highlight. Three.js [standard materials support emissive maps](https://threejs.org/docs/pages/MeshStandardMaterial.html), while [physical materials add clearcoat at extra per-pixel cost](https://threejs.org/docs/pages/MeshPhysicalMaterial.html). Keep emissive green eyes, cheek details, and antenna tip legible at low size and on light/dark wallpaper. Emission alone does not create an outer halo; bloom is optional after performance testing. Use first-party or cleared environment lighting assets if reflections are needed. Avoid a fully transparent glass layer that dims the face or complicates hit testing.

**Face implementation choices:**

- **Separate emissive meshes:** simplest for M1, crisp eyes and cheek dots, easy deterministic scale/rotation/blink/gaze; geometry count and complex expression drawing become awkward. Recommended for the procedural placeholder.
- **Texture atlas:** low runtime work for a finite set of carefully illustrated expressions; blending/intermediate eye motion needs extra layers or crossfades, and atlas resolution must survive high DPI. Good if the final art direction settles on a small fixed expression vocabulary.
- **CanvasTexture:** draw vector-like eye shapes into a small reusable canvas, upload only when expression/gaze changes; supports continuous cursor gaze and many expressions without a clip per face. It needs profiling for texture upload cost and careful UVs on a curved display. A strong first choice for the polished digital face after art tests. [Three.js CanvasTexture](https://threejs.org/docs/pages/CanvasTexture.html).
- **Custom shader:** flexible continuous glow, masking, and distortion at potentially low draw-call cost, but higher implementation/debugging cost and shader-specific compatibility risk. Defer until the simpler face cannot meet the visual and performance targets.

For the final model, place an emissive face layer just ahead of or within the glossy display so highlights do not wash out the green forms; test z-fighting and side-angle readability. The cheek lights and antenna tip can remain separate emissive meshes even if the eyes use CanvasTexture. Decide atlas versus CanvasTexture after checking the original images and a rendered prototype, not from file-format preference alone.

**Motion channels, no LLM required:** sine or critically damped hover offset; small body yaw/roll that returns to a neutral rest; deterministic blink timing seeded for repeatable tests; gaze target from desktop cursor projected into the face plane and clamped; spring-damper antenna bend with bounded displacement; short arm pivot gestures. For sleep, dim/close eyes, lower hover amplitude, droop antenna, and relax arms. Wake reverses those over a timed easing curve. Each frame applies a fixed order: base asset pose or clip → state pose → gaze and procedural offsets → expression/brightness → render. Clamp delta time after resume so a paused app cannot launch a giant spring step. When authored glTF clips arrive, [Three.js `AnimationMixer`](https://threejs.org/docs/pages/AnimationMixer.html) can drive them beneath the same procedural channels. Reserve semantic nodes and channel ownership to prevent a clip and the procedural layer writing conflicting transforms.

An image-to-3D service may help explore volume but cannot be assumed to produce faithful eye geometry, clean separate parts, correct pivots, or redistributable outputs. A manual Blender model, made in-house or commissioned with explicit commercial/redistribution rights, is the reliable shipping path. The M1 procedural sphere is a **platform test asset**, not a claim of art fidelity.

## 5. Deterministic state machine

Use a pure reducer `reduce(state, event, now) -> state` driven by a monotonic clock, with an explicit transition-duration map. The initial state is `SLEEPING`. Cursor movement changes gaze but never resets the inactivity timer; clicks, a tray Wake command, or a later accepted wake phrase are intentional wake events. “Tracking” means **eyes/display gaze and a bounded body turn while the window remains anchored**.

```text
SLEEPING --WAKE--> WAKING --WAKE_DONE--> IDLE
IDLE --CURSOR_TARGET_VALID--> TRACKING --TARGET_LOST/SETTLED--> IDLE
IDLE or TRACKING --INACTIVITY_TIMEOUT--> RETURNING_TO_SLEEP
RETURNING_TO_SLEEP --SLEEP_DONE--> SLEEPING
RETURNING_TO_SLEEP --WAKE--> WAKING
WAKING --WAKE--> WAKING (idempotent)
any state --USER_SLEEP--> RETURNING_TO_SLEEP (or SLEEPING if already asleep)
```

`CURSOR_TARGET_VALID` is based on cursor availability/proximity and only operates while awake; `TARGET_LOST` uses a short dwell to avoid flapping. `WAKE_DONE`/`SLEEP_DONE` come from known animation durations, not an LLM response. A click during `WAKING` does not restart the animation. A wake event during `RETURNING_TO_SLEEP` reverses from the current blended pose. A user Sleep command wins over gaze events in the same tick. A clock-resume event clamps elapsed time and reevaluates the inactivity deadline. Add reducer tests for these transitions, event precedence, and no cursor-driven wake.

Later, `LISTENING`, `THINKING`, `SPEAKING`, and `ERROR` should be an **orthogonal activity state** under the awake branch, or a small hierarchical state machine, so every gaze/hover combination does not become a separate state. An AI agent may request only validated semantic intents such as `showExpression('curious', 0.6)` or `playGesture('wave')`; it cannot set arbitrary internal transitions or bypass sleep/permission policy.

Future optional **physical movement** is a distinct `MovementController`: home anchor in display DIP, bounded target near the cursor, spring velocity, work-area collision/clamping, and a `RETURN_HOME` action before sleeping. It should start only under an explicit interaction mode, avoid covering taskbar/other controls, and be tested across monitors/DPI. It is **not** M1 and is not what `TRACKING` means.

## 6. Security, licences, and later integrations

**M1 security boundary.** Renderer: local packaged content only; `nodeIntegration:false`, `contextIsolation:true`, `sandbox:true`, `webSecurity:true`, strict CSP, navigation and new-window denial. Main: validate sender frame and origin, message schema, freshness, bounds, and size for every IPC channel. Expose narrow functions through preload; never expose `ipcRenderer` or Electron APIs directly. [Electron's security checklist](https://www.electronjs.org/docs/latest/tutorial/security/) explicitly calls for sender validation and currently prefers a custom app protocol over broad `file://` access. A custom `app://` handler should resolve only known packaged paths and reject traversal; dev mode may use Vite localhost, but production must make no network requests. Deny all Chromium permissions in M1 using both permission request and check handlers; [Electron notes both handlers are needed](https://www.electronjs.org/docs/latest/api/session). Microphone, screen capture, and remote content do not exist in M1. For public distribution, add [ASAR integrity/fuses](https://www.electronjs.org/docs/latest/tutorial/asar-integrity), signing, and release verification without postponing the baseline isolation work.

**Computer use later.** Keep model output as untrusted proposals. A trusted broker should bind an approval to a canonical action name, exact normalized arguments, target application/path, short expiry, and a one-use nonce derived from a real user gesture in trusted UI. Deny if any field changes. Never accept `approved`, `permission`, or similar tool arguments from the model, and do not let screen text, web pages, or a remote MCP client grant authority. Avoid generic shell execution and elevation. Screen capture must be visible, opt-in, limited in scope, and kept out of memory/logs unless explicitly saved. Process isolation limits the damage of a renderer or speech parser compromise; it does not make a broad IPC API safe.

**Asset rights.** Code licences do not cover bundled models, textures, animations, face art, audio, or voice weights. Keep a manifest with creator, source, rights document/version, permitted redistribution and commercial use, attribution, and whether the asset ships or is fetched. For M1, all geometry/expression assets should be authored in code and the icon should be first-party. Do not copy Violet code; do not ship AVATAR's pixiv VRMA pack, Violet's FBX, Warashi's frontend/Live2D samples, or unreviewed model weights. GPL is not a blanket ban on commercial software, but it creates distribution/source obligations that should be assessed before inclusion; there is no need for GPL components in M1. Recheck each dependency's exact resolved licence before release.

When custom GLB import is added, treat the file as untrusted input: cap file/texture sizes and node counts, reject remote/external resource URIs and unsupported extensions, load only from user-selected paths, and recover from parser/GPU errors without giving the renderer filesystem authority. A model licence embedded in metadata is useful evidence but is not a substitute for the creator's redistribution grant.

**Optional future features.** Voice gets a separate consent and audio capture design; evaluate local KWS/ASR/TTS engines with *specific* model/voice licences and real-room false-accept, latency, memory, and power tests. External AI APIs need explicit opt-in and asynchronous OS-backed secret storage; local models remain optional downloads, not an installer prerequisite. Memory starts as a small, inspectable, deletable local store only when an AI feature needs it. MCP and Cursor integration should use documented, opt-in surfaces and a narrow adapter; do not ship an always-listening loopback server or edit global Cursor/agent configuration for M1. Any future local bridge needs authentication, origin defense, message limits, and no privileged “set state and execute” channel. These interfaces should depend on semantic character events, not on whether the renderer is procedural or GLB.

## 7. Consumer Windows distribution

An [NSIS per-user installer](https://www.electron.build/docs/nsis/) is practical without asking end users to install Node, Python, Docker, or admin-only services. M1 should build an **unsigned local test installer** and verify clean install, launch, tray Quit, uninstall, and whether user data is retained or explicitly deleted. Public release needs a publisher identity, code signing of installed executables and installer, reproducible release artifacts, third-party notices, and clean-machine tests. [Microsoft's distribution guidance](https://learn.microsoft.com/windows/apps/package-and-deploy/choose-distribution-path) distinguishes direct installer and Store paths. Signing raises trust but does not guarantee a first-download SmartScreen pass. The [Microsoft code-signing options page](https://learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options) provides the actual current regional eligibility and OV/Store alternatives; choose only once the publisher and channel are known.

Auto-update is a later product feature, not M1. When added, make update metadata/package signature validation and rollback behavior explicit; do not assume “GitHub Releases + updater” is secure by itself. [electron-builder's updater documentation](https://www.electron.build/docs/features/auto-update/) describes its signature checks and per-user NSIS behavior, which vary by major version. Preserve or explicitly delete `%APPDATA%` data on uninstall according to a tested user choice. Store API credentials only when AI is enabled, via the [asynchronous `safeStorage` API](https://www.electronjs.org/docs/latest/api/safe-storage), with a clear “forget key” action and no plaintext logs. An installer-size goal such as 120 MB is a target to measure, not an established result.

## 8. M1: exact scope, packages, plan, and acceptance

**M1 outcome:** an offline, code-generated white spherical robot with black face and simple green emissive eyes/cheeks/antenna, sleeping at launch, waking on click or tray command, blinking/hovering, and following the desktop cursor with its eyes and a restrained body turn. The window remains anchored. No polished Blender asset, voice, AI, physical travel, settings window, update client, or computer-use action is required.

**Exactly these project-local npm packages for M1 (proposed version locks, not installed or integration-tested here):**

- Runtime: `three@0.185.1`.
- Development/build: `electron@44.9.3`, `vite@8.3.4`, `typescript@7.0.2`, `@types/three@0.185.4`, `@types/node@24.19.2`, `electron-builder@26.15.3`.

The `three`/`@types/three` pair uses the same r185 line because [the registry's latest Three release is r186](https://www.npmjs.com/package/three?activeTab=versions) while [the latest published types inspected here are r185](https://www.npmjs.com/package/%40types/three?activeTab=versions). `GLTFLoader`, `Raycaster`, materials, and `AnimationMixer` are modules inside `three`, not separate npm packages. [Electron's npm release list](https://www.npmjs.com/package/electron?activeTab=versions), [Vite's Node requirement](https://v8.vite.dev/blog/announcing-vite8), and [electron-builder's NSIS docs](https://www.electron.build/docs/nsis/) support the proposed starting versions, but compiling and packaging them together remains an M1 gate. Node.js **24 LTS is a developer prerequisite only**, not a runtime delivered to consumers; [Node's release page](https://nodejs.org/en/blog/release) lists the current LTS line. Pin exact resolutions in a lockfile and review release/security notes at kickoff. No global install, Docker, Python, React/R3F, VRM package, state-machine library, `zod`, updater, speech package, MCP SDK, or `@electron/fuses` is required for this *local prototype*. Add fuses before public distribution. If packaging proves unnecessary to diagnose the overlay, `electron-builder` can be deferred, but the M1 release gate below assumes an installer smoke test.

**Implementation sequence (future work; nothing implemented by this review):**

1. Establish a minimal `src/main`, `src/preload`, `src/renderer` layout. Compile main/preload with local TypeScript, renderer with Vite, and provide one dev and one Windows package command. Package a first-party tray icon. Verify a clean x64 Windows launch before adding 3D.
2. Create the small hidden transparent window and tray commands `Wake`, `Sleep`, `Show/Hide`, `Quit`. Show after renderer readiness without focus or white flash; set bounded window placement from `screen.workArea`.
3. Build a procedural robot from Three primitives and first-party materials. It must be recognizable from the supplied description at final on-screen size. Add transparent renderer, explicit alpha clear, camera/framing, modest lights, and context-loss recovery. Avoid bloom and external textures.
4. Implement the pure state reducer and procedural channels. Add small reducer tests only for genuine transition risks: wake interruption, inactivity, state precedence, and clock resume. Verify eye blink and hover with reproducible event traces.
5. Add main-process cursor samples, display events, screen-to-canvas conversion, eye/body gaze limits, hit-proxy raycasting, and restricted hit IPC. Toggle whole-window passthrough on fresh hits; log mode changes for diagnosis without logging sensitive screen context.
6. Test on at least one integrated-GPU Windows 11 laptop and a mixed-DPI two-monitor setup. Fix click-through/focus/DPI bugs before considering polished art. Build and install the unsigned local NSIS package on a clean test profile, then uninstall it.
7. Record a reproducible measurement sheet with hardware/OS/GPU/scale, Electron and app versions, display arrangement, frame cap, cold/warm time, frame-time p50/p95, CPU per process and aggregate, private bytes plus working set (or PSS if available), GPU utilization, and idle power where measurable. Sample after warm-up for several minutes in sleeping, awake idle, tracking, hidden, and resumed states. Record baselines with the app closed. A future Tauri comparison must use the **same** scene, size, DPI, frame schedule, and machine. CPU ≤2% sleeping, ≤6% awake, GPU ≤10%, RAM ≤300 MB, and installer ≤120 MB from `06` are **provisional targets**, not pass/fail facts; percentages need a defined machine and denominator.

**Testable M1 acceptance criteria:**

- **Visual:** on white and dark wallpaper, only the robot is visible; no rectangle, shadow, white startup flash, or clipping during hover/antenna motion. The body reads as white, the face as glossy black, and the eyes/cheeks/tip as green at the intended size.
- **Overlay:** remains above ordinary maximized Notepad, Explorer, browser, and Cursor windows without sitting on top of UAC secure desktop; tray Show/Hide/Quit works and no process remains after repeated quit cycles.
- **Input:** clicks on every transparent corner reach an app underneath; clicks on body, visible arms, and antenna can wake it; rapid edge entry/click is measured; no invisible large hit rectangle or persistent focus theft. Document any missed-first-click rate and tune it before declaring success.
- **State:** starts asleep; only click/tray Wake starts `WAKING`; wake completes to `IDLE`; valid cursor target enters `TRACKING`; target loss returns to `IDLE`; intentional inactivity enters `RETURNING_TO_SLEEP` and then `SLEEPING`; cursor motion alone never wakes or postpones sleep. Interrupted sleep/wake is deterministic.
- **Gaze:** eyes move and body turns within explicit angular limits while the overlay stays put. Tracking follows a pointer on a second monitor and remains smooth after scale changes. Physical floating *toward* the cursor is absent from M1 by design.
- **DPI and integrity:** pointer-to-eye direction and hit regions remain correct at 100/125/150% and mixed scale. With an elevated app focused, cursor gaze continues without relying on forwarded events, transparent areas still pass input, and any interaction limitation is handled by tray rather than elevation.
- **Resource report:** measurements use the stated method, include the app process tree and baseline, and are published before declaring budgets met. Sleep/hidden modes visibly reduce work; hidden rendering stops. No hard resource number is claimed until this report exists.
- **Security/package:** packaged renderer has sandbox/isolation, restrictive CSP, no arbitrary IPC or navigation, no production network access, and no microphone/screen permission. Per-user install/uninstall and data retention choice are verified. An unsigned local installer is acceptable only for M1 testing, not a nontechnical public release.

## 9. Decisions that still depend on the original art and later measurements

The design description is sufficient to **reject humanoid rigging and choose GLB** now. The actual close-up and full-body image pixels are needed to fix shell/display curvature, eye expression vocabulary, exact proportions, side/back design, arm joints, antenna mechanics, green luminance, reflection style, and final camera/lighting. Choose atlas versus CanvasTexture from rendered expression tests. Decide target polygon/texture budgets and whether a segmented antenna is visually adequate after the model is animated. Set hard CPU/RAM/installer targets after the M1 Windows measurements and target-hardware decision. Choose signing method only after publisher identity and distribution channel are known. None of those decisions should delay the code-generated overlay test.

## Five most important findings

1. **Keep Electron/TypeScript/Vite/Three.js provisionally; prove selective click-through and focus behavior on Windows.** Transparency alone does not solve input, and elevated apps break forwarded mouse movement.
2. **Replace VRM/VRoid/VRMA with Blender → GLB and a custom lightweight robot rig.** The character has no humanoid legs or head/neck skeleton.
3. **Use a procedural robot for M1.** It tests the highest platform risk before art production; eyes, hover, blink, and cursor gaze are deterministic.
4. **Treat reference-app licences and assets separately.** Violet has no clear code grant; AVATAR motions and Warashi media have separate terms; AILIS has a model-self-approval defect. AILIS does publish a Windows installer, correcting the research.
5. **Treat resource, installer-size, voice, and image-to-3D claims as unmeasured until tested.** A signed installer also may show SmartScreen warnings initially.

**Final recommended architecture:** Electron main process for window, cursor, tray, and later trusted permissions; sandboxed TypeScript/Three.js renderer; code-generated robot for M1; later Blender-authored GLB with semantic custom rig and a digital-face expression layer; deterministic state and motion controllers; optional, isolated AI/voice/integration modules only after the visual overlay passes Windows tests.
