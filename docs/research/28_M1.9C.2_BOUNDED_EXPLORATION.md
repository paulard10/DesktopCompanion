# M1.9C.2 — Bounded exploration

Status: **implemented for development only.** Execution and expiry fixes are in [M1.9C.3](29_M1.9C.3_WANDER_EXECUTION.md). Wandering stays off until Enable Wandering. This build does not wake a sleeping robot.

## 1. Confirmed timing conflict

Idle sleep and wandering are different clocks, and they never met.

`INACTIVITY_MS` in `src/shared/behavior.ts` is 60 seconds. Tray Wake, a body click, and chat activity start that deadline. Cursor samples do not move it. When the deadline passes, the behavior reducer enters `RETURNING_TO_SLEEP` on its own.

A wander rest in `src/shared/wander.ts` is 2–5 minutes, plus a 45-second quiet gate. The planner only moves when the snapshot says the robot is `IDLE` or `TRACKING`. Sleep and the return to sleep clear the schedule and do not call wake.

So a robot left awake went to sleep at about 60 seconds. The first wander opportunity, at least two minutes later, found it asleep and did nothing. No code was changed until that order was confirmed in those two modules.

## 2. Implementation

One exploration session lasts at most 6 minutes (`WANDER_EXPLORE_MS` and `EXPLORE_HOLD_MS`, both 360,000). The session is an absolute timestamp, `exploreUntil`. Nothing inside the session writes that timestamp again.

The session opens in two cases:

- Enable Wandering while the robot is already awake, visible, and not asleep.
- The phase becomes `WAKING` while wandering is already enabled, and no session is open. Tray Wake, a body click, and opening chat are the events that enter `WAKING`.

Enable while asleep does not open a session and does not schedule a hop. A second Enable, or a second wake, during an open session keeps the same `exploreUntil`. Presence and speech do not call this path.

The main process sends one duration to the avatar, `overlay:explore`. The preload accepts `null` or a finite number from 0 through 360,000 and drops anything else. The avatar stores `exploreUntil` on the behavior state. A later message is ignored while that time is still ahead. `null` clears it. A message that arrives while the robot is sleeping or already returning to sleep is ignored.

The planner still returns at most one command. The main process still has one `setTimeout`. A hop still goes through `moveBy` or `moveHome`. Click-through, work-area clamping, speed, and the neon trail are unchanged.

## 3. Sleep deferral

Wandering off sends no explore message. The 60-second deadline is unchanged, and the reducer sleeps on that deadline exactly as before.

While `now < exploreUntil`, the idle-sleep branch in `settle` and `clockResume` does not run. The original `sleepDeadline` stays where Wake put it. The hold does not add time to that deadline, and it does not add time to itself.

When the hold ends, the next behavior step uses the normal rule. If the 60-second deadline has already passed, that step enters `RETURNING_TO_SLEEP` immediately. The same thing happens when the main process sends `null`.

Tray Sleep sends `USER_SLEEP` and clears the session first. `USER_SLEEP` always enters `RETURNING_TO_SLEEP` and clears `exploreUntil`, whether or not the 60 seconds have passed.

## 4. Lease behavior

The first hop still waits 2–5 minutes, and the robot must also have been quiet for 45 seconds. Enabling does not move.

A hop, arrival, body hover, body click, or quiet reset does not change `exploreUntil`. Hovering the robot still delays the departure, because that was the existing quiet gate. It does not keep the robot awake past the session.

Cursor movement away from the robot is not an input to the lease. The planner never watches the pointer except for the existing on-body tracking flag.

At `exploreUntil` the planner returns no command and no future check. An owned hop that is still moving is stopped. A manual move is not owned, so Stop, Return Home, and a direction command keep their current priority. After that, the scheduler has nothing to fire until a user wake opens a new session.

A skipped chance, including one blocked by chat, the microphone, Whisper, Qwen, or Pablo, is dropped. It is not queued. Those blocks do not extend the session. If the session ends while a wander hop is paused, that hop is stopped rather than resumed.

With a 2-minute minimum rest, one session can contain one hop, or two if the first rest was short enough that the second still falls before 6 minutes. The third departure is still Home, and that rule is tested when the departure time is inside the session. On the minimum cadence the third departure lands on the 6-minute boundary, so Home does not occur inside a single session.

## 5. Timer cleanup

There is one wander timeout. Replacing it clears the previous one and bumps a generation counter. A callback whose generation no longer matches returns without planning. Shutdown sets the closed flag, clears the timer, sends explore `null`, and only then destroys the overlay. `settleQueued` is still declared before `destroy`.

Disable Wandering clears the session, clears the timer, stops an owned hop, and sends explore `null`. A later callback cannot depart.

Tray Sleep does the same clear while leaving wandering enabled, then sends sleep. The next wake may open one new session. The scheduler itself never sends wake.

Hide, show, and a display change replan inside the current session. They do not move `exploreUntil`. A display change still stops an owned hop and reclamps to the new work area.

## 7. Manual Windows validation

Quit the current `npm run dev` first. The process that is running now does not contain this change. Start `npm run dev` again, then:

1. Leave Wandering off. Wake the robot and wait. It should sleep in about 60 seconds and should not move on its own.
2. Wake it and choose Enable Wandering. It should stay still. The first hop should come only after the 2–5 minute rest.
3. With Neon Trail on, that hop should leave the same green pearls as a manual move.
4. After 6 minutes from Enable, there should be no further hop, and the robot should return to sleep on its own.
5. Wake it again with Wandering still enabled. A new wait should start. It should not move immediately, and it should sleep again after that new session.
6. During a session, choose Sleep. The robot should sleep immediately and stay asleep.
7. Wake, Enable, then Disable Wandering. No hop should follow, and the 60-second sleep should be back.
8. Move in each direction, Stop, and Return Home should still work, including while a wander was waiting.
9. Open chat during a move. Travel should pause and resume after chat closes.
10. After quitting every instance, `npm run smoke` should reach a first frame. A line that says `second-instance-exit` is not a pass.

## 8. Remaining limitations

Wandering is still a development tray item. `npm run start` does not show it.

One session is not long enough for the every-third-journey Home on the 2-minute minimum cadence. Home still runs when a third eligible departure falls inside a session.

Typing in the chat composer, and opening chat, still call the existing wake. That refreshes the 60-second idle deadline, as it did before this change. It does not extend the 6-minute session. If that wake happens near the end of a session, sleep after the session can wait out the refreshed deadline.

A hop that was started by the user is not cancelled when the session ends. An owned wander hop is.

No keyboard hook and no application monitor were added. Typing in another program is still invisible, so an open chat remains the block for that case.

Qwen, Whisper, Pablo, trail drawing, and movement animation were not changed.
