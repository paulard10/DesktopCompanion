# M1.8A.3 MEMORY OPTIMIZATION REPORT

**Date:** 2026-10-23  
**Scope:** Read-only diagnosis and research. No application code, dependencies, models, microphone data, Windows settings, or credentials were changed.

## Recommendation

Keep multilingual Whisper Tiny and the current 1 GiB preflight guard for now. The immediate blocker is reproducible as a *guard decision*: with common applications open, available physical memory can fall below 1 GiB before Whisper starts. The user has demonstrated that transcription works when memory becomes available. Whether Whisper would safely finish under the busy workload is **unconfirmed**; the rejected run never launched it. The smallest safe improvement is to measure the actual launch headroom, system commit headroom, paging and responsiveness under the user's normal workload, then calibrate the guard from those results. A quantized Tiny model is the first isolated candidate if the measured memory cost still prevents use; do not replace the working model based on download size alone.

## 1. Guard audit and evidence

- [`src/main/localSpeech.ts`](../../src/main/localSpeech.ts) validates the WAV and then rejects when `os.freemem() < (minimumAvailableBytes ?? 1024 * 1048576)`. The production call in [`src/main/chatWindow.ts`](../../src/main/chatWindow.ts) supplies no override, so the exact threshold is **1,073,741,824 bytes = 1,024 MiB**. `minimumAvailableBytes` exists for tests. The error is raised **before** SHA verification, temporary WAV creation, or child-process launch.
- On Windows, Node/libuv's `os.freemem()` comes from `GlobalMemoryStatusEx().ullAvailPhys` ([libuv implementation](https://github.com/libuv/libuv/blob/v1.x/src/win/util.c)). Microsoft defines this as immediately reusable physical memory, including standby, free and zero pages ([MEMORYSTATUSEX](https://learn.microsoft.com/windows/win32/api/sysinfoapi/ns-sysinfoapi-memorystatusex)). It is neither process private bytes nor the amount of wholly unused RAM. It is a volatile point-in-time value, not a guarantee that a future allocation will succeed.
- The guard does **not** add 680 MiB to 1 GiB, subtract Whisper memory from `os.freemem()`, or reserve memory. It compares a single system number with a fixed threshold. Thus there is no arithmetic double counting in this code. The 1 GiB threshold is provisional and may be conservative for some workloads, but the current evidence cannot establish a lower safe value.
- The [original pilot](13_LOCAL_ASR_PILOT.md) measured a **679.5–680.1 MiB sampled peak private allocation**, a **191.9–192.2 MiB peak working set**, and process durations of **1.493, 3.618 and 5.306 seconds** for a 4.517-second synthetic sample. The [natural follow-up](14_NATURAL_SPANISH_ASR_VALIDATION.md) records the user's later report of six tests at roughly **1.4–1.6 seconds**, **~680 MiB private**, and **one error in 39 words**; the six raw records were not supplied for independent audit. Working set is resident physical pages; private bytes are closer to process commit. They cannot be summed, nor can 680 MiB private be directly subtracted from available physical memory. The existing PowerShell monitor samples about every 100 ms and may miss a brief private peak.
- Read-only snapshots on this laptop (8,017 MiB total) returned **551 MiB available** earlier in this audit and **765 MiB at 2026-10-23 18:07 UTC**. Both are below the guard. These were *not* captured at the user's failed click, and the exact applications and commit headroom at those moments were not recorded. The user's Chrome/ChatGPT failure followed by success after closing them is consistent with the guard, but no measurement proves which process consumed the headroom or whether the blocked inference would actually have caused paging.
- The [integration report](15_PUSH_TO_TALK_INTEGRATION.md) describes a short-lived, single CPU-only `whisper-cli.exe` using `-l es -t 2 -ng -nt`, a 30-second timeout and cleanup in `finally`. The model is not held in Electron between utterances. The renderer has at most 20 seconds of 16 kHz mono float samples (~1.22 MiB before overhead), and a PCM WAV of at most ~0.61 MiB; IPC/copy overhead and the rest of Electron were not measured here. The model file is 77,691,713 bytes (~74.1 MiB) on disk. Asset SHA verification streams it and warms the OS cache after the memory check; it does not deliberately retain a 74 MiB model buffer in the main process.

**Resource budget interpretation:** ~680 MiB sampled helper private bytes is the only credible measured per-run *commit-style* requirement; ~192 MiB was the sampled resident peak. Neither includes a measured worst-case 20-second utterance, other Electron processes, Windows commit pressure, paging, or a safety margin. A 1 GiB available-physical guard leaves a nominal 344 MiB gap above the private-byte figure, but this subtraction mixes different metrics and must **not** be treated as verified spare RAM. Measure both `ullAvailPhys` and system commit headroom (`GetPerformanceInfo.CommitLimit - CommitTotal`, per [Microsoft's memory guidance](https://learn.microsoft.com/en-us/windows/win32/memory/memory-performance-information)) before selecting a new guard.

## 2. Memory reduction candidates

### Quantized multilingual Tiny

The [whisper.cpp maintainer's model catalog](https://huggingface.co/ggerganov/whisper.cpp) lists multilingual `tiny-q8_0` at **42 MiB** and `tiny-q5_1` at **31 MiB** on disk versus **75 MiB** for ordinary Tiny. Those names intentionally omit `.en`; English-only models are unsuitable. The approximate disk savings are **33 MiB (44%)** and **44 MiB (59%)**. The catalog's disk figures do **not** predict private bytes, working set, paging or latency; decoder and scratch allocations may dominate. The exact 1.9.2 binary, Spanish quality and memory for these weights have not been tested. Start a separate, justified Q8_0 pilot only after baseline memory measurement; evaluate Q5_1 only if Q8_0 is inadequate. Compare on the same six consented Spanish clips and workload. Whisper code is [MIT](https://github.com/ggml-org/whisper.cpp/blob/v1.9.2/LICENSE), original Whisper code/weights are [MIT](https://github.com/openai/whisper/blob/main/LICENSE), and the maintainer's model repository declares MIT; retain notices and pin exact weight provenance and hashes before redistribution.

### whisper.cpp flags

The local **v1.9.2** `whisper-cli.exe -h` confirms `--audio-ctx`, `--max-context`, `--best-of`, `--beam-size`, `--no-fallback`, `--threads`, `--processors`, `--language` and `--no-gpu` options. The current two-thread, one-process, Spanish, CPU-only path is already conservative. Reducing audio context, text context or search breadth might alter allocations or latency, but has no demonstrated memory saving on this hardware and can damage recognition. `--no-fallback` can avoid extra decoding passes but may worsen difficult speech; it is not a credible primary memory fix. Avoid changing these flags in the app until one-at-a-time isolated measurements prove both benefit and acceptable Spanish accuracy. `-ng` already avoids GPU use on the integrated Iris Xe.

### Small Spanish ASR alternatives

- **Vosk small Spanish 0.42:** [official model list](https://alphacephei.com/vosk/models.html) gives **39 MB disk**, **Apache-2.0 model licence**, and generic **~300 MB runtime memory for small models**. That 300 MB is vendor guidance, **not** a measurement on this laptop or directly comparable to Whisper's private bytes. The published Spanish WERs are on different datasets and must not be compared with the user's six-clip result. Vosk is offline and [supports Windows x64 and Node bindings](https://alphacephei.com/vosk/install); its engine [source licence](https://github.com/alphacep/vosk-api/blob/master/COPYING) is Apache-2.0. The Node binding uses `node-ffi-napi`, which adds native/Electron packaging and ABI validation work. It is the most plausible *non-Whisper* lower-memory candidate, with accuracy still unknown for this voice/use case.
- **sherpa-onnx:** the [official Node package instructions](https://k2-fsa.github.io/sherpa/onnx/javascript-api/install.html) support Windows x64, with native DLLs and no global compiler requirement; the engine is [Apache-2.0](https://github.com/k2-fsa/sherpa-onnx/blob/master/LICENSE) and supports offline inference. Its [multilingual Whisper Tiny ONNX export](https://k2-fsa.github.io/sherpa/onnx/spoken-language-identification/pretrained_models.html) has roughly **12 MB INT8 encoder + 86 MB INT8 decoder + token file** when only those files are selected. [Sherpa's export guide](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/whisper/export-onnx.html) identifies non-`.en` Whisper models as multilingual and usable for ASR, so Spanish is a plausible test target. This is **not evidence of lower live RAM** than ggml Tiny, and Electron native-addon packaging is more involved than the existing CLI child process. The exact ONNX export's weight licence/provenance was not clearly declared on its [repository page](https://huggingface.co/csukuangfj/sherpa-onnx-whisper-tiny); commercial redistribution of that artifact remains **unverified** even though engine and original Whisper licences are permissive. A smaller sherpa Spanish transducer could be investigated later, but none has passed the language, licence, accuracy and memory gates here.

All listed candidates execute offline when their assets are local. No model, npm package or native binary was downloaded or installed in this audit. **Disk size and live memory are distinct quantities.**

## 3. Process lifecycle and guard calibration plan

1. **Observe without weakening the guard.** On one voluntary short push-to-talk attempt under each of two ordinary conditions (quiet baseline; Chrome and ChatGPT open), capture timestamped **available physical MiB at preflight**, system **commit total/limit**, and a clear numeric refusal reason. During a successful run, sample helper **peak private bytes, peak working set, page faults, total CPU time**, lowest available physical memory, **Stop-to-draft latency**, and UI responsiveness. Report aggregates only; do not log audio or transcript. An instrumentation change would be a *future implementation step*, not performed here. The existing isolated monitor can help, but its 100 ms cadence can miss peaks. Do not bypass the application guard merely to gather a risky busy-workload trace.
2. **Check post-exit recovery.** Confirm the child exits, temporary audio is removed, and its private allocation disappears. Compare available RAM after exit, accounting for other activity and reclaimable standby cache. A persistent Whisper server or pooled helper would keep memory occupied while idle and is a poor default on 8 GB RAM. Hashing the model at each launch may affect disk-cache warmth and latency, but it occurs after the guard and is not an explanation for this refusal.
3. **Only then tune the decision rule.** If busy-workload measurements show adequate physical and commit headroom, low paging and responsive UI, consider a *measured* threshold or a combined physical/commit check. Do not set it to 512 MiB merely because a 192 MiB working set was observed. Keep a reserve for the OS and other apps, reject uncertain readings, and preserve one-helper-at-a-time, cancellation and cleanup. If headroom really is too low, give the user a precise, non-destructive explanation rather than launching.
4. **Isolated model gate if needed.** Compare Q8_0, then possibly Q5_1, with the current Tiny under the same consented Spanish clips, Chrome/ChatGPT workload, timestamps, and OS memory metrics. Proposed criteria (not established facts): no worse transcript quality on the six known clips and a larger representative set; **at least ~200 MiB or 25% less measured peak private bytes or clearly less resident pressure**; no materially worse Stop-to-draft time (aim ≤3 seconds for ~5-second speech under normal load); no serious paging or UI stalls; full process/temp cleanup; verified licence/hash and clean Windows x64 packaging. A disk-only improvement is insufficient. Do not replace existing Tiny until those gates pass. If quantized Tiny fails, pilot Vosk small Spanish separately before considering a larger Whisper model.

## Decision and unresolved facts

**GO for guarded M1.8A.2 use when preflight passes; NO-GO for lowering the guard or changing the ASR model today.** The present low-memory condition is real as far as the Windows `ullAvailPhys` metric is concerned, while the guard's exact safety margin and the risk of running below it remain unmeasured. No current evidence shows quantization, flags, sherpa-onnx or Vosk preserving the user's Spanish accuracy while materially reducing this laptop's memory pressure. The next implementable change should be privacy-safe memory/latency instrumentation and clearer numeric diagnostics, followed by a small user-controlled workload comparison.
