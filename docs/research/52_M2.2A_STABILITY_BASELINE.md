# M2.2A — Installed-app stability baseline

Status: **0.1.0 measurement record. No optimization was made from these numbers. Optional startup shipped later in 0.1.1 and is recorded in notes 53–55. A Windows sign-in launch was not part of this measurement.**

The samples below are DesktopCompanion 0.1.0 from commit `fa6917a875c388096920896d91c1dcaab2967590`. They were not repeated on 0.1.1. Every sample used processes whose executable path is `%LOCALAPPDATA%\Programs\DesktopCompanion\DesktopCompanion.exe`. `npm start` and `npm run dev` were not used.

## 1. Method

The machine has 8,016.7 MiB of physical RAM and 12 logical processors.

CPU seconds are the change in user-mode plus kernel-mode time across the wall interval, divided by 10,000,000. Percent of one logical processor is that CPU time divided by the wall time. Percent of the machine divides that by 12. These are not lifetime totals and not an instantaneous scheduler reading.

Private bytes are committed private memory, not physical RAM. Working set can include shared pages, so a sum of working sets is not exclusive RAM. Private working set was not collected.

Each row is the user-confirmed state for that sample. Process metrics alone were not treated as proof of sleep, chat, or movement. The user sent the confirmation, and the sample started then. Stable states A, B, C, and H used two samples of about 11 seconds after a short settle. Transient states D, E, F, and G used one sample of about 12 seconds so the activity could fall inside the window.

No sample lost a process halfway through. No `whisper-cli.exe` ran. Available RAM stayed under the 1,024 MiB Whisper floor for most of the session, so microphone and Whisper tests were not run.

## 2. Unclassified sample

Taken before any confirmed state. Five processes, 10.444 seconds. Tree: 13.76% of one logical processor, 1.15% of the machine, 282.03 MiB private, 175.37 MiB working set. Available RAM at the end was 1,062.0 MiB. This is context only. It is not scenario A.

## 4. What changed between states

Sleeping uses about 12–14% of one logical processor. Awake idle uses about 39–48%. The extra cost is the GPU process (about 7–8% asleep, about 25–29% awake) and renderer client 4 (about 5% asleep, about 13–17% awake). Private commit rose only about 4 MiB from A to B.

Opening chat did not raise CPU above the awake-idle band. It added renderer client 7, about 27 MiB of private commit and almost no CPU. The working-set sum rose by about 110 MiB. That sum can count shared pages more than once. The private-commit increase is the figure to keep.

The Demo send and the Demo cancel stayed in that same awake band, 41% and 45% of one logical processor. Private commit was about 11 MiB above the chat-idle reading. The user signaled the send and the cancel so the samples would overlap those actions. This audit did not see the reply text. Nothing in the process data shows a separate generation spike.

Manual movement raised the tree from the awake band to 50% of one logical processor. The main process went from under 2.5% to 7.81%. Renderer client 4 and the GPU process stayed near their awake readings.

The confirmed wander hop measured 52% of one logical processor and 268 MiB private, close to manual movement. The main process was lower than during continuous manual moves (2.51% versus 7.81%). A hop can finish before 12 seconds, so this sample can include a short rest after the hop. It does not show Wandering leaving a higher CPU cost than a manual move.

Neon Trail during movement measured 65% of one logical processor and 302 MiB private. Against manual movement without the trail, that is about 15 percentage points of one logical processor and about 35 MiB of private commit. Renderer client 8 accounted for 3.52% of one processor and 31.44 MiB private. The GPU process rose from 26.96% to 35.69%. The working-set sum rose more, to 399 MiB, led by that renderer’s 96 MiB working set.

After the user stopped movement and returned the robot to sleep, CPU fell to 14.6% and 18.7% of one logical processor. That is near scenario A (12.4% and 13.9%), not near the awake or movement readings. The second H sample is a little higher than A because renderer client 4 used 9.57% in that interval. GPU use was back near the sleep readings, about 8%. Private commit stayed near 299 MiB because the chat renderer and the trail renderer were still alive. Both used no CPU while the robot was asleep.

## 5. Stability

The original four processes never exited or restarted. Extra renderers appeared when chat and the trail were used, and one idle renderer left before the no-trail movement sample. No unexpected child and no crash appeared.

Private commit moved with those processes: up by about the size of a new renderer, down by about the size of the one that left. The long-lived main and GPU processes gained roughly 6 MiB and 10 MiB of private commit from A to H. That is one session of real use, not a leak finding. A repeated chat open/close stress test was not run. One create-and-keep of the chat window does not justify calling the increase a leak.

Sleep lowered CPU. Awake idle costs more, and that cost is the visible animation. Chat, Demo, and cancellation did not add a meaningful CPU load on top of being awake. Movement adds a modest main-process cost. The trail adds one renderer and some GPU time only while it is enabled. Wandering, during the one confirmed hop, matched manual movement and did not leave the CPU high afterward.

## 6. Recommendation

Keep the validated 0.1.0 build as it is. No animation, eye, gesture, movement, wandering, or Neon Trail change is justified by these measurements. The awake cost is the product, about 3–4% of this 12-processor machine. The trail cost is the feature drawing particles.

Login startup was not part of this 0.1.0 measurement. It later shipped in 0.1.1 as a tray choice, default off, per user, without elevation. That later test did not repeat these samples and did not include a Windows sign-in launch.

Available RAM during these samples was about 780–948 MiB. That is below the 1,024 MiB Whisper guard. Whisper stays unavailable in this package, and it was not tested.
