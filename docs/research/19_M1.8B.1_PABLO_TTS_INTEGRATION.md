## 2. Voice backend selected and why

**Chromium `window.speechSynthesis` in the chat renderer** (not SAPI-only).

Per `docs/research/18_WINDOWS_TTS_FEASIBILITY.md`, **Microsoft Pablo** appears in Chromium’s `getVoices()` list with `localService: true`, but was **not** in the classic System.Speech inventory (Helena/Zira only). SAPI-only would not reliably expose Pablo; Electron’s Chromium stack matches the user-validated pilot path.

No cloud TTS, no Piper/sherpa downloads, no new npm dependencies.

## 3. How Microsoft Pablo is selected

Constants in `textToSpeech.ts`:

- Name: `Microsoft Pablo - Spanish (Spain)` (`PABLO_VOICE_NAME`)
- Locale: `es-ES` (`PABLO_LOCALE`)

`pickPabloVoice()`:

1. Filters voices to `es-ES`.
2. Requires `/pablo/i` in `name` (does **not** fall back to Helena or Laura).
3. Resolves the live `SpeechSynthesisVoice` by matching stored `voiceURI`.

`createChromiumTtsProvider()` waits for `voiceschanged` (plus a 2.5s cap) before speaking. If Pablo is missing, speak returns `failed` and the UI shows a clear error.

## 4. Play / Stop behavior

- **Manual Speak** on each assistant/demo line (`aria-label="Speak reply"`).
- **Global Stop** in the speech settings bar while speaking.
- One playback at a time: new Speak calls `tts.stop()` first.
- **Auto-read** optional (default **off**); only new assistant/demo lines when enabled.
- User messages, reasoning blocks, and errors are not auto-spoken.
- States: idle ↔ speaking; UI status bar and line-level `Speaking` styling.

## 5. Interaction with microphone and Whisper

- Mic button disabled while `tts.state() === 'speaking'`.
- Starting push-to-talk calls `tts.stop()` before arming the mic.
- TTS does not arm or open the microphone.
- Main sends `chat:tts-force-stop` on chat hide, destroy, minimize, and app quit (alongside existing `speech:force-stop`).
- Renderer disposes TTS on `pagehide`.

## 6. Character animation behavior

- Main publishes overlay presence **`SPEAKING`** while `ttsSpeaking` (overrides session presence until playback ends).
- `presence.ts` applies a subtle antenna/eye/hover pulse for `SPEAKING`.
- **`prefers-reduced-motion: reduce`** disables pulse amplitude (static pose).
- Sleep/wake behavior unchanged; conversational presence still suppressed while the robot is asleep.

## 8. Performance considerations

- TTS runs entirely in the chat renderer; no extra main-process audio pipeline.
- Text capped at **1600** chars; longer replies split into **≤420** char sequential chunks (no overlapping utterances).
- Voice enumeration timeout **2.5s** on first speak (one-time per provider instance).
- No disk writes for chat text or synthesized audio.

## 9. Manual Windows validation steps

1. Quit any running Desktop Companion (required for smoke and to reload preload).
2. `npm run build` then `npm run start` (or `npm run dev`).
3. Wake robot, open chat, send a **Demo** message → click **Speak** on the reply → confirm **Microsoft Pablo** audio and **Speaking** bar + robot motion.
4. Click **Stop** mid-phrase → audio stops, robot leaves `SPEAKING`.
5. Start **Speak** on one message, then **Speak** on another → first stops.
6. While speaking, confirm mic control is disabled; start **Hold to talk** after stopping TTS → mic works; starting record while speaking should stop TTS first.
7. Close chat while speaking → playback stops.
8. Settings: toggle speech off/on, adjust rate (0.75–1.25), leave **auto-read** off unless testing optional auto playback.
9. Optional: disable network → Speak still works if Pablo is `localService`.
10. Optional: rename/remove Pablo in Windows speech settings → Speak shows Pablo-unavailable message (no silent fallback).

## 10. Known limitations

- Pablo availability depends on Windows/Chromium voice packages; no silent fallback voice.
- `speechSynthesis` quirks (enumeration delay, interrupted errors) handled with timeout, cancel, and abort controller.
- Auto-read is off by default; enabling still skips user/reasoning/error text.
- Preview/dev presence picker may omit `SPEAKING` (overlay uses live TTS presence only).
- Future engines can implement `TextToSpeechProvider` without rewriting chat UI.

## Regression checklist (unchanged)
