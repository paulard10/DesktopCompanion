# M2.0C.1 — Motion regression

Status: **rejected on the Windows desktop.** Curious, Listening, Thinking, Responding, and Error still showed no body motion. Happy only made the robot slightly bigger. The antenna and the arms did not visibly move. Move Up, Down, Left, and Right did not move the window. Unit tests were not a fix. Diagnostics continue in [M2.0C.2](38_M2.0C.2_VISUAL_ACTUATOR_DIAGNOSTICS.md).

## 1. What the desktop was doing

The open dev log, while this was diagnosed, showed `trail status ... hold=asleep` and no `travel request` line. The robot was asleep. The dev preview lives in the chat window, and an open chat is still a travel pause. Those two facts explain the report without a broken `setBounds` path.

## 2. Body motion

**Cause.** Every state was drawn on top of the same idle wave: hover ±0.04, roll ±0.055, antenna ±0.12. The new gestures were smaller than that wave, and Happy, Error, and Responding fell back to it as soon as their short arch ended. Idle also added a second slow roll. With the robot asleep, sleep replaces every preview with one droop, so the buttons cannot look different until Wake.

**Evidence before.** `secondarySampleInto` left `ambientMix` unset, so `ambientPose` always reached the mesh. Curious, Listening, and Thinking differed by only a few hundredths of a radian on that wave. A happy bounce of 0.028 sat inside a hover of 0.04.

**After.** A distinct hold or a one-shot sets `ambientMix` to 0. The director multiplies the idle hover, pitch, roll, and antenna by that mix before the pose is shown. Blink is not touched. Idle keeps the original wave and no longer adds a roll of its own. The channel limits are the same ones that already fit the window.

| Pose | What you should see | Idle wave |
| --- | --- | --- |
| Idle | The original float, plus a small breath | On |
| Curious | Face up, body rolled one way | Off while held |
| Listening | Antenna up, both arms slightly raised, no roll | Off while held |
| Thinking | Face down, rolled the other way, antenna back | Off while held |
| Responding | One face nod, 640 ms, then idle | Off only during the nod |
| Happy | One bounce and arm lift, 780 ms, then idle | Off only during the bounce |
| Error | One uneven lean, 860 ms, then idle | Off only during the lean |
| Speaking | A small antenna and breath, only while the cue is `SPEAKING` | Off while speaking |
| Sleep | Slow breath, no gesture | The sleep blend, unchanged |

Transforms are still assigned every frame from the rest pose plus the current sample. They do not accumulate. A cue change clears the previous gesture. The same cue does not start it again.

## 3. Manual movement

**Cause.** `moveBy` still calls `requestTravel`, `stepTravel`, and `BrowserWindow.setBounds`. M2.0C did not edit that path. `travelBlock` returns `chat` whenever the chat window is visible, `voice` for the microphone or Pablo, and `busy` while a reply is generating. Sleep does not block a move. A yielded manual move is not cancelled by wandering, including while the robot is asleep or a hop is already in progress.

The dev preview does not set `ttsSpeaking` or `captureBusy`. Closing chat still clears those flags, hides the window, and the next travel step sees no block. A move that started while chat was open stays paused and continues when chat closes. A move with chat already closed changes position on the next tick.

**Evidence.** With chat closed, Up, Down, Left, and Right each leave the start point. With chat open they stay on `phase=paused` and `pause=chat`, and the same hop moves once the block is cleared. The live console had not printed a travel command during the captured buffer, which fits a click that never got past the open chat, or a click made while the log was only trail lines.

**After.** In development, one line is printed when a command is received:

`travel request command=up block=none asleep=false phase=moving from=… to=…`

`block=chat` means the window will not move until chat closes. `block=voice` or `block=busy` is the microphone, Pablo, or a running reply. The first real `setBounds` change prints `travel bounds x,y -> x,y` once, not on every tick. The phase line still prints only when the phase or the pause reason changes.

## 6. Windows validation

Quit the current `npm run dev`, then start it again. Wake the robot from the tray before judging gestures. Leave chat closed before judging Move.

1. Idle floats as before, without a second roll and without a constant bounce.
2. Dev preview, chat open: Curious, Listening, and Thinking each hold a different posture. The console prints `pose=curious`, `pose=listening`, or `pose=thinking` once per change, not every frame.
3. Responding prints `gesture=nod` once, then `gesture=none`. Happy prints `gesture=bounce` once. Error prints `gesture=concern` once. None of them keep repeating.
4. Speaking moves only while Pablo is talking. Stop, or let the line finish. The pose returns to idle.
5. Sleep cancels a bounce. The eyes still close. Wake returns the idle float.
6. Close chat. Tray: Move up, down, left, and right. Each line should include `block=none` and one `travel bounds` line, and the window should finish the hop. Stop halts it. Return home still works.
7. Open chat and Move up. Expect `block=chat` and no bounds line. Close chat. That hop continues.
8. Enable Wandering only if you want it. A manual Move still travels. Disable it afterward.
9. The body stays easy to click. Neon Trail still follows a hop and stays still when the window is still.

## 7. Remaining limitations

An open chat still pauses travel. That is the M1.9 rule, not a stuck preview. Sleep still replaces every preview, so gesture buttons do nothing visible until Wake. The idle float returns after a nod, bounce, or lean. This session did not watch the desktop. The running `npm run dev` does not contain this fix.
