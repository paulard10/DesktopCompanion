## Previous architecture and audit

The actual source at the checkpoint defined these independent roles:

- `placement.ts` owned nominal overlay width, height and initial parking margin.
  `overlayWindow.ts` consumes its placement result for the native window.
- `clickThrough.ts` owned the body proxy diameter. Main-process polling converts
  desktop cursor DIP to window-local DIP, then checks the centered circle.
- `createScene.ts` imported the interaction diameter to size the camera's body
  projection. `robotFrame.ts` independently owns world-unit rig geometry and
  field of view. Viewport sizing comes from live `window.innerWidth/innerHeight`.
- `chatTrigger.ts` defined badge center and radius, while renderer CSS separately
  repeated its equivalent square bounds. This was a real synchronization risk.
- `main.ts` anchors chat to live overlay bounds, with a duplicated nominal
  300 × 400 fallback. `chatPlacement.ts` owns the independent chat size and gap.
- `neonTrail.ts` independently specified the nominal body radius for its tail
  attachment. Trail particle geometry, emission, lifetime and renderer styling
  have separate purposes.
- `desktopMovement.ts` uses the actual traveling window rectangle. Existing
  Return Home uses the previously established parking rectangle, clamped to the
  display work area. It does not describe a new physical robot-home feature.
- Electron cursor, window and display work-area coordinates are DIP. Renderer
  CSS pixels correspond to these dimensions. Device-pixel ratio affects canvas
  bitmap resolution, not desktop travel coordinates.

The animated rig has no single fixed painted-pixel rectangle: arms, antenna,
hover, tilt and gestures extend beyond the nominal central body. The 160-DIP
interaction proxy is not an exact silhouette or raycast result.

## New architecture and exact value mapping

`src/shared/companionLayout.ts` is the single definition of the following legacy
values. It has no imports, platform APIs, settings reads or runtime selectors.
Its exported literal is typed `as const`; consumers do not mutate it.

- `windowDip.width = 300`, `windowDip.height = 400`: previously the placement
  constants and the main-process chat fallback. Existing placement exports are
  aliases, preserving caller APIs.
- `placementMarginDip = 16`: previously `OVERLAY_MARGIN_DIP`. Initial bottom/right
  placement and small-display clamping are unchanged.
- `cameraFramingDip.bodyDiameter = 160`: previously the scene's use of
  `ORB_DIAMETER_DIP`. This describes nominal body projection, separately from
  native-window input capture.
- `bodyProxyDip.diameter = 160`: previously `ORB_DIAMETER_DIP`. Its derived radius
  remains 80; local center remains live width/2, height/2, normally (150, 200).
- `chatBadgeDip = { centerX: 262, centerY: 332, radius: 18 }`: previously the
  chat-trigger constants. The pure `chatBadgeBoundsDip()` helper derives the same
  CSS square: left 244, top 314, width 36, height 36. The trusted hit stays circular.
- `trailAnchorDip.bodyRadius = 80`: previously trail-local `BODY_RADIUS_DIP`.
  The trail's separate 8-DIP edge gap remains in `neonTrail.ts`; tail distance is
  still 88 DIP behind the live window center along the movement direction.

The renderer now applies badge bounds through `chatBadgeLayout.ts` before scene
creation and its first frame. The four duplicated CSS values were removed.
Property assignment uses the existing first-party renderer code; no inline
script/style CSP exception was added. Badge visibility and click handling are
unchanged.

Chat anchoring and travel footprints deliberately remain live-window concepts.
They were not replaced with a nominal layout rectangle. The chat fallback alone
uses the shared nominal window size. No arbitrary renderer-supplied hit regions
or new messages were introduced.

### Values deliberately kept separate

- Camera projection diameter, input proxy diameter and trail attachment radius
  retain distinct fields despite their current numeric relationship. Future
  changes must explicitly coordinate them rather than silently infer equivalence.
- World body radius 1, field of view 28 degrees, model position/scale, face, eyes,
  arms, antenna, lights, materials and animation poses remain in their existing
  modules. There is no new claim of exact projected full-rig bounds.
- Native window footprint, painted character, circular hit proxy, badge square,
  badge hit circle, chat window and trail canvas remain different shapes.
- Chat stays 380 × 520 DIP with a 12-DIP placement gap; its minimum dimensions and
  live resizing/clamping are unchanged.
- Travel speed, easing, 120-DIP nudges, wander distances/timers, click polling and
  stale-sample behavior were not centralized as layout. Equal numeric literals
  in those systems do not establish a semantic relationship.
- DPR cap 2 and bitmap scaling remain renderer concerns. No new monitor-transition
  behavior or physical-pixel conversion was added.

## Limitations and next M3.1b parameters

This is one fixed legacy definition, not a compact selector or synchronization
protocol. No new exact visual bounding box, full-rig projection test, monitor-DPR
refresh policy or renderer-to-main layout handshake has been added. Source tests
cannot prove appearance equivalence in every animated pose or display setup.

After review and explicit M3.1b approval, a proposed compact comparison would need
coordinated choices for nominal window size, camera body projection, trusted body
proxy, badge center/radius and trail attachment radius. The existing placement
margin should be reconsidered only if the compact design requires it. Chat should
retain its readable independent dimensions and anchor to the new live rectangle;
travel/home clamping must use that live footprint. Validate actual projected arms,
antenna and animation extremes before approving a smaller window. Keep DPR,
world-model design, speed/easing and particles independent unless a separately
justified change is approved. No compact values or visual changes are selected here.
