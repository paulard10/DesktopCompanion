## 12. Attempt storage design and assessed durability

No database/dependency. One fixed **attempt.jsonl** per dedicated disposable
operation directory. First open is **wx+**: any existing file, including empty/torn,
blocks another commit. Before potential dispatch, write one exact record with
**version, offline domain, random attemptId, DISPATCH_COMMITTED state, timestamp**.
Await FileHandle.sync and bounded descriptor readback before returning ACK.

Terminal COMPLETED/FAILED/UNKNOWN is a second line on the same open descriptor,
followed by sync/readback. No replace/rename gap, record reset, append retry,
compaction or delete operation exists in the module. Recovery reads at most
1025 bytes, checks file identity/link count and rejects malformed/extra fields,
oversize or inconsistent sequences. Existing receipt code is not reused as a
screen ledger because it retains synthetic hashes/answers and records invocation
after entering its dispatch callback.

Official basis, assessed rather than assumed:

- [Node fs documentation](https://nodejs.org/docs/latest-v24.x/api/fs.html#filehandlesync)
  describes sync as a request whose behavior depends on the OS/device; exclusive
  open has a network-filesystem caveat. Reading bytes back is not power-loss proof.
- [libuv v1.52.1 Windows source](https://raw.githubusercontent.com/libuv/libuv/v1.52.1/src/win/fs.c)
  implements the file sync through FlushFileBuffers. Observed host Node is 24.21.0,
  libuv 1.52.1; no claim that all Electron/device versions behave identically.
- [Microsoft FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers)
  documents file flushing and discusses caching/write-through concerns. No volume
  flush, administrator permission or global storage change was attempted.

Observed test TEMP drive: **local (DriveType 3), NTFS**. OS ACK and process-exit
persistence are tested. **No physical power cut, kernel crash, controller-cache,
directory-entry-loss or nonlocal filesystem guarantee was established.** Before a
real pilot, review durable namespace provisioning/flush/retention and failure model;
do not label this TEMP implementation a certified live ledger.

## 14. UNKNOWN recovery

No file -> NOT_STARTED observation, not permission. Valid committed-only file ->
UNKNOWN/consumed. Empty, malformed, torn, oversized, unreadable or inconsistent
record -> UNKNOWN/consumed. Valid terminal line -> its terminal state, still consumed.
No reader resumes, retransmits, reissues consent or automatically repairs a record.

Unconfirmed terminal persistence after fake dispatch produces UNKNOWN without an
answer or retry. A crash after commit but before actual invocation may consume an
attempt that never ran; this deliberate loss of availability is acceptable for
at-most-once admission. Never promise exactly-once delivery, no charge or remote recall.

## 20. Cancellation

Before commit/admission: no credential/fake invocation. During commit: cancellation
invalidates subsequent dispatch; a file already created stays consumed. After entry:
stop local waiting and suppress stale results, but keep the attempt consumed/UNKNOWN
where delivery could be uncertain. Grants never reset and no work is queued/resumed.

Filesystem requests are asynchronous but individual OS sync calls are not assumed
abortable or hard-time-bounded. A storage stall cannot authorize later dispatch
after cancellation/expiry, but may delay settlement/cleanup. Future live isolation
must assess this separately; the normal application has no such active operation.
