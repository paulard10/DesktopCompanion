## 2. Three-layer diagnosis and evidence

### A — Native BrowserWindow/background initialization

The constructor already requests `frame:false`, `transparent:true`,
`backgroundColor:'#00000000'`, `resizable:false`, `show:false`, alwaysOnTop and
skipTaskbar. Background material is explicitly none. However, unlike the working
robot, Home and trail, the selector did **not** call setBackgroundColor after
construction. Constructor options alone were insufficient on this runtime.

A temporary native probe uses the actual Electron **44.9.3**, current selector
page/preload and geometry, and normal GPU acceleration. It has **no capture
controller, acquisition API, image export or real-image preview capability**.
Its confirmation button is hidden; its two stages differ only by this operation:

`win.setBackgroundColor('#00000000')`

**MEASURED / USER-OBSERVED A/B result:**

- A: constructor background option only; background getter **#FFFFFF**, overall
  opacity **1**, DevTools closed, content **(0,0,1536,1024) DIP**. User sees opaque
  selector, consistent with Prompt 91.
- User presses the probe's **Aplicar B** button. Runtime logs
  `stage:B-explicit-background`; getter becomes **#000000**, while opacity stays
  **1**, content stays **(0,0,1536,1024)** and DevTools stays closed.
- User explicitly confirms: **“Vi SONDA B; ahora se ve el escritorio; cerré la
  sonda”**. Probe reports successful close and exit **0**.

The getter reports RGB **without alpha**, so its color difference alone is not
proof of transparency. The controlled native API change plus the user's visible
A/B observation establish the effect. This is an application-level **native
background initialization** failure, resolved by an explicit post-construction
clear; the underlying Electron/Chromium implementation of the constructor path
has not been traced to a specific upstream defect. Do not generalize to all
Electron platforms/versions or claim a GPU driver bug.

The first keyboard-only visual attempt timed out without logging step B. Although
the user initially selected the positive answer, that run was not accepted as
causal proof. It was repeated with explicit buttons, a logged B intervention and
normal close, giving the verified result above. The final diagnostic consumes
initial readiness before arming the B button so it cannot mistake startup ready
IPC for the intervention.

### B — Chromium document background

Computed values on the actual local page: root and body backgrounds both
**rgba(0,0,0,0)**, background images none, opacity 1. Root color-scheme is dark.
There is no opaque explicit document background during SELECTING. The opaque
`body.preview` background is phase-specific and was not active in the failure.

The separate offscreen **software** output probe reads only our own local
renderer-generated bitmap, never the desktop or an OS screenshot. It measures:

- Original root/body declarations: empty-area alpha **53/255**.
- Explicit transparent root/body declarations: still **53/255**.
- Changing root color-scheme to normal: still **53/255**.
- Temporarily clearing the scrim: **0/255**.
- Restoring dark root and scrim: **53/255**.

Thus the color-scheme/opaque-CSS hypotheses were not supported by these tests.
No CSS correction was applied. Software renderer evidence does not by itself
prove native DWM blending; the native A/B observation above addresses that layer.

An initial GPU offscreen attempt supplied empty NativeImages and was inconclusive.
The proof therefore uses the documented software output mode in its **own
disposable process**; the companion's hardware acceleration/global settings are
unchanged. Measurements wait for own renderer frames so stale bitmaps are not
mistaken for new style results. No page image or bitmap is written to disk/logs.

### C — Fullscreen HTML/CSS elements

The actual #surface background is **rgba(9,24,16,0.208)**, from `#09181035`.
Its alpha is exactly **53/255**, about 20.8% tint, not an opaque black layer.
Surface opacity is 1, position absolute, no background image, filter,
backdrop-filter, blend mode or isolation effect, and no ::before/::after content.
There is no active fullscreen canvas/#app image layer or screenshot backdrop.
The hidden preview is not painted during selection.

The small controls panel intentionally paints **255/255** alpha and retains
contrast/readability. After a fixed synthetic drag, the outline paints
**255/255**, while selection interior and outside empty area both remain
**53/255**. This supports a clear outline over a lightly tinted desktop.
The root/body/surface/controls CSS and renderer are kept byte-for-byte unchanged.

## 4. Exact minimal correction

In `createScreenSelectionController().start()`, **after** the existing
`setContentBounds(s.display.bounds)` and **before** loadURL, explicitly call:

```ts
win.setBackgroundColor('#00000000');
```

Only this initialization call and its explanatory comment change application
runtime. It follows the successful explicit-background operation and the pattern
already used by the working companion windows. It clears the native background
without fading the controls, changing the page layout or replacing the selection
workflow. The setting is applied once per temporary window, not on a polling loop.

The CSS tint is genuine translucency. No screenshot, recorded frame, OCR,
background image or pre-confirmation screen acquisition is used to imitate it.
No unrelated frame/shadow/fullscreen/size flag is changed.

## 5. Input, geometry and consent remain intact

The selector intentionally receives mouse-down/drag/up and controls while active.
It does **not** enable global mouse passthrough; visual transparency and input
capture are different. The unchanged renderer uses pointer capture while dragging,
normalizes rectangle direction and sends through its narrow bridge. Cancel and
Escape destroy/release the temporary window; the desktop gets normal input again.

Preserve the Prompt 90 correction exactly: **setContentBounds(display.bounds)**,
full-display scope, strict native content and viewport/DPR equality and zero new
tolerance. 1536×1024 remains the validated surface here; workArea is not substituted.
No hardcoded screen size, crop mapping or DPI transformation changed.

Existing single-session/display/source identity, sender/top-frame/session ID,
phase, source/crop/PNG budgets, actual image dimensions and stale-result rejection
remain. Acquisition is still exclusively after the user's separate Capture
confirmation. Startup, tray opening, drag, Escape and Cancel do not capture.
No disk/clipboard write, upload, OCR, model request or microphone is introduced.
Windows may still acquire a whole display transiently **after confirmation**;
no immediate physical memory wiping or cryptographic erasure is claimed.
