## 3. Two consent stages

**Stage A — local acquisition:** select an area and personally click the existing
`Capture selected area` button. Dragging, opening the selector and cancellation
still acquire nothing. Existing local full-display transient acquisition,
own-window exclusion and proper crop rules remain in report 64.

**Stage B — one local simulation:** type a question, click Review, inspect image
and exact question, then separately click `Run offline vision test`.
Neither capture, typing, review alone nor Enter in the textarea starts a test.
There is no default question, OCR, automatic question inference or auto-retry.

Stage B **never permits external transmission**. Its token has no remote scope,
is not a stored preference and cannot be upgraded to future provider consent.

## 4. Canonical image ownership

After native cropping and size verification, full-display NativeImage references
are still dropped **before PNG serialization or delivery**, as in M3.4a.
Main transfers the resulting **same cropped PNG Buffer** and trusted pixel
geometry into one `OfflineVisionSession`. Frozen metadata prevents callers from
changing its crop/source dimensions. There is no second full-display copy.

Main generates an independent random image ID and SHA-256 of the exact PNG.
The renderer receives the original preview IPC copy only; it cannot provide
replacement PNG/Base64, URL, path, hash or crop dimensions through vision IPC.
All operations resolve the existing main-owned session, never capture again.

The existing M3.4b.1 validator now additionally accepts the main caller's
`approved-local-crop` discriminator. The historical synthetic discriminator and
strict parser remain compatible. **Neither discriminator proves approval**;
the owned capture/session/IPC boundary supplies that authority.

## 5. One-time authorization and lifecycle

Review validates the draft and current crop using the existing request builder.
It creates a random UUID capability bound to:

- Active selection session and random image identity.
- Exact crop digest, frozen geometry owner and fixed vision model/endpoint policy.
- Exact question, monotonically increasing draft revision and selected scenario.
- One specific **offline simulated** operation, expiring after **30 seconds**.

Run checks session/token/revision, expiry, draft/scenario equality and a fresh PNG
digest. It consumes approval **synchronously before** starting asynchronous work.
Duplicate clicks/replay cannot create a second operation. Later tests require
another explicit review and run. No queued user operations.

Editing or changing the scenario revokes approval. An oversized edit also
revokes the previous permission; it cannot keep old consent alive. Cancel review
revokes it. Discard, close, render/preload failure, display/session cancellation,
replacement and Quit dispose the crop and approval. Application shutdown uses
the existing selection destroy path. Old window/frame/session IDs are rejected.

Expiry is checked at use, without an idle timer/poller. The inherited **120-second
selection lifetime** remains an outer deadline and is not extended by editing,
review or execution. An open preview can therefore expire while composing.

## 6. Question validation

The browser/main/adapter share one pure validator:

- Nonempty/non-whitespace, at most **500 JavaScript UTF-16 code units**.
- At most **2,000 UTF-8 bytes**; Unicode must round-trip without lone surrogates.
- No NUL/disallowed control characters.
- Accepted spaces, accents, punctuation and line breaks are retained exactly.

Textarea maxlength/count follows the same 500-unit convention. Empty/invalid
questions disable Review locally and are also rejected by trusted main checks.
Normal editing and Enter/newline do not submit. Review cannot silently replace
the current draft: question, revision and scenario must already match.

## 9. Cancellation, discard and stale results

One generation number plus adapter identity gates every asynchronous result.
Cancel/edit/dispose increment generation and abort the active adapter, removing
its timeout/mock listener. Late replies cannot publish into an old or new
preview, clear a newer operation or reopen a discarded window.

Discard invokes the existing narrow cancel path and destroys the temporary
window. Renderer removes image src, revokes its Blob URL, clears question,
review/token and answer references. Main drops crop, question, digest, approval
and adapter references. New capture creates a fresh session/image/token space.
Starting selection while the existing session is active remains a no-op;
Discard/close first to replace it. There is no silent selection replacement.

No immediate physical memory zeroing, erasure of OS paging/crash data or control
over external caller references is claimed.

## 10. IPC and Electron security

The dedicated preload adds **one discriminated `vision(action)` method** to the
existing selection bridge. Fixed `selection:vision` messages accept only edit,
review, run and cancel shapes. Extra properties, arbitrary pixels, URLs/paths,
wrong session, revision/scenario and unexpected argument counts are rejected.

Main requires the exact owned WebContents, exact top-level mainFrame, null frame
parent, exact trusted selection URL, enabled development feature and PREVIEWING
phase before dispatch. No other robot/Home/chat preload gains this capability.

Preserved: sandbox true, contextIsolation true, nodeIntegration false,
webSecurity true, denied permissions/popups/webviews/redirects/navigation,
in-memory selection partition, trusted local assets, restrictive response CSP,
`img-src blob:` and `connect-src 'none'`. No generic capture/file/network/command
interface is exposed. Native proof uses its separately owned synthetic app://
frame; production controller's trusted localhost rule is not loosened for it.

Screenshot instructions remain untrusted pixels. No OCR/tool/action execution
or mouse/keyboard automation is added. The static mock is not evidence of a
real model's resistance to visual prompt injection.

## 11. Privacy, budgets and performance

Original capture budgets remain **16 MiB PNG / 4,194,304 crop pixels / 4096 source
side / 8,388,608 source pixels**. Vision remains **2 MiB PNG / 2,097,152 pixels /
2048 side / 384 output tokens**, with unchanged strict RGB/RGBA PNG parsing.

A valid preview can exceed vision budgets or use a PNG variant the validator
does not admit. Review then reports a local size/format limit while retaining
preview and Discard. No secret compression, resizing, recapture, larger limit or
transmission. Full-display-size previews cannot authorize the proper-subcrop
vision path. Select a smaller area in a fresh session to retry.

Ownership costs: main now retains at most the already bounded **16-MiB crop PNG**
through preview lifetime, in addition to renderer IPC/Blob/decoded texture copies
that existed before. It keeps no full-display image. Digesting uses existing
bytes. Review and Run separately validate/build; transient inflate, Base64 and
JSON copies are bounded by adapter limits and are released after validation.
The mock never receives the image/request body. No physical peak-RAM figure is
claimed; validation/building are synchronous and main-thread latency at maximum
budgets still needs measurement before live integration.

No new polling, interval, permanent renderer or background process. Only bounded
active-test delays/deadline plus the inherited session deadline. SHA/PNG work
occurs on explicit preview/review/run, not in an idle loop. No images/questions,
tokens or answers enter logs, clipboard, history, voice, TTS or application files.
Existing aggregate capture duration/dimensions/byte logs remain.

No real Windows responsiveness/CPU/RAM comparison was performed here. Historical
