# M2.0D — Real-time presence

Status: **implemented, waiting for a Windows look.** The expression geometry from M2.0C is unchanged. This milestone connects those expressions to chat, the microphone, Whisper, and Pablo. The overlay was not watched in this session. Quit `npm run dev` and start it again before looking. The main process and the chat preload do not pick up these edits from a renderer reload.

## 1. Existing lifecycle signals

The app already had one conversation session, one capture state, and one playback callback. M2.0D reuses them.

| Signal | Where it already lived | What it means |
| --- | --- | --- |
| Session `THINKING` | `conversationSession.send` | The user sent text and no visible reply has arrived. Demo and Qwen share this path. |
| Session `RESPONDING` | Assigned once, when the stream phase becomes `generating` | The first visible reply text. Later tokens update the transcript and keep the same presence. |
| Session `HAPPY` / `ERROR` | `showBriefly`, 1600 ms / 2400 ms | A finished reply, or a provider, timeout, or playback-independent failure. The timer returns to `IDLE` only while that presence is still current. |
| Session `IDLE` | Stop, reset, and the end of a brief pose | The turn is finished. |
| Turn counter | `mine !== turn` | A reset or a newer send drops the old iterator before it can publish. |
| Capture `requesting`, `recording`, `transcribing`, `idle` | `SpeechCapture` | An explicit microphone press, local recording, Whisper, then the editable draft. |
| `speechSynthesis` speaking | `chromiumTtsProvider` calls `onSpeaking` only when playback state changes | Pablo is actually playing. |
| Conversation Mode | `voiceSession` | Auto-read policy for one completed reply. It does not own the face. |
| Sleep phase | Character director | `SLEEPING` and `RETURNING_TO_SLEEP` already close the eyes and drop secondary gestures before any presence is applied. |
| Curious | `eyeCueFromState` while awake, tracking, and idle | Ambient gaze. It is an eye cue, not a presence name. |
| Dev preview | Chat preview buttons | Eye cues and presence names. They previously wrote the robot directly. |

There is no `LISTENING` presence name. The validated listening face and raised arms are the `ATTENTIVE` presence. `CURIOUS`, `SLEEPING`, `BLINK`, and `WAKING` stay eye-preview cues.

## 2. Final expression priority

`resolveCharacterPresence` in `src/shared/characterPresence.ts` is the only presence decision. The chat window publishes it. The director applies it. Sleep remains the director's decision and wins over the result of this function.

1. Real playback: `SPEAKING`, reason `tts-start`.
2. Microphone requesting or recording: `ATTENTIVE`, reason `mic-start`.
3. Whisper processing: `THINKING`, reason `asr-start`.
4. A busy turn with visible reply text: `RESPONDING`, reason `first-token`.
5. A busy turn waiting for that text: `THINKING`, reason `send`.
6. Provider or timeout failure: `ERROR`, reason `provider-error`.
7. Capture, transcription, or Pablo failure: `ERROR`, reason `voice-error`.
8. Editable draft: `IDLE`, reason `draft-ready`. An active send still wins over the draft.
9. Reply celebration: `HAPPY`, reason `reply-done`. If playback has already replaced that celebration, the publisher settles to `IDLE` instead of starting the bounce again.
10. A development presence preview, only while the real signals above are quiet.
11. Session idle: `IDLE`, reason `idle`.
12. Nothing selected yet: `CLEAR`, reason `cleared`.

The publisher sends a presence to the robot only when the presence or the reason changes. The director ignores a repeated presence. `noteSecondaryCue` ignores a repeated gesture. A stream token therefore cannot restart the nod.

## 3. Event-to-expression mapping

| Lifecycle | Presence | Reason | Gesture |
| --- | --- | --- | --- |
| Awake, nothing in progress | `IDLE` | `idle` | Existing idle and gaze. Tracking still selects Curious eyes. |
| Explicit microphone press, including the permission request | `ATTENTIVE` | `mic-start` | Validated listening arms and antenna. |
| Recording stopped and Whisper running | `THINKING` | `asr-start` | Validated thinking pose. |
| Editable transcript | `IDLE` | `draft-ready` | Attentive idle. The listening arms come down. Nothing is sent. |
| User presses Send | `THINKING` | `send` | Thinking, for Demo and Qwen. |
| First visible reply text | `RESPONDING` | `first-token` | One nod. Later tokens stay in this presence. |
| Reply finished, audio off | `HAPPY`, then `IDLE` | `reply-done`, then `idle` | One cheerful gesture, then idle. |
| Pablo playback starts | `SPEAKING` | `tts-start` | Speaking motion for the duration of playback. |
| Pablo playback ends on an idle session | `IDLE` | logged as `tts-end` | Speaking motion stops. |
| Stop, reset, or chat close during a turn | `IDLE` | `idle` | The in-flight pose ends. |
| Capture, transcription, provider, timeout, or Pablo failure | `ERROR` | `voice-error` or `provider-error` | One error gesture, then idle. |
| Tray or idle Sleep | Director sleep | unchanged | Eyes close and the gesture drops immediately. |

Audio that is switched off stays out of `SPEAKING` and does not raise the error gesture. A missing Pablo voice, or a `speechSynthesis` failure, does.

Development logs, only when the presence changes:

```text
desktop-companion: presence none -> THINKING reason=send
desktop-companion: presence THINKING -> RESPONDING reason=first-token
desktop-companion: presence RESPONDING -> SPEAKING reason=tts-start
desktop-companion: presence SPEAKING -> IDLE reason=tts-end
```

The log names the presence being entered. `tts-end` is the exit label used when playback returns to idle. A draft uses `draft-ready`. The line contains no message text, transcript, audio, or key.

## 5. IPC and security

The channel remains `chat:voice-presence`. The preload allowlist is `ATTENTIVE`, `THINKING`, `IDLE`, `ERROR`, and `CLEAR`. Any other value is dropped in the preload. The main process stores the four poses and treats `CLEAR` or anything else as no voice signal. The handler still requires the visible chat frame.

No new channel, dependency, permission, or credential path was added. The transition log is development-only and records the presence name and the reason. Microphone capture still starts from the button. The memory guard and the provider limits are unchanged.

## 6. Cancellation and stale events

- Stop during generation aborts the provider and publishes `IDLE` from the current turn.
- Reset increments the turn, clears history, and publishes `IDLE`. An older iterator returns without publishing.
- The happy and error timers publish `IDLE` only when the presence is still the one they started. `stop()` cancels that timer.
- Chat hide and destroy clear playback, the voice signal, and the preview, then publish. They also force-stop capture and speech.
- A voice or playback message that arrives after the chat is hidden fails the visible-frame check and is ignored.
- The capture callback reports the draft before the capture state returns to idle, so the idle refresh does not wipe the draft pose. A failure reports `ERROR` after that idle refresh.
- Submit and reset clear the draft signal before the next session pose, so a leftover draft cannot rename a later celebration as `draft-ready`.
- A development preview is discarded when any real reason wins, so it cannot return after the real event ends. Sleep, a busy turn, recording, transcription, and playback reject a new preview.

## 9. Windows manual validation

Quit the running app and start `npm run dev` again. Use **Demo** mode. Wake the robot before each look. In a development terminal, confirm the presence lines appear once per change and contain no chat text.

1. **Text, Demo off for speech.** Turn Conversation Mode off and turn speech off. Send a short Demo message. Expect thinking, then one nod when the reply text appears, then one cheerful gesture, then idle. The listening arms should stay down. Stop during the thinking pause and expect idle, with no reply kept on screen as a speaking pose.
2. **Microphone.** Press the microphone, allow it, speak, and stop. Expect the listening pose only while it is recording, thinking while it transcribes, then idle with the text left in the composer. The message must not send itself. Edit it, then press Send and expect the Demo sequence from step 1.
3. **Capture failures.** Deny the microphone, or cancel the recording, or wait for the 20 second cap. Expect one brief error pose and no transcript send. If the memory guard refuses Whisper, expect the same error pose and a text Send that still works.
4. **Pablo.** Turn speech on. Use the reply's Speak button. Expect the speaking pose only while audio is heard. Stop must drop it immediately. Turn speech off and send another Demo message: the reply stays a text celebration, with no speaking pose.
5. **Conversation Mode.** Turn it on and send one Demo message. After the reply, Pablo should read it once and the speaking pose should match the audio. It must not turn the microphone back on.
6. **Sleep.** During a nod or the cheerful gesture, choose Sleep. The eyes close and the gesture drops. Wake returns to the current idle or real activity, without reviving the old gesture.
7. **Close.** Close chat during recording, during a Demo reply, and during speech. The robot returns to idle. Open chat again. The old listening or speaking pose stays gone.
8. **Preview.** While idle, use a development expression button. Then send a Demo message. The real thinking and reply poses take over, and the preview does not return when the reply finishes.

A live Qwen request is not required for this pass.

## 10. Remaining limitations

The desktop has not confirmed these transitions yet. Smoke could not launch a second instance.

`ATTENTIVE` is the listening pose, so a finished draft uses `IDLE` rather than a second attentive name. The permission dialog is included in the listening pose because the user has already pressed the microphone button.

The validated Happy presence still carries its small whole-body lean and antenna offset for as long as that presence is held. The bounce itself remains the one-shot gesture. If Pablo starts during the celebration, playback replaces it, and the bounce does not start again when playback ends.

Curious remains the low-priority tracking cue. This mapper does not schedule it. Sleep remains the director's phase, so a presence message cannot open the eyes of a sleeping robot.
