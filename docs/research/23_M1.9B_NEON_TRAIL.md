Status: **implemented, then failed the first Windows visual test.** A white rectangle appeared under the robot and no pearls were drawn. The transparency fix is [M1.9B.1](24_M1.9B.1_TRAIL_TRANSPARENCY.md). The preload now also sends `trail:fault` and `trail:drew`.

## 1. Architecture and new files

The avatar window still owns the robot and its click target. Pearls live in a second frameless window so they stay on the desktop when the robot moves on. That window is not a child of the avatar, so it does not travel with it.

The main process owns both windows. It samples the avatar’s real DIP bounds while a move is in progress and decides when a pearl is born. The trail page only draws. It cannot move a native window.

| File | Role |
| --- | --- |
| `src/shared/neonTrail.ts` | Distance sampling, caps, fade math, DIP mapping |
| `src/shared/neonTrail.test.mts` | Generator, coordinates, window-safety source checks |
| `src/main/trailWindow.ts` | Transparent trail window, show/hide, z-order |
| `src/preload/trailPreload.ts` | Hello, spawn, viewport, clear. No window control |
| `src/renderer/trail.html`, `trail.css`, `trail.ts` | Canvas 2D pearls |
| `src/main/overlayWindow.ts` | Publishes travel samples. Final step lands with `setBounds` |
| `src/main/main.ts`, `src/main/tray.ts` | Dev tray: Enable, Disable, Reset |
| `src/shared/ipc.ts`, `src/shared/trustedUrl.ts` | Trail channels and `trail.html` trust |
| `vite.config.mts`, `tsconfig.preload.json`, `package.json` | Build and test wiring |

Qwen, Whisper, and Pablo are unchanged.

## 2. Why Canvas 2D

A second Three.js context would add another WebGL context on an Iris Xe machine with 8 GB of RAM. The pearls are a handful of soft circles, not a scene. Canvas 2D radial gradients draw a bright core and a lime halo without a bloom pass.

`paintPearl` is the only drawing function. A later milestone can replace it without changing the sampler or the window policy.

The production trail script is **2.56 kB** (1.27 kB gzip), separate from the robot bundle.

## 3. Particle drawing and timing

Pearls are born from distance, not from the clock.

- Spacing is 16 DIP. Standing still adds none.
- A paused move adds none, and the anchor resets so the resume does not draw a line across the pause.
- A jump longer than 48 DIP is treated as a hitch. The gap is dropped instead of bursting.
- At most 2 pearls are born per sample, and at most 32 are alive.
- Life is 500–900 ms. Diameter is 4–10 DIP. Drift, size, and life come from a fixed integer seed.
- Each pearl eases in, drifts a few DIP, shrinks, and fades out. Age 1 removes it.
- Color is a white-green core with a neon-green halo (`rgba(57, 255, 46, …)`). No `shadowBlur` and no postprocessing.
- The animation loop is `requestAnimationFrame`, and only while a pearl exists. An empty list cancels the frame and tells the main process the burst is over.

The birth point is the trailing edge of the **160 DIP body**, not the center of the 300×400 window. The body circle is centered in that window (radius 80). The pearl sits 8 DIP outside that circle, opposite the velocity. Left, right, up, and down each leave the pearls behind the robot.

## 4. Exact trail window behavior

The window is created only after **Enable Neon Trail**. It stays hidden until a pearl exists.

- Transparent, frameless, no shadow, Mica disabled, square corners.
- `focusable: false`, and `setFocusable(false)` again on show.
- `skipTaskbar: true` so it stays off the taskbar and Alt+Tab.
- `showInactive()` only. Nothing calls `focus()`.
- `before-input-event` is cancelled, so a stray key does not land in the page.
- Always `setIgnoreMouseEvents(true)`. There is no path that passes `false`.
- Same always-on-top level as the avatar (`floating`). When the trail is shown, the trail calls `moveTop()` and then the avatar calls `moveTop()`, so the robot stays above the pearls. Electron focus repeats that order.
- Bounds are the DIP box around the live pearls, padded and clamped to the current work area. The window is not the full desktop.
- Chat open clears and hides the trail immediately, so pearls do not sit on the composer.
- Stop movement stops new pearls. The ones already born finish their fade.
- Return home is a normal move, so it leaves a trail when the trail is enabled.
- Sleep and the return to sleep clear pearls immediately.
- Hide, disable, display loss, and quit clear pearls and drop the window. Disable and quit destroy it. An idle burst only hides it, so the next move does not pay to create the page again.
- Close is cancelled unless the app is quitting. The window hides and the list is cleared.

## 5. Coordinate handling

All positions are Electron DIP. `trailWorkArea` checks `scaleFactor` and returns the work area unchanged. It never multiplies a position by the scale.

Global DIP becomes canvas DIP with:

`localX = globalX - trailWindow.x`

`localY = globalY - trailWindow.y`

Negative monitor origins stay negative until that subtraction. The taskbar is outside `workArea`, and the trail box is clamped to that rectangle. A pearl that would land outside the work area is not born.

`devicePixelRatio` scales only the canvas bitmap so the circles stay sharp. It is not applied to desktop coordinates.

A display change clears the list and forgets the anchor. The next move starts clean on the display that contains the avatar. Pearls are not drawn on a second monitor.

## 6. Click-through guarantees

The trail never becomes an interactive window. Mouse events are ignored for its whole life, including while it is animating. The avatar keeps the existing 160 DIP circle test. A click on the body hits the avatar, which is above the trail. A click on a pearl, or on a transparent corner, passes through the trail to the window underneath.

The trail preload cannot set bounds, call `setIgnoreMouseEvents`, or `invoke` anything. The only messages it sends are hello, reduced-motion changes, and idle.

## 7. Resource and performance

- No second WebGL context. The trail page does not import Three.js.
- No bloom, no `shadowBlur`, no full-desktop repaint. The window hugs the live pearls.
- The draw loop stops when the list is empty. A hidden window does not schedule frames.
- The main process sends a spawn only when a pearl is born, and a viewport only when the box changes. It does not stream positions every animation frame.
- An expiry timer runs at 100 ms only while pearls are alive, then stops.
- While you are developing, the console prints `desktop-companion: trail active=` at most once a second, and `desktop-companion: trail canvas=2d maxFrameMs=` when a burst ends. That is the frame-time evidence. This session did not read a live number, because the running app is still the previous build.

The built trail page is 2.56 kB of script and 0.19 kB of CSS.

## 9. Manual Windows validation

Quit the running Desktop Companion first. The process that is open now does not contain this build.

1. `npm run dev`.
2. Confirm the robot does not move and no pearls appear.
3. Wake the robot. It starts asleep, and sleep clears the trail.
4. Tray: **Enable Neon Trail**. Still no pearls until a move.
5. Move left, right, up, and down. Pearls should appear just behind the body, glow, shrink, and vanish. They should not form a solid line.
6. Stop movement. No new pearls. The ones on screen should finish fading.
7. Return home. The trip home should leave a trail.
8. During a move, click a desktop icon through a transparent corner and click the robot body. Typing in another app should keep focus.
9. Open chat during a trail. Pearls should disappear, and the robot should wait. The composer should keep focus.
10. Start the microphone or let Pablo speak. Travel should still wait.
11. **Disable Neon Trail**, then move. The robot should move with no pearls.
12. Enable again, move, then **Reset Trail**. Pearls should clear. The next move should draw again.
13. If Windows reduced motion is on, enable the trail and move. Movement should work and the trail should stay empty. The console should show `desktop-companion: trail reduced-motion`.

`npm run start` without `DESKTOP_COMPANION_MOVE=1` does not show these tray items, and the trail stays off.

## 10. Known limitations

- The trail is a development control. It is off until Enable Neon Trail.
- Pearls stay on the one display that contains the robot.
- An open chat clears the trail instead of fading it across the composer.
- Sleep clears pearls immediately. Stop lets them fade.
- A hitch longer than 48 DIP leaves a gap rather than a burst.
- The newest pearls sit in the transparent part of the avatar window, around the body. The opaque robot covers anything directly under the sphere.
- Reduced motion is read from the trail page after you enable it.
- There is no wandering, and no saved trail preference.

## 11. What remains for M1.9C — autonomous wandering

M1.9C would add a main-process planner that chooses the next point inside the same work area and feeds the movement controller that already exists. It would use the same speed cap, the same pause rules for chat, microphone, and Pablo, and the same stop from the tray.

The planner would not get a new way to place windows, and it would not run while the trail page or the avatar page asked for it. Sleep, reduced motion, and an open chat would hold it. The neon trail would follow those samples without a second implementation.

That planner is now [M1.9C](26_M1.9C_AUTONOMOUS_WANDERING.md). It is off until Enable Wandering.
