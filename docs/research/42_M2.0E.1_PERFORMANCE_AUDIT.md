# M2.0E.1 — Performance baseline and audit

Status: **audit only.** No feature code was changed. The character, chat, movement, wandering, Neon Trail, Qwen, Whisper, and Pablo stay as validated.

This note separates three kinds of evidence:

- **Collected here:** source inspection, the production bundle from `npm run build`, and one 10-second working-set sample of the already-running dev app.
- **Not collected:** CPU, GPU utilization, frame time, and a labeled pass through the states below. Those need the Surface while its activity is known.
- **Calculation, not a capture:** triangle counts derived from geometry constructor arguments. The live count is the startup line `desktop-companion: webgl ready`.

## 2. Rendering lifecycle

The overlay is 300×400 DIP (`OVERLAY_WIDTH_DIP`, `OVERLAY_HEIGHT_DIP`).

`createCompanionScene` builds the renderer once:

- `alpha: true`, `antialias: true`, `premultipliedAlpha: false`
- `powerPreference: 'high-performance'`
- clear color alpha 0
- `SRGBColorSpace`, `ACESFilmicToneMapping`, exposure 1.05
- pixel ratio `min(devicePixelRatio, 2)` via `MAX_PIXEL_RATIO`
- `setSize(cssWidth, cssHeight, false)`, so the backing store is the CSS size times that ratio

On this laptop the integrated GPU is the only GPU, so `high-performance` has no discrete chip to wake. The cap of 2 means a 200% scale factor does not allocate a larger buffer than 600×800 for the 300×400 window. A 150% scale factor uses 1.5 if that is the reported ratio. The ratio actually used is printed once: `desktop-companion: webgl ready calls=… triangles=… dpr=… gpu=…`. That line was not in the retained dev-terminal buffer, so dpr, triangle count, and the GPU string were **not collected**.

The loop is `renderer.setAnimationLoop`. Three.js schedules that with the display refresh. The callback returns immediately when the document is hidden. `visibilitychange` detaches the loop while hidden and attaches it again when shown. Tray Hide calls `overlay.hide()`, which hides the window and should take the document hidden. While the robot is on screen, including asleep, the document stays visible and the callback keeps being scheduled.

`shouldRenderFrame` in `behavior.ts` allows a WebGL draw on every callback except full `SLEEPING`, which draws only after 80 ms. `RETURNING_TO_SLEEP`, waking, idle, tracking, gestures, and travel are not on that 80 ms gate. The important detail is the order in `createScene.ts`: `director.step` runs **before** the `render` flag is checked. A skipped draw still runs the pose math. It does not call `renderer.render`.

No frame time or frames-per-second number was collected. Idle motion was validated at the current rate. This audit does not treat a lower awake rate as safe.

### Scene contents, from the constructors

Lights, created once: one hemisphere, two directional, one point on the antenna tip. `renderer.shadowMap` is never enabled.

Materials, created once: two `MeshPhysicalMaterial`s (white shell, glossy face) and `MeshBasicMaterial`s for the eyes, cheeks, antenna tip, arm rings, and catchlights. The shell material is shared by the body and both arms. The face material uses roughness 0.07 and clearcoat 1. That is the validated look.

Meshes, created once: body sphere, face lens, two eye tori, two catchlights, two cheeks, antenna stem, antenna tip, and six pieces on each arm. That is 22 meshes. `apply` writes transforms and colors. It does not construct geometry. `dispose` disposes those geometries and materials, then `renderer.dispose()` runs. Nothing in the running app calls `createCompanionScene(...).dispose()`; the page is destroyed with the window on quit.

Geometry arguments, and the triangle count those arguments imply for a full sphere (`widthSegments * heightSegments * 2`). This is arithmetic, not a captured `renderer.info` value:

| Mesh | Arguments | Implied triangles |
| --- | --- | --- |
| Main body | `SphereGeometry` 64 × 48 | 6,144 |
| Face lens | `SphereGeometry` 48 × 36 | 3,456 |

The other meshes are small tori, capsules, and spheres. The startup log is the number to trust.

`director.step` allocates one pose object on every callback, including skipped sleep draws. Eye, gaze, and secondary buffers are reused.

## 3. Electron and timers

`backgroundThrottling` is not set. Electron’s own default remains. The code’s explicit stop is `document.hidden`, not a custom throttle.

| Timer | Interval | When it runs |
| --- | --- | --- |
| Cursor poll | 16 ms | While the overlay is shown, including sleep. Sends a cursor IPC every tick. Stopped on hide. |
| Travel | 32 ms | Only while a move is in progress. Cleared when travel goes idle. |
| Wander | one `setTimeout` | Armed only when wandering is enabled. Wandering and the trail menu are behind `devMovement` (`DESKTOP_COMPANION_DEV` or `DESKTOP_COMPANION_MOVE`). |
| Wander lease | one `setTimeout` | Same gate. |
| Trail age | 100 ms | Only while trail particles exist. |
| Trail draw | display refresh | Only while particles or the dev marker are alive. `cancelAnimationFrame` when the canvas is empty. |
| Speech capture | display of elapsed time, plus a 20 s deadline | Only during a recording. |
| Pablo voice list | short poll, then cleared | Until voices settle. |
| Happy / error | 1,600 ms / 2,400 ms | One timer, cancelled on stop, reset, and chat close. |
| Dev Compare | 1,400 ms | Only after the Compare button, and only in a dev build. |

Click-through depends on the 16 ms poll. Sleep does not hide the window, so the poll continues while the robot sleeps on screen. The pointer log itself is debounced. The IPC is not.

Chat close calls `hide()`. The `BrowserWindow` stays. The next open reuses it. Quit calls `chat.destroy()`, which removes the IPC listeners listed in `chatWindow.ts` and destroys the window. Overlay destroy removes its IPC and display listeners and stops both timers. Trail disable calls `destroyWindow()` and stops the age timer. A later enable creates a new trail window. Those listeners are not stacked on each enable.

`createScene`’s `dispose` does not remove the visibility or WebGL context listeners, and it does not call `stopExplore`. That path is unused during normal shutdown because the page goes away with the window.

Single-instance: a second launch logs `desktop-companion: second-instance-exit` and exits. The first process is left running. Shutdown is `before-quit` → `shutdown`: wander timers, tray, chat, overlay, trail, then `app.quit`.

## 4. Memory and voice

Whisper is not inside the Electron process. `createLocalSpeechJob` spawns `whisper-cli.exe` with `ggml-tiny.bin`, `-l es`, `-t 2`, `-ng` (no GPU), and a 30 s kill timer. One job at a time. Cancel kills the child. The temp directory is removed in `finally`. Stderr is drained and not logged. The spawn is refused unless available memory is at least 1,024 MiB (`MINIMUM_ASR_AVAILABLE_BYTES`). A failed reading is a refusal, not a zero. This audit did not change that guard, the model, or the launch flags.

`ggml-tiny.bin` was not in the workspace tree, so its disk size was not measured. No `whisper-cli.exe` was in the process sample below, so transcription was not running then. The resident size of a live transcription was **not collected**.

Pablo uses `speechSynthesis` in the chat renderer. Chat hide sends `ttsForceStop` and `speechForceStop`. `pagehide` calls `tts.dispose()`. Closing the chat does not destroy the renderer, so the chat process remains after the first open.

Qwen cancellation is the session `AbortController` plus the turn counter. No request was made for this audit.

The avatar renderer is one WebGL context for the life of the overlay window. Geometries and materials are not recreated per frame.

## 7. Windows measurement procedure

Use the existing dev terminal. Do not add a profiler, a counter that stays installed, or a second copy of the app. Quit extra Desktop Companion windows first so only one tree exists. Leave Cursor running if that is how you work, and do not add Cursor’s processes into the companion total.

In Task Manager, Details, show the Command line column. Keep rows whose command line contains `DesktopCompanion`. Drop rows whose command line contains `Cursor`. Also drop any other Electron app. For each kept row, note the pid, the `--type=` value (`gpu-process`, `renderer`, `utility`, or none for the main process), CPU, and memory. On the Performance tab, note GPU 0 (Intel Iris Xe) only as a whole-machine figure, and say what else was moving on screen.

For each state, wait until the activity is actually that state, then watch for 60 seconds. Write the start and end memory of each companion pid. Note the highest CPU you see, and whether it was a spike or the whole minute. Stop the watch. Do not leave a log running.

The avatar terminal prints, once:

```text
desktop-companion: webgl ready calls=… triangles=… dpr=… gpu=…
```

Copy that line into the sheet. It is the real triangle count and pixel ratio.

| State | How to enter it | What to watch |
| --- | --- | --- |
| A Startup | Quit, start `npm run dev`, open the robot | Which pids appear, the webgl line |
| B Sleeping | Leave the robot asleep, chat closed, trail off | Renderer CPU. Draws are gated; the callback is not |
| C Awake idle | Wake, do not open chat, do not move the window | Renderer CPU against B |
| D Chat open, idle | Open chat, type nothing | A chat renderer should already exist after the first open |
| E Demo reply | Demo mode, one short message, speech off | Main and chat CPU during the reply only |
| F Pablo | Speak on that reply, then Stop | Chat CPU only while audio plays |
| G Wander | Dev tray, enable wandering, one hop, then disable | The 32 ms travel timer should exist only during the hop |
| H Neon Trail | Enable, let one move draw pearls, then disable | Trail renderer should exit after disable |
| I Whisper | One explicit recording under 20 s, then stop | `whisper-cli.exe` present only during the job, gone after, including after Cancel |
| J Chat open/close | Open and close chat five times | Chat pid should stay the same. Memory should not climb on each close |
| K Wake/sleep | Wake and Sleep five times | No extra renderer pid |
| L Idle | Awake or asleep, 10 minutes, no typing | End memory against the start of the 10 minutes |

If available memory is under 1,024 MiB, skip state I. The guard will refuse the launch. That refusal is the safety policy, not a failed test. Do not lower it.

After J and K, the companion pid list should match the list from the start of that state, plus nothing else. `whisper-cli.exe` should be absent.

## 8. Bundle

Vite’s 500 kB warning is the avatar entry, `main-*.js`, at 562.32 kB (gzip 142.32 kB). Chat and the trail are separate entries and are small.

The avatar page imports from `'three'`, which resolves to the prebuilt `three.module.js` (662,772 bytes). The minified avatar chunk contains `WebGLRenderer`, `ACESFilmicToneMapping`, and `MeshPhysicalMaterial`. It does not contain `GLTFLoader`, `EffectComposer`, `CSS3DRenderer`, `DRACOLoader`, or `OrbitControls`.

Tree-shaking cannot pull individual Three.js source files through that package entry. The chunk size matches “most of `three.module.js`, minified, plus the robot.” Splitting that chunk would not shrink the overlay process, because the overlay needs the renderer on the first frame. Chat does not load it. Silencing the warning would not change runtime memory.

No extra dependencies are in the renderer graph. `package.json` runtime dependencies are only `three`.

## 9. Visual polish

No defect was identified against the validated robot or the validated chat layout. The user has accepted both.

These are observations, not a request to change the look:

- The glossy face and the white shell are `MeshPhysicalMaterial` with clearcoat, tone-mapped, on a transparent antialiased canvas. That combination is the likely GPU cost if section 7 shows the GPU busy while idle. Changing it changes the accepted appearance.
- The body and lens use the segment counts above. Fewer segments would change the outline.
- The face plate stays at identity rotation. That fix stays.
- Chat spacing, the collapsed Developer Tools section, and the docked composer were accepted in M2.0D.1.
- The trail is a separate transparent Canvas 2D window and only exists while enabled. Its draw loop already stops when no pearl is alive.
- Windows transparency is handled by `setBackgroundMaterial('none')` and a clear color on both the avatar and the trail. No new fringe was reported in the validation.

## 10. Prioritized backlog

Ranked for an 8 GB Iris Xe laptop. Nothing below is approved to implement until the sheet in section 7 is filled.

### Essential fixes

None. There is no measured failure, leak, or frame-time number that justifies a code change now.

### Worthwhile only if the sheet shows it

1. **Stop doing full pose work on skipped sleep frames.** Evidence: `director.step` runs on every refresh while `SLEEPING` draws at 80 ms. Expected benefit: less renderer CPU while the robot is asleep on screen. GPU draws are already gated. Difficulty: small. Risk: the slow breath, if a gap longer than `MAX_FRAME_MS` (100) is introduced. An 80 ms gap stays under that clamp. Measure: state B CPU before and after, and a visual check that sleep still breathes. Rollback: restore the current `setAnimationLoop` callback.

### Optional polish

2. **Material or segment changes.** Only if state C shows the GPU busy and the CPU fix does not matter. High risk to the accepted face and body. Needs a side-by-side screenshot. Rollback: restore `physical()` and the segment counts.

### Not justified by the evidence

- Lowering the awake frame rate. Idle, gaze, and blink were accepted at the current rate. No frame time was captured.
- Slowing the 16 ms cursor poll. Click-through depends on it while the window is shown.
- Splitting or replacing the Three.js entry to clear the Vite warning. Chat is already separate. The overlay still has to load the renderer.
- Destroying the chat window on every close. Reopen would pay the startup cost again. State J checks whether the retained window grows.
- Weakening the 1,024 MiB Whisper guard, changing the tiny model, or enabling Whisper’s GPU.
- Removing `powerPreference: 'high-performance'` on this machine. There is no second GPU here.
- Wiring `dispose()` for a leak that the current shutdown does not hit.

## 11. Risks and rollback

M2.0E.2 should start from the measurement sheet, not from this list. The only low-risk code candidate is the sleep callback. If state B is already near idle CPU, that change is not worth the regression risk to the sleep pose.

Any later change should be one patch, with the same typecheck, test, build, and smoke commands, plus the two states it claims to affect. Revert that patch if the visual check fails. Do not combine a material edit with a frame-rate edit.

Wander, the trail, movement distances, eye geometry, secondary-motion amplitudes, and the presence mapper are outside this backlog.
