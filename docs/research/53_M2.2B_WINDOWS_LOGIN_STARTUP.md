# M2.2B — Optional Windows login startup

Status: **source design for optional login startup. The 0.1.1 build, install, and Windows registry test are in notes 54 and 55. This note is not yet committed. A Windows sign-in launch was not tested.**

The sections below record the design. Where they describe the installed 0.1.0 copy, that was the state before the upgrade in note 55.

## 1. APIs

Electron 44.9.3, confirmed from the installed type declarations and the v44.9.3 Windows implementation:

- `app.setLoginItemSettings(settings)`
- `app.getLoginItemSettings(options)`

On Windows, Electron writes one value under the current user:

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`

Windows can leave that value in place and turn it off from Task Manager or Settings. That switch lives under:

`HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run`

Electron 44 treats those as different facts. `openAtLogin` is true only when the Run value named with the app user model id matches the formatted command, including the quotes Electron adds around a user path that contains spaces. `executableWillLaunchAtLogin` is true when any Run entry for that executable is still approved. It ignores arguments and includes machine-wide entries, so it is not the tray state. `launchItems` lists the matching entries. Each item's `enabled` flag is the Task Manager approval for that entry. Path comparison on those items is case-insensitive and uses the unquoted executable path.

`name` on `setLoginItemSettings` chooses the Run value. When it is omitted, Electron uses the app user model id. `getLoginItemSettings` reads `openAtLogin` from that same id. This app sets `app.setAppUserModelId('com.desktopcompanion.shell')` and passes that string as `name`. The two stay one constant, `APP_USER_MODEL_ID`.

`enabled: true` clears a Task Manager disable mark. This code always passes `enabled: true`. Turning the feature off uses `openAtLogin: false`, which deletes both the Run value and the approval value for that name. The code does not write a disabled approval blob of its own.

The arguments are an empty list on every write and every read. The path passed to Electron is the raw executable path. Electron quotes it when the registry command is built. The same unquoted path and the same empty argument list are passed to the read.

## 2. Registration scope

The checkbox can call the API only when all of these are true:

- The process is Windows.
- `DESKTOP_COMPANION_DEV` and `DESKTOP_COMPANION_SMOKE` are off.
- `process.execPath` is `%LOCALAPPDATA%\Programs\DesktopCompanion\DesktopCompanion.exe`.
- That file exists.
- The path is not under `node_modules`, `win-unpacked`, `release`, or `cursor`, and the file is not `electron.exe`, `node.exe`, `npm`, or Vite.

Development, `npm start`, smoke, and `release\win-unpacked` fail that check and never call `getLoginItemSettings` or `setLoginItemSettings`. The tray row is present and disabled, unchecked, and its click returns without a Windows call.

A successful enable writes only the current-user value `com.desktopcompanion.shell`, with the installed executable and no arguments. Machine-wide Run keys, scheduled tasks, and Windows services are not used. No elevation is requested.

The operating system is the source of truth. The choice is not stored in `user-preferences.json`.

## 3. Default and launch behavior

The default is off. Startup does not call `setLoginItemSettings`. Installation does not add the Run value. `runAfterFinish` remains false.

There is no separate login-launch mode. A start from Windows uses the same path as a normal start:

- The existing single-instance lock runs before the window is created. A second process logs `second-instance-exit` and leaves.
- Start Awake is still the saved preference. The new checkbox does not read or write it.
- Wandering still begins off.
- Chat stays closed until the user opens it.
- The microphone, Whisper, Qwen, and speech playback are not started by this feature.

## 4. External changes

A registered entry and an effectively enabled entry are different states. The entry is registered when the current-user value `com.desktopcompanion.shell` points at this installed executable. It is effectively enabled only when that same entry's `enabled` flag is true. The tray checkbox follows the effective state.

If Task Manager or Windows Settings disables the entry, the Run value can remain and `openAtLogin` can stay true while `enabled` is false. The checkbox is unchecked. Opening the menu only reads that state.

Checking the box again writes `openAtLogin: true` and `enabled: true`, which is Electron's supported way to clear the disable mark. Unchecking deletes this app's value by that name. Another Run value is not written or deleted.

The checkbox does not use `executableWillLaunchAtLogin`. That flag can be true because a different value, or a machine-wide entry, launches the same executable.

After a write, the code reads the login item again. Enable is accepted only when the read shows this app's entry registered, approved, and stored as the unquoted installed path with an empty argument list. Disable is accepted only when that entry is gone. A thrown call, a failed read, or a read that does not match the request leaves the checkbox on the effective state and does not report success. A failed read shows the box unchecked.

The menu is rebuilt after a toggle and on tray click and right-click, so a later open sees the current Windows state.

## 5. Uninstall and upgrade

Electron's API does not remove the Run value when the app is uninstalled. `build/installer.nsh` now defines `customUnInstall` beside the existing per-user install-mode hook.

On a real uninstall, the macro reads only `HKCU\...\Run\com.desktopcompanion.shell`. It deletes that value, and the matching StartupApproved value, when the command is this install's `DesktopCompanion.exe` or that quoted executable followed by arguments. Any other value name is left alone. `userData` is not referenced. HKLM is not referenced.

electron-builder runs the previous uninstaller with `--updated` during an upgrade. The macro sees `${isUpdated}` and leaves the Run value in place, so an update does not turn the feature on and does not clear a choice the user already made. The current 0.1.0 uninstaller does not contain this macro. It was not run.

The predicate `uninstallRemovesLoginValue` covers the same ownership rule in unit tests. Those tests do not write the registry and do not run the uninstaller. `makensis` later compiled this include while building the 0.1.1 installer. The 0.1.0 setup file was not replaced.

## 6. Files

- `src/shared/windowsLoginStartup.ts` — decision logic, with no Electron import.
- `src/main/windowsLoginStartup.ts` — the only `setLoginItemSettings` / `getLoginItemSettings` calls.
- `src/main/main.ts` — tray wiring after the app user model id is set. No startup write.
- `src/main/tray.ts` — Preferences checkbox.
- `src/shared/windowsLoginStartup.test.mts` — mocked API tests.
- `build/installer.nsh` — uninstall cleanup for this value only.
- `package.json` — test list.
- `src/shared/packagedRelease.test.mts` — identity assertion now follows `APP_USER_MODEL_ID`.

`user-preferences.json`, movement, animation, chat, and security preferences were not given a new field or a new behavior.

## 7. Security

The API stays in the main process. Preload, the renderer, and IPC do not gain a login channel. Sandbox, context isolation, `nodeIntegration: false`, `webSecurity`, and the production CSP are unchanged. The 1,024 MiB Whisper guard is unchanged. The feature does not request administrator rights and does not write HKLM.

## 9. Manual validation

The installed 0.1.1 app later showed the checkbox. Note 55 records the user checks and the real enable/disable registry result. A Windows sign-out or reboot is still a separate confirmation. It was not done.

A. Open the tray. Preferences contains Start Awake and Start with Windows. Start with Windows is unchecked.
B. Check Start with Windows. No administrator prompt appears.
C. The current-user Run value `com.desktopcompanion.shell` points at `%LOCALAPPDATA%\Programs\DesktopCompanion\DesktopCompanion.exe` with no arguments.
D. Start Awake stays whatever it was.
E. Uncheck Start with Windows. That Run value and its StartupApproved value are gone.
F. With the box on, disable the entry in Task Manager or Windows Settings. Reopen the tray. The box is unchecked. Check it again if the entry should be active.
G. Start the app once with Start Awake off and once with it on. Wandering stays off until the tray enables it. Chat, the microphone, and Qwen stay idle.
H. Start the app while it is already open. The second process exits and the first remains.
I. Quit and start from the Start Menu. Movement, sleep, and the tray still behave as in the validated build.

A Windows sign-out or reboot is a separate confirmation. It was not done.

Development and `release\win-unpacked` should show the row disabled and should not create the Run value.

## 11. Limitations

- The source changes are in the installed 0.1.1 app. Note 55 records that upgrade.
- The uninstall macro is in the 0.1.1 installer. The 0.1.0 uninstaller that ran during the upgrade did not contain it.
- The NSIS macro was reviewed, mirrored by unit tests, and compiled by `makensis` for the 0.1.1 installer.
- The clean smoke passed with no installed companion running. A later smoke needs that app closed again, because both share the single-instance lock.
- An approved entry with unexpected arguments is shown as on, because Windows will launch it. Reporting an enable as successful still requires the empty argument list and `openAtLogin` on the readback. Unchecking deletes this app's value by name.
- `executableWillLaunchAtLogin` can be true because another entry launches the same executable. The checkbox ignores that flag.
- Run values with any other name are left in place, including a value that happens to launch the same executable.
- A machine-wide startup entry is reported by Electron but is not treated as this checkbox and is not removed.

## 13. Installer lifecycle

`customInstall` is not defined, and `runAfterFinish` is false. A first install does not write the Run value.

electron-builder 26.18.0 upgrades by running the uninstaller that is already on the machine, with `--updated`. The installed 0.1.0 uninstaller has no login cleanup, and 0.1.0 never created this Run value. A later upgrade, after 0.1.1 is installed, runs that newer uninstaller. `customUnInstall` sees `${isUpdated}` and leaves the Run value and its StartupApproved value untouched, whether the entry is approved or disabled. `deleteAppDataOnUninstall` stays false, and the macro does not reference `%APPDATA%\desktop-companion`.

A real uninstall does not receive `--updated`. The macro then reads only `HKCU\...\Run\com.desktopcompanion.shell`. It deletes that value, and the matching StartupApproved value, when the command is this install's `DesktopCompanion.exe`. Other Run names are not read. The installed 0.1.1 uninstaller includes this macro. The 0.1.0 uninstaller that ran for the upgrade did not.
