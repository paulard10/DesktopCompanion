# M1.9B.1 — Trail transparency fix

Status: **transparency is fixed. Particles were still missing after the Windows test.** The delivery failure and the correction are in [M1.9B.2](25_M1.9B.2_NEON_TRAIL_PIPELINE.md).

The floating robot was already fine. Neon Trail was enabled, and a move showed a solid white rectangle under the robot with no neon-green pearls. That rectangle was the trail window. This build keeps the M1.9B canvas window. It does not add a graphics engine or a second WebGL context.

## 1. Verified root cause

Two independent faults stacked. Either one is enough to fail the visual test. Together they match the screenshot: a white block, and no green.

**The window background stayed white.** `createOverlayChrome()` already passes `transparent: true` and `backgroundColor: '#00000000'`. On this Windows 11 / Electron 44 setup that constructor option is not enough. The avatar window only becomes transparent after `setBackgroundMaterial('none')` and `setBackgroundColor('#00000000')` run on the created `BrowserWindow` (`src/main/overlayWindow.ts`). The trail window set the material and never set the color. An empty transparent HTML page then shows the native window color. Electron’s default is white.

**Every pearl was dropped before paint.** `Particle.born` is `Date.now()`, about 1.76e12 in October 2026. The trail preload parsed `born` with the same helper it uses for screen coordinates, and that helper rejects any number whose absolute value is above 100,000. `readTrailFrame` therefore delivered a real viewport and an empty particle list. The main process had already called `showInactive()` on the pearl box under the robot. The canvas had nothing to draw.

The page that loaded was `trail.html`. The white shape is that window, sized to the live pearl box, not a second surface and not the avatar. CSS `background: transparent` was already present and did not clear the native window color. No `fillRect` of white existed in the trail page.

## 3. Why the white rectangle appeared

The main process samples the avatar in DIP, births pearls by distance, and shows the trail window on the pearl bounds with `showInactive()`. That part ran. The renderer then received zero particles, so `paintPearl` never ran. Windows painted the unset window color through the transparent page. The rectangle sat under the robot because those bounds hug the pearls, which are born just behind the 160 DIP body.

## 4. How transparent canvas rendering is guaranteed

The trail window now follows the avatar’s working sequence:

1. Constructor chrome stays `transparent: true`, `frame: false`, `hasShadow: false`, `thickFrame: false`, `backgroundMaterial: 'none'`, `roundedCorners: false`, `focusable: false`.
2. Immediately after `new BrowserWindow`, and again on `show` and at the start of every `showAt`, the window calls `setBackgroundMaterial('none')` and `setBackgroundColor('#00000000')`.
3. `trail.css` sets `margin: 0` and `background` / `background-color: rgba(0, 0, 0, 0)` on `html`, `body`, and `canvas`. The HTML file does not use an inline style, so production CSP stays `style-src 'self'`.
4. Boot sets the same transparent background on the document element, the body, and the canvas.
5. The 2D context is created with `{ alpha: true }`. Each frame clears with `globalCompositeOperation = 'copy'` and `fillStyle = 'rgba(0, 0, 0, 0)'` across the bitmap, then returns to `source-over`. On Windows, `clearRect` on a transparent window can punch the clear back to opaque white. The copy-composite fill writes real transparent pixels instead.
6. `devicePixelRatio` changes only the canvas bitmap size. DIP positions are not multiplied. `trailLocal` subtracts the window origin, including a negative monitor origin.
7. `paintPearl` is still the only drawer: a white-green core a few DIP wide and a neon-green halo. That core is the pearl highlight, not a rectangle.
8. `requestAnimationFrame` runs only while pearls exist. An empty list cancels the loop.

Click-through and focus are unchanged. `lockPointer` always calls `setIgnoreMouseEvents(true)`. Nothing calls `setIgnoreMouseEvents(false)` or `.focus()`. `showInactive()` is the only show path. `before-input-event` is cancelled. On show, the trail calls `moveTop()` and then the avatar calls `moveTop()`.

**Fail-safe.** The window stays hidden, and no opaque fallback is created, when:

- the preload file is missing (`trail-preload-missing`, checked before `new BrowserWindow`);
- the main frame fails to load (`trail-load-failed`);
- the renderer process exits (`trail-renderer-gone`);
- the canvas or the 2D context is missing (`trail-renderer-fault`, and boot does not throw an error page);
- the renderer reports zero pearls drawn.

`pageFailed` blocks every later `showAt`. Avatar movement, chat, Whisper, and Pablo do not depend on the trail page. After a fault, **Disable Neon Trail** and then **Enable Neon Trail** to try again. Enable on an already-enabled trail does not rebuild the window.

## 5. How particle visibility was verified

One event, after the fix:

Desktop move → overlay publishes a DIP sample → `stepTrail` births a pearl whose `born` is `Date.now()` → main shows the pearl box only after `trail:hello` → `trail:spawn` → preload `readTrailFrame` keeps that timestamp and the DIP point → `trail.ts` maps it with `trailLocal` → `particleVisual` returns a positive alpha → `paintPearl` fills a green radial gradient → `trail:drew` reports a count greater than zero.

The unit test uses `born = 1_761_300_000_000`. The frame keeps one particle. At `born + 250` ms, alpha is above 0 and the diameter has shrunk. The same timestamp is rejected as a screen coordinate. A 1.5 device pixel ratio turns a 120×40 DIP viewport into a 180×60 bitmap and does not move the DIP point. `trailLocal(-1700, 80, -1920, 40)` is `{220, 40}`.

This session did not photograph the fixed window. The process already running `npm run dev` is the previous build, and it was left running. Live pixels need the manual steps in section 7.

Development-only logs, with no coordinates and no credentials, at most once a second:

- `desktop-companion: trail deliver count=N` when the main process sends pearls
- `desktop-companion: trail drew count=N` when the canvas reports a non-zero draw

A move that is working prints both with N greater than 0. `deliver` without `drew` means the renderer still dropped the payload. `drew` is not printed for a zero count; a zero count hides the window. `desktop-companion: trail canvas=2d maxFrameMs=` still prints when a burst ends.

## 7. Manual Windows validation

Quit the running Desktop Companion first. The open `npm run dev` process does not contain this fix. Then start it again. `npm run start` does not show the trail tray items.

1. `npm run dev`. The robot should not move, and no rectangle should appear.
2. Wake the robot. It starts asleep, and sleep clears the trail.
3. Tray: **Enable Neon Trail**. The desktop should stay clear until a move.
4. Move left, right, up, and down. Neon-green pearls should appear just behind the body, glow, shrink, and vanish. There should be no white or solid rectangle.
5. In the `npm run dev` terminal, confirm `trail deliver count=` and `trail drew count=` with a count above zero.
6. Stop movement. No new pearls. The ones on screen should finish fading, and the rectangle should not remain.
7. Return home. The trip home should leave a trail.
8. During a move, click a desktop icon through the trail and click the robot body. Typing in another app should keep focus.
9. Open chat during a trail. Pearls should disappear. The composer should keep focus.
10. Start the microphone or let Pablo speak. Travel should still wait. Text chat should still send.
11. **Disable Neon Trail**, then move. The robot should move with no pearls and no rectangle.
12. Enable again, move, then **Reset Trail**. Pearls should clear. The next move should draw again.
13. If Windows reduced motion is on, enable the trail and move. Movement should work, the trail should stay empty, and the console should show `desktop-companion: trail reduced-motion`.

If the trail page cannot load, the console shows `desktop-companion: trail-load-failed` or `trail-renderer-fault`, the trail window stays hidden, and the robot still moves.

## 8. Remaining limitations

- Live Windows pixels are not confirmed until the steps above are run on a restarted `npm run dev`.
- The trail stays off until **Enable Neon Trail**. There is still no saved preference and no wandering.
- Pearls stay on the one display that contains the robot.
- An open chat clears the trail. Sleep clears it. Stop lets the current pearls fade.
- A hitch longer than 48 DIP leaves a gap.
- The small white-green core inside each pearl is intentional. It is a few DIP across, not a window.
- The newest pearls can sit in the transparent part of the avatar window. The opaque robot covers anything directly under the sphere.
- After a trail fault, Disable and then Enable is required before the window is created again.
- `clearRect` is not used for the transparent clear. The copy-composite fill is the Windows-safe clear and stays on the same canvas.
