Status: **delivery fix implemented. Stop for a real Windows visual check.** This session did not see a green pixel on the desktop.

The white rectangle is gone. Movement still works. The dev terminal showed `trail enabled` and `travel command=… phase=moving`, and it did not show `trail deliver` or `trail drew`.

## 1. First confirmed failing stage

**Trail-window readiness.** The sandboxed preload throws before `contextBridge` runs, so the page never gets `window.trail`, never sends `trail:hello`, and the main process stays `ready=false`.

`commit` returns before `sendSpawn` and before `trail deliver` whenever `ready` is false. The canvas is never asked to paint. This is not a Canvas failure and not a movement failure.

## 3. Root cause and correction

Electron’s sandbox lets a preload script require Electron. It does not let that script require another application file. `trailPreload.js` was `require("../shared/neonTrail.js")` so it could parse birth timestamps. The script aborted, the bridge was missing, and pearls stayed in the main process.

The preload is a single file again. It forwards spawn, viewport, and marker payloads. The trail page, which Vite bundles, calls `readTrailFrame` and `readTrailViewport`. Birth timestamps are still accepted there. A `preload-error` hides the window and sets the fault flag. Avatar movement does not depend on it.

Each dev sample, at most once a second (sooner if pearls were born but not sent), prints:

`desktop-companion: trail status enabled=… ready=… visible=… fault=… samples=… spawned=… delivered=… alive=… hold=… size=…`

`hold` is why that sample birthed nothing: `baseline`, `still`, `hitch`, `full`, `outside`, `idle`, `asleep`, `chat`, `reduced`, `clear`, `no-work-area`, or `display`. `hold=none` means at least one pearl was born. No coordinates, chat, or credentials are logged.

A draw report, once per burst, prints count, age at arrival, how many were already expired, how many fell outside the canvas, and the canvas bitmap and DIP size.
