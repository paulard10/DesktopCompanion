# M1.9C — Autonomous wandering

Status: **implemented for development only.** Sleep coordination for a real wander is in [M1.9C.2](28_M1.9C.2_BOUNDED_EXPLORATION.md). A shutdown crash and a manual-move pause are fixed in [M1.9C.1](27_M1.9C.1_MOVEMENT_REGRESSION.md). Wandering stays off until Enable Wandering.

Wandering is off until **Enable Wandering**. `npm run start` does not show that item. Nothing in this build wakes a sleeping robot, and no model response can move the window.

## 1. Architecture

The planner is `src/shared/wander.ts`. It has no Electron, no timer, and no window calls. It returns one command or none: a direction, `home`, or `stop`, plus the time of the next check.

The overlay controller is still the only code that calls `setBounds`. A wander command goes through the existing `moveBy` and `moveHome` path, so speed, easing, work-area clamp, click-through, and the neon trail are unchanged. The trail is not drawn a second time. If Neon Trail is off, or reduced motion is on, a wander hop still moves and simply leaves no pearls.

The main process keeps a single `setTimeout`. It is created only while wandering is enabled and a future check exists. Disable, quit, sleep, and a manual move clear it. There is no wander interval. The 32 ms travel timer still runs only during a move, then stops.

## 3. Scheduling

Balanced mode. The numbers live at the top of `wander.ts`.

| Constant | Value |
| --- | --- |
| `WANDER_MIN_REST_MS` | 2 minutes |
| `WANDER_MAX_REST_MS` | 5 minutes |
| `WANDER_QUIET_MS` | 45 seconds |
| `WANDER_HOME_EVERY` | 3 journeys |
| Hop | 120 DIP, the existing nudge |

The rest length comes from a fixed integer seed, so a given seed always waits the same amount, and that amount is always inside 2–5 minutes. Enabling does not move. The first hop waits out that rest, and the robot must already be idle and visible. Hovering the robot, a body click, or an open chat resets the quiet clock. A skipped chance is not queued.

Every third departure is Return home. The other two are one short hop. The next hop avoids an immediate reversal when another direction has at least 48 DIP of room. A direction that would only twitch against the edge is skipped.

## 4. Safety

- Default off. The tray items use the same development gate as Move left.
- Sleep and the return to sleep cancel an owned hop and clear the timer. Wake is never called.
- Waking is not “fully awake.” The rest clock starts again at idle.
- Chat open, microphone or Whisper (`listening`), Pablo (`speaking`), and Qwen generation (`generating`) use the existing travel block. A new hop is not started. An hop already in motion pauses in place and is not followed by another request.
- Manual Move, Stop, and Return home cancel the wander claim immediately. The manual move replaces it. The next wander wait starts only after that move has finished.
- Disable clears the timer immediately and stops an owned hop.
- A display change stops an owned hop and starts a new wait on the new work area. The planner never receives a second monitor.
- Hops use the work area, so the taskbar is outside the range. Negative monitor origins stay valid.
- No keyboard hook. Typing in another application is not visible to the app. Typing in the chat is covered because an open chat already blocks travel.
- No focus, no click-through change, no mouse injection, no screen capture, no model call.
- The planner does not look at other windows. Short hops are the low-disruption policy, not an attention detector.

## 6. Manual validation

Quit the running app and start `npm run dev` again. Wandering stays off until you ask.

1. Wake the robot. Leave it. For at least two minutes it should not move on its own.
2. Tray: **Enable Wandering**. It should still wait. The terminal shows `wander enabled` and no immediate `wander depart`.
3. After the wait, one short hop. If Neon Trail is enabled, that hop leaves pearls. If the trail is disabled, the hop is plain.
4. It should rest again for minutes, not chain hops. Every third departure should head home.
5. During a hop, open chat, or start the microphone, or let Pablo speak. The robot should pause. Closing that block may finish the same hop. It should not start a second one.
6. Tray **Move left** or **Stop movement** during a hop. The manual command wins. Wandering does not add another move behind it.
7. **Return home** still works from the tray.
8. **Disable Wandering**. The current owned hop stops, and no later hop is scheduled. Sleep the robot, then enable wandering: it must stay asleep until you wake it yourself.
9. Clicks through the transparent frame still pass. The robot body still clicks. Focus stays in the other app.

`npm run start` should not show Enable Wandering.

## 7. Not in this build

Wandering is not saved, and it is not on in production. Turning it on for a normal launch needs an explicit later approval. The app still cannot see the active window or keystrokes outside its own chat.
